E1 Find the second-highest salary (3 ways) + employees who earn it Co. 2 
-- 1) Subquery: the highest salary below the overall MAX (works on every DB)
SELECT MAX(salary) AS second_highest
FROM employee
WHERE salary < (SELECT MAX(salary) FROM employee);

-- 2) DISTINCT + LIMIT/OFFSET (MySQL / PostgreSQL)
SELECT DISTINCT salary FROM employee
ORDER BY salary DESC
LIMIT 1 OFFSET 1;
--    Oracle 12c+ / SQL Server 2012+
SELECT DISTINCT salary FROM employee
ORDER BY salary DESC
OFFSET 1 ROWS FETCH NEXT 1 ROWS ONLY;

-- 3) DENSE_RANK: handles ties and generalises to the Nth highest
SELECT salary FROM (
  SELECT salary, DENSE_RANK() OVER (ORDER BY salary DESC) AS rnk
  FROM employee
) t WHERE rnk = 2
GROUP BY salary;   -- or use DISTINCT

-- Name + salary of every employee on the second-highest salary
SELECT name, salary FROM (
  SELECT name, salary, DENSE_RANK() OVER (ORDER BY salary DESC) AS rnk
  FROM employee
) t
WHERE rnk = 2;

Use DISTINCT (or DENSE_RANK) so that duplicate top salaries don't push the real second-highest value out. Way 1 returns NULL when no second value exists. For the Nth highest, change 2 to N, or use OFFSET N-1.

Expected answer: 95000, earned by Priya and Karan.

Approach 1: subquery with MAX (works in every dialect)

SELECT MAX(salary) AS second_highest
FROM employee
WHERE salary < (SELECT MAX(salary) FROM employee);
second_highest
95000
  • The inner query returns 120000. The outer query returns the highest salary below that.
  • Ties are handled correctly: the three 120000 rows are all excluded together.
  • NULLs are safe: MAX ignores NULLs, and NULL < 120000 is UNKNOWN, so that row is filtered out.
  • No second-highest (one distinct salary, or an empty table): returns one row containing NULL. That is often what the interviewer wants (it is the LeetCode #176 requirement).
  • It only works for N = 2. For N = 3 you would have to nest it again, so it does not generalise.

Approach 2: DISTINCT + LIMIT/OFFSET (or OFFSET…FETCH)

-- MySQL / PostgreSQL
SELECT DISTINCT salary
FROM employee
WHERE salary IS NOT NULL          -- required in PostgreSQL, where NULL sorts first in DESC
ORDER BY salary DESC
LIMIT 1 OFFSET 1;                 -- MySQL also accepts: LIMIT 1, 1

-- SQL Server 2012+ / Oracle 12c+ / PostgreSQL
SELECT DISTINCT salary
FROM employee
WHERE salary IS NOT NULL
ORDER BY salary DESC
OFFSET 1 ROWS FETCH NEXT 1 ROWS ONLY;

-- SQL Server, older style with TOP
SELECT MAX(salary) FROM employee
WHERE salary NOT IN (SELECT TOP 1 salary FROM employee ORDER BY salary DESC);

-- Oracle 11g and older, with ROWNUM
SELECT salary FROM (
  SELECT salary, ROWNUM rn FROM (
    SELECT DISTINCT salary FROM employee
    WHERE salary IS NOT NULL ORDER BY salary DESC)
) WHERE rn = 2;

Common mistake: leaving out DISTINCT.

SELECT salary FROM employee ORDER BY salary DESC LIMIT 1 OFFSET 1;
-- returns 120000 (the second of three 120000 rows), which is WRONG

Getting NULL instead of an empty result: when no second salary exists, LIMIT/OFFSET returns zero rows. To return NULL, wrap it as a scalar subquery:

SELECT (SELECT DISTINCT salary FROM employee
        WHERE salary IS NOT NULL
        ORDER BY salary DESC LIMIT 1 OFFSET 1) AS second_highest;

Approach 3: DENSE_RANK (best for "Nth highest" and for getting the names)

SELECT name, salary
FROM (
  SELECT name, salary,
         DENSE_RANK() OVER (ORDER BY salary DESC) AS rnk
  FROM employee
  WHERE salary IS NOT NULL
) ranked
WHERE rnk = 2;

Why DENSE_RANK and not RANK or ROW_NUMBER?

salary ROW_NUMBER RANK DENSE_RANK

120000 2 1 1
120000 3 1 1

90000 6 6 3
  • ROW_NUMBER() = 2 gives a 120000 row, which is wrong.
  • RANK() = 2 gives no rows, because RANK jumps from 1 to 4.
  • DENSE_RANK() = 2 gives the two 95000 rows, which is correct.

A CTE version reads more cleanly:

WITH ranked AS (
  SELECT e.*, DENSE_RANK() OVER (ORDER BY salary DESC) rnk
  FROM employee e WHERE salary IS NOT NULL
)
SELECT name, salary FROM ranked WHERE rnk = 2;

Approach 4: correlated subquery for the Nth highest (no window functions)

Logic: a salary is the Nth highest when exactly N−1 distinct salaries are greater than it.

-- N = 2
SELECT DISTINCT e1.salary
FROM employee e1
WHERE e1.salary IS NOT NULL       -- important, see the note below
  AND 1 = (SELECT COUNT(DISTINCT e2.salary)
           FROM employee e2
           WHERE e2.salary > e1.salary);
  • For 95000, the distinct salaries above it are {120000}, so the count is 1 = N−1. It matches.
  • NULL trap: without e1.salary IS NOT NULL, the NULL row gives a count of 0 (x > NULL is never true), so for N = 1 it would wrongly match alongside 120000.
  • Cost is O(n²). That is fine on small tables but slow on large ones. Prefer DENSE_RANK.

To get the names of the Nth-highest earners with this method:

SELECT name, salary FROM employee
WHERE salary = (SELECT DISTINCT e1.salary FROM employee e1
                WHERE e1.salary IS NOT NULL
                  AND 1 = (SELECT COUNT(DISTINCT e2.salary) FROM employee e2
                           WHERE e2.salary > e1.salary));

Getting the names with Approach 1

SELECT name, salary
FROM employee
WHERE salary = (SELECT MAX(salary) FROM employee
                WHERE salary < (SELECT MAX(salary) FROM employee));

Nth highest as a reusable MySQL function (classic follow-up)

DELIMITER $$

Likely follow-ups:

  • What if the table is empty? MAX returns NULL, while LIMIT and DENSE_RANK return no rows. Wrap the query in a scalar subquery (or use COALESCE) if you need exactly one row.
  • Which is fastest on a large table? With an index on salary, the MAX subquery and ORDER BY…LIMIT both use an index scan. DENSE_RANK needs a sort or window pass, so it is a little heavier, but it is the most flexible.

E2 Highest-paid employee(s) in each department (ties included) 
-- Window function (MySQL 8+, PostgreSQL, Oracle, SQL Server)
SELECT name, salary, dept_id FROM (
  SELECT e.*, RANK() OVER (PARTITION BY dept_id ORDER BY salary DESC) AS rnk
  FROM employee e
) t
WHERE rnk = 1;

-- Without window functions (correlated / tuple subquery)
SELECT e.name, e.salary, d.name AS dept
FROM employee e JOIN department d ON d.id = e.dept_id
WHERE (e.dept_id, e.salary) IN (

Approach 1: window function (preferred)

SELECT department, name, salary
FROM (
  SELECT d.name AS department, e.name, e.salary,
         RANK() OVER (PARTITION BY e.dept_id ORDER BY e.salary DESC) AS rnk
  FROM employee e
  JOIN department d ON d.id = e.dept_id
  WHERE e.salary IS NOT NULL      -- otherwise Neha (NULL) ranks 1st in Analytics on PostgreSQL/Oracle
) t
WHERE rnk = 1
ORDER BY department, name;
  • RANK or DENSE_RANK = 1 keeps ties. ROW_NUMBER = 1 picks one arbitrary row per department. Use it only when the requirement is exactly one row per group, and add a tie-breaker such as ORDER BY salary DESC, id.
  • PostgreSQL alternative: ORDER BY e.salary DESC NULLS LAST instead of the WHERE filter.

Approach 2: join with the grouped MAX (works everywhere, including MySQL 5.7)

SELECT d.name AS department, e.name, e.salary
FROM employee e
JOIN (SELECT dept_id, MAX(salary) AS max_sal
      FROM employee
      GROUP BY dept_id) m
  ON m.dept_id = e.dept_id
 AND m.max_sal = e.salary
JOIN department d ON d.id = e.dept_id
ORDER BY department, e.name;
  • The derived table is {1:120000, 2:120000, 3:95000, NULL:60000}. Joining back on both columns keeps every tied row.
  • The NULL group (Arjun) is dropped because NULL = NULL is not true in a join.

Approach 3: correlated subquery

SELECT d.name AS department, e.name, e.salary
FROM employee e
JOIN department d ON d.id = e.dept_id
WHERE e.salary = (SELECT MAX(e2.salary)
                  FROM employee e2
                  WHERE e2.dept_id = e.dept_id);

This is easy to read. It runs the subquery once per row, though the optimizer often rewrites it, so an index on (dept_id, salary) makes it fast.

Approach 4: NOT EXISTS (no one in the same department earns more)

SELECT d.name, e.name, e.salary
FROM employee e
JOIN department d ON d.id = e.dept_id
WHERE e.salary IS NOT NULL        -- without this, Neha is returned (see trap)
  AND NOT EXISTS (SELECT 1 FROM employee e2
                  WHERE e2.dept_id = e.dept_id
                    AND e2.salary > e.salary);

Trap: for Neha, e2.salary > NULL is never true, so NOT EXISTS is TRUE and she would show up as a top earner. That is why the explicit NULL filter is needed.

Wrong answer interviewers like to catch

SELECT dept_id, name, MAX(salary) FROM employee GROUP BY dept_id;

name is neither grouped nor aggregated. PostgreSQL, SQL Server, Oracle and MySQL with ONLY_FULL_GROUP_BY (the default since 5.7) reject it. Older MySQL returned an arbitrary name that was not necessarily the top earner.

Variations

  • Include departments with no employees (Finance shows up with NULLs): FROM department d LEFT JOIN (...ranked...) t ON t.dept_id = d.id AND t.rnk = 1.
  • Top 3 per department: WHERE rnk <= 3. Use DENSE_RANK if you mean the top three salary levels.

  • RANK vs ROW_NUMBER here? RANK keeps ties. ROW_NUMBER forces exactly one row per department, which you might want for "pick one", and then you should add a tie-breaker.
  • What index would help? A composite index on (dept_id, salary DESC) serves the grouping, the correlated subquery and the window partition sort.

E4 Window functions

A window function calculates a value across a set of related rows (the "window"). Unlike GROUP BY, it does not collapse those rows. Syntax: fn() OVER (PARTITION BY ... ORDER BY ... [ROWS ...]).

SELECT name, dept_id, salary,
  ROW_NUMBER() OVER (PARTITION BY dept_id ORDER BY salary DESC) AS rn,
  RANK()       OVER (PARTITION BY dept_id ORDER BY salary DESC) AS rnk,
  DENSE_RANK() OVER (PARTITION BY dept_id ORDER BY salary DESC) AS drnk,
  LAG(salary)  OVER (PARTITION BY dept_id ORDER BY salary DESC) AS prev_salary,
  LEAD(salary) OVER (PARTITION BY dept_id ORDER BY salary DESC) AS next_salary,
  SUM(salary)  OVER (PARTITION BY dept_id)                      AS dept_total,
  SUM(salary)  OVER (PARTITION BY dept_id ORDER BY salary DESC) AS running_total
FROM employee;
salary ROW_NUMBER RANK DENSE_RANK
900 1 1 1
800 2 2 2
800 3 2 2
700 4 4 (gap) 3 (no gap)
  • ROW_NUMBER: a unique sequence. Typical uses are de-duplication and top-N per group.
  • RANK: tied rows get the same rank, and the next rank skips numbers.
  • DENSE_RANK: tied rows get the same rank, with no gaps.
  • LAG/LEAD: read the previous or next row's value, e.g. to compare with the last reading or compute deltas.
  • SUM/AVG OVER: per-group totals or running totals, without needing GROUP BY.

What they are

A window function computes a value across a set of rows related to the current row without collapsing them. GROUP BY returns one row per group; a window function keeps every row and adds a computed column.

function_name(args) OVER (
    [PARTITION BY col, ...]          -- split rows into groups (like GROUP BY, but rows are kept)
    [ORDER BY col [ASC|DESC], ...]   -- order inside each partition
    [frame_clause]                   -- which rows relative to the current row (ROWS/RANGE BETWEEN ...)
)

Categories

Category Functions
Ranking ROW_NUMBER(), RANK(), DENSE_RANK(), NTILE(n), PERCENT_RANK(), CUME_DIST()
Offset/value LAG(col, n, default), LEAD(col, n, default), FIRST_VALUE(), LAST_VALUE(), NTH_VALUE()

Logical execution order: FROM → WHERE → GROUP BY → HAVING → window functions → SELECT → DISTINCT → ORDER BY → LIMIT. This is why you cannot use a window function in WHERE. Wrap it in a subquery or CTE and filter outside. (Some databases, such as Snowflake, BigQuery and Teradata, support QUALIFY for this; MySQL, PostgreSQL and SQL Server do not.)

Frames: ROWS vs RANGE (the most commonly misunderstood part)

ROWS  BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW   -- physical rows
RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW   -- all rows with the same ORDER BY value (peers) included
ROWS  BETWEEN 2 PRECEDING AND 1 FOLLOWING
ROWS  BETWEEN CURRENT ROW AND UNBOUNDED FOLLOWING
  • Default frame: with ORDER BY and no frame, it is RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW. Without ORDER BY, the frame is the whole partition.
  • Consequence 1 (ties): SUM(salary) OVER (ORDER BY salary) gives all three 120000 rows the same running total, because they are peers. Use ROWS (or add a unique tie-breaker) for a true row-by-row running total.
  • Consequence 2 (the LAST_VALUE trap): LAST_VALUE(name) OVER (PARTITION BY dept_id ORDER BY salary) returns the current row, not the department's last row, because the default frame ends at the current row. Fix it with ROWS BETWEEN UNBOUNDED PRECEDING AND UNBOUNDED FOLLOWING, or use FIRST_VALUE with the opposite ORDER BY.
SELECT name, dept_id, salary,
  FIRST_VALUE(name) OVER w AS lowest_paid,
  LAST_VALUE(name)  OVER (w ROWS BETWEEN UNBOUNDED PRECEDING AND UNBOUNDED FOLLOWING) AS highest_paid
FROM employee
WHERE dept_id IS NOT NULL AND salary IS NOT NULL
WINDOW w AS (PARTITION BY dept_id ORDER BY salary);   -- named window: MySQL 8, PostgreSQL

Practical uses

  • Deduplicate (keep the latest reading per IoT sensor):
    DELETE FROM sensor_reading WHERE id IN (
  SELECT id FROM (SELECT id, ROW_NUMBER() OVER (PARTITION BY sensor_id, reading_ts ORDER BY id DESC) rn
                  FROM sensor_reading) x WHERE rn > 1);
  • Latest status per incident: ROW_NUMBER() OVER (PARTITION BY incident_id ORDER BY updated_at DESC) = 1.
  • Gap detection (sensor went silent): reading_ts - LAG(reading_ts) OVER (PARTITION BY sensor_id ORDER BY reading_ts) > INTERVAL '5' MINUTE.
  • Top N per group, month-over-month change, percent of total: amount * 100.0 / SUM(amount) OVER ().

Likely follow-ups:

  • Window function vs GROUP BY? GROUP BY collapses rows into one per group. A window function keeps all rows and adds the aggregate alongside each one.
  • Can you filter on a window result in WHERE? No, because windows are evaluated after WHERE. Use a subquery or CTE (or QUALIFY where supported).
  • Performance? Each distinct PARTITION BY/ORDER BY combination needs a sort. An index matching (partition cols, order cols) can avoid it, and you should reuse the same window (a named WINDOW) where possible.
  • Which versions support them? MySQL 8.0+, PostgreSQL 8.4+, SQL Server 2005+ (frames since 2012), and Oracle 8i+.
E5 ACID properties Co. 2
  • Atomicity: either the whole transaction happens or none of it does. On failure it rolls back (@Transactional rolls back on a RuntimeException).
  • Consistency: a transaction moves the database from one valid state to another. Constraints, FKs and triggers still hold afterwards.
  • Isolation: concurrent transactions don't see each other's uncommitted work. The isolation levels are READ UNCOMMITTED, READ COMMITTED, REPEATABLE READ and SERIALIZABLE. They prevent dirty reads, non-repeatable reads and phantom reads respectively.
  • Durability: once a transaction commits, it survives a crash. This is done with write-ahead/redo logs.

Example: a money transfer debits one account and credits another, and both must succeed together.

Scenario: transfer ₹500 from account A (balance 1000) to account B (balance 200).

CREATE TABLE account (id INT PRIMARY KEY, holder VARCHAR(50),
                      balance DECIMAL(12,2) NOT NULL CHECK (balance >= 0));

START TRANSACTION;                                   -- BEGIN in PostgreSQL / SQL Server
UPDATE account SET balance = balance - 500 WHERE id = 1;   -- A
UPDATE account SET balance = balance + 500 WHERE id = 2;   -- B
INSERT INTO transactions(sender_id, receiver_id, amount) VALUES (1, 2, 500);
COMMIT;                                              -- or ROLLBACK on any error
Property Meaning In the transfer
Atomicity All statements succeed, or none take effect If the credit to B fails (for example the server crashes after the debit), the debit from A is rolled back. Money is never lost halfway. Implemented with the undo log / rollback segments.
Consistency A transaction moves the database from one valid state to another, and all constraints hold CHECK (balance >= 0), foreign keys and the business rule "total money A+B stays 1200" hold before and after. If A had only 300, the CHECK fails and the transaction rolls back.
Isolation Concurrent transactions do not see each other's intermediate state (to a degree set by the isolation level) Another transaction reading A and B mid-transfer never sees A=500 and B=200 (₹500 "missing"). Implemented with locks and/or MVCC.
Durability Once committed, the change survives crashes After COMMIT returns, A=500 and B=700 survive a power failure. Implemented with the write-ahead / redo log flushed to disk.

In Spring Boot:

@Service
@RequiredArgsConstructor
public class TransferService {
    private final AccountRepository accounts;

    @Transactional(isolation = Isolation.READ_COMMITTED, rollbackFor = Exception.class)
    public void transfer(Long fromId, Long toId, BigDecimal amount) {
        // Lock rows in a consistent order (lower id first) to avoid deadlocks
        Account from = accounts.findByIdForUpdate(fromId);   // SELECT ... FOR UPDATE
        Account to   = accounts.findByIdForUpdate(toId);
        if (from.getBalance().compareTo(amount) < 0) {
            throw new InsufficientFundsException(fromId);    // RuntimeException, so the transaction rolls back
        }
        from.debit(amount);
        to.credit(amount);
        // JPA dirty checking flushes both UPDATEs at commit, atomically
    }
}

public interface AccountRepository extends JpaRepository<Account, Long> {
    @Lock(LockModeType.PESSIMISTIC_WRITE)
    @Query("select a from Account a where a.id = :id")
    Account findByIdForUpdate(@Param("id") Long id);
}

Gotchas worth mentioning: by default Spring rolls back only on unchecked exceptions (use rollbackFor). @Transactional also does nothing on self-invocation (a call from inside the same class bypasses the proxy) or on private methods.

Dirty read T2 reads data T1 has written but not committed T1 debits A to 500 and has not committed. T2 reads 500 and approves a loan. T1 rolls back, so T2 acted on a value that never existed.
Non-repeatable read T1 reads the same row twice and gets different values, because T2 updated and committed in between A statement job reads A=1000, a transfer commits, and the job re-reads A=500 within the same transaction.
Phantom read T1 runs the same range query twice and gets different rows, because T2 inserted or deleted matching rows SELECT COUNT(*) FROM transactions WHERE amount > 1000 returns 2, then T2 inserts a new large transfer, and it returns 3.

public class Account {
    @Id Long id;
    BigDecimal balance;
    @Version Long version;   // UPDATE ... WHERE id=? AND version=?  → OptimisticLockException on a conflict
}

Likely follow-ups:

  • Optimistic vs pessimistic locking? Optimistic uses a version column, detects conflicts at write time and retries; it suits low contention. Pessimistic uses SELECT FOR UPDATE and blocks other writers; it suits high-contention money movement.
  • How do you keep ACID across microservices? You can't with a single database transaction. Use the Saga pattern (choreography or orchestration with compensating actions), the transactional outbox, and idempotent consumers. Avoid 2PC/XA in microservices.
  • What does propagation = REQUIRES_NEW do? It suspends the current transaction and starts an independent one, for example for an audit log that must be saved even if the outer transaction rolls back.
  • How do deadlocks happen, and how do you avoid them? Two transactions lock rows in opposite order. Lock in a consistent order, keep transactions short, and retry on deadlock errors.
E6 Stored procedures: what, why, "hierarchy" Hexaware

What: a precompiled, named block of SQL plus procedural logic, stored in the database. It accepts IN/OUT/INOUT parameters and is invoked with CALL or EXEC. Why: it saves network round-trips because the logic runs next to the data, gives a reusable and centrally owned piece of business logic, offers security (grant EXECUTE without granting table access), and benefits from a cached execution plan. Downsides: it is harder to version, test and port, and logic gets split between the app and the DB.

Hierarchy / how the DB objects relate:

  • Nested procedures: a procedure can CALL other procedures. For example, process_order calls validate_stock, then create_invoice, then log_audit. Nesting depth is limited (SQL Server allows 32). Transaction handling, i.e. who commits, should normally sit in the outermost procedure.
  • Functions: return a single value or a table and can be used inside SELECT/WHERE. They generally cannot perform DML or commit. Procedures can call functions. A function cannot call a procedure that modifies data.
  • Triggers: run automatically on INSERT/UPDATE/DELETE. They can call procedures.
  • Views: saved SELECTs (a virtual table). Procedures and functions can query them.
-- MySQL
DELIMITER //
CREATE PROCEDURE raise_dept_salary(IN p_dept INT, IN p_pct DECIMAL(5,2))
BEGIN
  UPDATE employee SET salary = salary * (1 + p_pct/100) WHERE dept_id = p_dept;
  CALL log_audit('RAISE', p_dept);      -- nested call
END //
DELIMITER ;
CALL raise_dept_salary(10, 5);

From Spring you can call it with @Procedure (Spring Data JPA), SimpleJdbcCall, or entityManager.createStoredProcedureQuery(...).

What

A stored procedure is a named, precompiled block of SQL and procedural logic (variables, IF, loops, cursors, error handlers) stored in the database and executed with CALL (MySQL/PostgreSQL) or EXEC (SQL Server). It can take IN, OUT and INOUT parameters, run DML and DDL, manage transactions, and return result sets.

Why use them

  • Fewer network round-trips: one call runs many statements, which helps with bulk or batch operations such as nightly aggregation of IoT readings.
  • Logic close to the data, which suits heavy set-based processing.
  • Security: grant EXECUTE on the procedure without granting table access.
  • Reuse by several applications or report tools.
  • Plan caching (in SQL Server and Oracle especially).

Nesting (the "hierarchy" in practice):

  • A procedure can call other procedures and functions. MySQL allows recursive calls only if max_sp_recursion_depth > 0; SQL Server limits nesting to 32 levels (@@NESTLEVEL).
  • A function can call other functions, but generally cannot call a procedure that modifies data (rules vary by database).
  • A trigger can call procedures or functions and can fire other triggers (cascading triggers). This is a common source of hidden behaviour and debugging pain.
  • A view can use functions.

MySQL example: fund transfer with IN/OUT parameters and error handling

DELIMITER $$

CREATE PROCEDURE transfer_funds(
    IN  p_from    INT,
    IN  p_to      INT,
    IN  p_amount  DECIMAL(12,2),
    OUT p_status  VARCHAR(30),
    OUT p_new_bal DECIMAL(12,2)
)
BEGIN
    DECLARE v_balance DECIMAL(12,2);

    -- Any SQL error: roll back and report it
    DECLARE EXIT HANDLER FOR SQLEXCEPTION
    BEGIN
        ROLLBACK;
        SET p_status = 'ERROR';
    END;

    START TRANSACTION;

    SELECT balance INTO v_balance FROM account WHERE id = p_from FOR UPDATE;

    IF v_balance IS NULL THEN
        SET p_status = 'ACCOUNT_NOT_FOUND';
        ROLLBACK;
    ELSEIF v_balance < p_amount THEN
        SET p_status = 'INSUFFICIENT_FUNDS';
        ROLLBACK;
    ELSE
        UPDATE account SET balance = balance - p_amount WHERE id = p_from;
        UPDATE account SET balance = balance + p_amount WHERE id = p_to;
        INSERT INTO transactions(sender_id, receiver_id, amount) VALUES (p_from, p_to, p_amount);
        COMMIT;
        SET p_status  = 'SUCCESS';
        SET p_new_bal = v_balance - p_amount;
    END IF;
END$$

DELIMITER ;

-- Call it
CALL transfer_funds(1, 2, 500, @status, @bal);
SELECT @status, @bal;

E7 Table A and Table B hold the same records: what does INNER JOIN return? Hexaware

If the join column is unique in both tables, you get every row once, i.e. as many rows as the table has. Duplicates multiply and NULLs never match (NULL = NULL evaluates to unknown).

A.val: 1, 1, 2, NULL        B.val: 1, 1, 2, NULL
SELECT * FROM A JOIN B ON A.val = B.val;
-> val 1: 2 x 2 = 4 rows
-> val 2: 1 x 1 = 1 row
-> NULL : 0 rows
Total = 5 rows (not 4)

For a value that appears m times in A and n times in B, the join produces m x n rows.

Short answer: an INNER JOIN returns every pair of rows (a from A, b from B) for which the join condition is TRUE. If both tables have the same unique values, you get one row per value, the same number of rows as each table. Duplicates multiply, and NULLs never match.

Case 1: same records, unique values

A.id: 1, 2, 3          B.id: 1, 2, 3
SELECT A.id AS a_id, B.id AS b_id FROM A INNER JOIN B ON A.id = B.id;
a_id b_id
1 1
2 2
3 3

That is 3 rows. LEFT, RIGHT and FULL joins would also return exactly 3 rows here, because every row has a match.

Case 2: same records, with duplicates (the interview trick)

A.id: 1, 1, 2          B.id: 1, 1, 2
value count in A count in B rows produced
1 2 2 2 × 2 = 4
2 1 1 1 × 1 = 1

Total: 5 rows, not 3. Each A row with value 1 matches both B rows with value 1.

a_id b_id
1 1
1 1
1 1
1 1
2 2

Rule: for each join key, output rows = (count in A) × (count in B).

Case 3: NULLs in both tables

A.id: 1, 2, NULL       B.id: 1, 2, NULL

INNER JOIN returns 2 rows (1 and 2). NULL = NULL evaluates to UNKNOWN, not TRUE, so the NULL rows never pair.

  • To match NULLs on purpose: ON A.id = B.id OR (A.id IS NULL AND B.id IS NULL), MySQL's ON A.id <=> B.id, or the standard IS NOT DISTINCT FROM (PostgreSQL, SQL Server 2022+).
  • LEFT JOIN would return 3 rows, with NULL | NULL for A's NULL row (unmatched, so B's columns are NULL-padded). FULL JOIN would return 4 rows: the two matches, plus A's NULL and B's NULL as separate unmatched rows.

Mixed worked example

A.id: 1, 2, 2, 3, NULL       B.id: 2, 2, 3, 4, NULL
key A count B count INNER rows
1 1 0 0
2 2 2 4
3 1 1 1
4 0 1 0
NULL 1 1 0

INNER = 5. LEFT = 5 + 2 unmatched A rows (1 and NULL) = 7. RIGHT = 5 + 2 unmatched B rows (4 and NULL) = 7. FULL = 5 + 2 + 2 = 9.

Same records, but no join condition (or ON 1=1)

That is a CROSS JOIN (Cartesian product): 3 × 3 = 9 rows for Case 1.

Related set operations interviewers sometimes want instead

  • SELECT * FROM A INTERSECT SELECT * FROM B returns the common rows with duplicates removed (Case 2 gives {1, 2}). In set operations, NULLs are treated as equal.
  • A EXCEPT B (MINUS in Oracle) returns rows in A but not in B. For tables with identical records it returns nothing.
  • UNION removes duplicates; UNION ALL keeps them.

Likely follow-ups:

  • How do you avoid row multiplication? Join on a unique key, deduplicate first (SELECT DISTINCT or ROW_NUMBER in a CTE), or use EXISTS when you only need to filter.
  • How do you check that two tables are identical? Run (A EXCEPT B) UNION ALL (B EXCEPT A) and confirm it is empty, and also compare COUNT(*) (and per-key counts) to catch differences in duplicates.
  • Is there any difference between JOIN and INNER JOIN? No. INNER is optional.
E8 20 records starting from the 5th row (first and last name) Co. 2 
-- MySQL / PostgreSQL
SELECT first_name, last_name FROM users
ORDER BY id
LIMIT 20 OFFSET 4;          -- MySQL also accepts: LIMIT 4, 20

-- Oracle 12c+ / SQL Server 2012+
SELECT first_name, last_name FROM users
ORDER BY id
OFFSET 4 ROWS FETCH NEXT 20 ROWS ONLY;

OFFSET 4 skips rows 1–4, so the result begins at row 5. Always include ORDER BY, because without it the row order is not deterministic. For pagination the general formula is OFFSET (page-1)*size. Spring Data's Pageable produces this SQL for you.

"Starting from the 5th row" means skip 4 rows and take 20, which gives rows 5–24 in the chosen order (ids 5–24 if ordered by id).

Why ORDER BY is mandatory

Tables are unordered sets. Without ORDER BY, the database may return rows in any order (insertion order, index order, or whatever a parallel scan produces), and the "5th row" can change between executions. That causes duplicated or skipped rows across pages. Always order by a unique column, or add a unique tie-breaker such as ORDER BY last_name, id.

MySQL

SELECT first_name, last_name
FROM users
ORDER BY id
LIMIT 20 OFFSET 4;

-- equivalent shorthand: LIMIT offset, count
SELECT first_name, last_name FROM users ORDER BY id LIMIT 4, 20;

PostgreSQL

SELECT first_name, last_name FROM users ORDER BY id LIMIT 20 OFFSET 4;
-- the SQL-standard form also works
SELECT first_name, last_name FROM users ORDER BY id OFFSET 4 ROWS FETCH NEXT 20 ROWS ONLY;

SQL Server 2012+

SELECT first_name, last_name
FROM users
ORDER BY id                         -- ORDER BY is REQUIRED for OFFSET/FETCH
OFFSET 4 ROWS FETCH NEXT 20 ROWS ONLY;

SQL Server 2008 and older (no OFFSET) use ROW_NUMBER:

SELECT first_name, last_name FROM (
  SELECT first_name, last_name, ROW_NUMBER() OVER (ORDER BY id) AS rn FROM users
) t
WHERE rn BETWEEN 5 AND 24;

Or TOP with NOT IN (works, but clumsy):

SELECT TOP 20 first_name, last_name FROM users
WHERE id NOT IN (SELECT TOP 4 id FROM users ORDER BY id)
ORDER BY id;

Oracle 12c+

SELECT first_name, last_name FROM users
ORDER BY id
OFFSET 4 ROWS FETCH NEXT 20 ROWS ONLY;

Oracle 11g and older use ROWNUM. ROWNUM is assigned before ORDER BY, so you need nested queries:

SELECT first_name, last_name FROM (
  SELECT a.*, ROWNUM rn FROM (
    SELECT first_name, last_name FROM users ORDER BY id
  ) a
  WHERE ROWNUM <= 24          -- upper bound in the middle layer (stops early)
)
WHERE rn >= 5;                -- lower bound outside

WHERE ROWNUM >= 5 on its own returns nothing. The first candidate row gets ROWNUM 1, fails the test and is discarded, so the next candidate also gets ROWNUM 1, and so on.

SELECT id, first_name, last_name FROM users
WHERE id > 24
ORDER BY id
LIMIT 20;

-- multi-column sort (last_name, id): row-value comparison (MySQL, PostgreSQL)
SELECT id, first_name, last_name FROM users
WHERE (last_name, id) > (:lastName, :lastId)
ORDER BY last_name, id
LIMIT 20;

  SELECT MAX(s) FROM (SELECT SUM(amount) AS s FROM transactions GROUP BY receiver_id) x
);

The derived table must have an alias (x) in MySQL, PostgreSQL and SQL Server.

Interpretation B: the single highest transaction and its receiver

FROM transactions t
JOIN users u ON u.id = t.receiver_id
WHERE t.amount = (SELECT MAX(amount) FROM transactions);

WHERE amount = (SELECT MAX…) is automatically tie-safe.

Variations interviewers chain on

-- Net balance per user (received − sent), including users with no transactions
SELECT u.id, u.first_name,
       COALESCE(r.recv, 0) - COALESCE(s.sent, 0) AS net
FROM users u
LEFT JOIN (SELECT receiver_id, SUM(amount) recv FROM transactions GROUP BY receiver_id) r ON r.receiver_id = u.id
LEFT JOIN (SELECT sender_id,   SUM(amount) sent FROM transactions GROUP BY sender_id)   s ON s.sender_id   = u.id;
-- Aggregate in subqueries BEFORE joining. Joining transactions twice and then summing multiplies rows (see E7).

-- Highest single amount received per receiver
SELECT receiver_id, MAX(amount) FROM transactions GROUP BY receiver_id;

-- Show sender and receiver names: join users twice with different aliases
SELECT t.id, s.first_name AS sender, r.first_name AS receiver, t.amount
FROM transactions t
JOIN users s ON s.id = t.sender_id
JOIN users r ON r.id = t.receiver_id;

Net result for the first five users: Asha −700, Ravi −300, Meena +1000, John +500, Priya −500. (Check: 0−700, 1200−1500, 1700−700, 1700−1200, 0−500. The values sum to 0, as they should.)

Edge cases:

  • Users who received nothing do not appear in a GROUP BY on transactions. Start from users LEFT JOIN ... if they must appear with 0.
  • A receiver_id that is NULL, or that has no matching user (orphan data), is dropped by the INNER JOIN.
  • Use DECIMAL, not FLOAT, for money.

Likely follow-ups:

  • Top 3 receivers? Use DENSE_RANK() <= 3 on the totals, or LIMIT 3 if ties don't matter.
  • Highest receiver per month? Partition the RANK by month: DATE_FORMAT(created_at,'%Y-%m') in MySQL, date_trunc('month', created_at) in PostgreSQL.
  • Which index helps? (receiver_id, amount), which is a covering index for the GROUP BY plus SUM.
E11 Explain Angular

Angular is Google's component-based, TypeScript framework for building SPAs. Its main pieces:

  • Components (template + class + styles) and standalone components, which are the default since v17 and don't need an NgModule. Older apps use NgModules.
  • Data binding: interpolation {{ }}, property binding [prop], event binding (event), and two-way binding [(ngModel)].
  • Dependency injection: services declared with @Injectable({providedIn:'root'}) hold shared logic and API calls.
  • RxJS Observables for async work, e.g. HttpClient, async pipe, switchMap, debounceTime.
  • Router: lazy-loaded routes, guards (canActivate), resolvers.
  • Forms: template-driven and reactive (FormGroup, validators).
  • Signals (v16+): signal(), computed(), effect() give fine-grained reactivity. Together with zoneless change detection they are the newer alternative to Zone.js.
  • Also: directives, pipes, HTTP interceptors (attach JWTs, handle errors), lifecycle hooks (ngOnInit, ngOnDestroy), and the CLI for scaffolding and builds.

One-liner: Angular is Google's TypeScript-based, component-driven framework for building single-page applications. It ships "batteries included": a router, HttpClient, forms, dependency injection, testing tools and the CLI, all in one opinionated, consistent structure. That is why it is popular for large enterprise dashboards.

4. Pipes

Pipes transform values in templates. Built-in pipes: date, currency, decimal, percent, uppercase, json, async, keyvalue, slice.

@Pipe({ name: 'timeAgo', standalone: true })      // pure by default: re-runs only when the input reference changes
export class TimeAgoPipe implements PipeTransform {
  transform(iso: string): string {
    const mins = Math.floor((Date.now() - new Date(iso).getTime()) / 60000);
    return mins < 1 ? 'just now' : mins < 60 ? `${mins} min ago` : `${Math.floor(mins / 60)} h ago`;
  }
}

The async pipe subscribes to an Observable or Promise, unsubscribes automatically on destroy, and marks the component for check under OnPush.

5. Services and dependency injection

A service is a class holding reusable logic or state (API calls, caching, WebSocket connections). Angular's hierarchical injector creates instances and passes them in.

@Injectable({ providedIn: 'root' })              // app-wide singleton, tree-shakable
export class IncidentService {
  private http = inject(HttpClient);             // inject() function (v14+); constructor injection also works
  private base = '/api/incidents';

  list(params: { page: number; size: number }) {
    return this.http.get<Page<Incident>>(this.base, { params: { ...params } });
  }
  acknowledge(id: number) {
    return this.http.patch<void>(`${this.base}/${id}/ack`, {});
  }
}
  • Injector hierarchy: environment/root injector, then route-level providers, then the element injector (component providers: [...] gives each component instance its own copy).
  • Tokens: InjectionToken<AppConfig>('APP_CONFIG') with { provide: APP_CONFIG, useValue: {...} }. Other provider types are useClass, useFactory and useExisting.
  • Resolution modifiers: inject(X, { optional: true, self: true, skipSelf: true, host: true }).

7. HttpClient and interceptors

// Functional interceptor (v15+)
export const jwtInterceptor: HttpInterceptorFn = (req, next) => {
  const router = inject(Router);                 // call inject() synchronously, not inside the async callback
  const token = inject(AuthService).token();
  const authReq = token ? req.clone({ setHeaders: { Authorization: `Bearer ${token}` } }) : req;
  return next(authReq).pipe(
    catchError((err: HttpErrorResponse) => {
      if (err.status === 401) router.navigate(['/login']);   // or try a refresh-token flow
      return throwError(() => err);
    })
  );
};

// main.ts, standalone bootstrap
bootstrapApplication(AppComponent, {
  providers: [
    provideRouter(routes, withComponentInputBinding()),
    provideHttpClient(withInterceptors([jwtInterceptor, loadingInterceptor, errorInterceptor])),
    provideAnimationsAsync(),
  ]
});

Classic version: a class implementing HttpInterceptor, registered with { provide: HTTP_INTERCEPTORS, useClass: JwtInterceptor, multi: true } in AppModule. Interceptors run in the order they are provided for requests, and in reverse order for responses.

9. Signals (Angular 16+, the modern reactivity primitive)

double   = computed(() => this.count() * 2);  // derived, memoized, lazy

  effect(() => console.log('count changed', this.count()));  // side effects (logging, localStorage, manual DOM)
}
inc() { this.count.update(c => c + 1); }      // or .set(5)
  • Interop with RxJS: toSignal(obs$, { initialValue: [] }) and toObservable(sig) from @angular/core/rxjs-interop.
  • Newer APIs: input(), output(), model(), viewChild(), linkedSignal(), and resource()/httpResource() for async data. Check which are stable in your Angular version.
  • Why signals: fine-grained change tracking (Angular knows exactly which views depend on which signal), no manual subscriptions in templates, and they enable zoneless change detection.

10. Change detection

  • Default: Zone.js patches async APIs (events, timers, XHR). After any of them, Angular checks the whole component tree from top to bottom.
  • OnPush: a component is checked only when (a) an @Input reference changes, (b) an event fires inside it, (c) the async pipe emits or a signal it reads changes, or (d) markForCheck() is called. You must use immutable updates: this.items = [...this.items, x], not push.
  • Zoneless: provideZonelessChangeDetection() drops Zone.js and relies on signals, the async pipe and events. It became stable in v20 and is the default for new projects in recent versions.
  • Tools: ChangeDetectorRef.markForCheck() / detectChanges(), plus track in @for to avoid re-rendering whole lists.
  • A real-time dashboard receiving many WebSocket messages per second must use OnPush or signals, and often buffers or throttles updates (bufferTime(500)).

Likely follow-ups:

  • Angular vs AngularJS? AngularJS (1.x) is JavaScript with MVC, $scope and digest cycles, and is end-of-life. Angular (2+) is TypeScript, components, RxJS and AOT compilation, and a complete rewrite.
  • What is AOT? Ahead-of-time compilation turns templates into JavaScript at build time, which gives faster startup, earlier template error detection, and smaller bundles. It is the default.
  • Observable vs Promise? An Observable is lazy, can emit many values, can be cancelled (unsubscribed), and has operators. A Promise is eager, resolves once, and cannot be cancelled.
  • How do you share data between components? Parent to child with input()/@Input, child to parent with output()/@Output, and between unrelated components with a shared service holding a signal or BehaviorSubject (or NgRx/SignalStore for large apps).

2. Live alert feed over WebSocket (STOMP with Spring)

@Injectable({ providedIn: 'root' })
export class AlertStreamService {
  private auth = inject(AuthService);                    // inject() must run in an injection context (field initialiser)
  private client = new Client({                          // @stomp/stompjs
    brokerURL: 'wss://[host]/ws',
    reconnectDelay: 5000,
    beforeConnect: () => { this.client.connectHeaders = { Authorization: `Bearer ${this.auth.token()}` }; }
  });
  private _alerts = signal<Alert[]>([]);
  readonly alerts = this._alerts.asReadonly();
  readonly highCount = computed(() => this._alerts().filter(a => a.severity === 'HIGH').length);

  connect() {
    this.client.onConnect = () =>
      this.client.subscribe('/topic/alerts', msg => {
        const alert: Alert = JSON.parse(msg.body);
        this._alerts.update(list => [alert, ...list].slice(0, 200));   // cap the list size
      });
    this.client.activate();
  }
  disconnect() { this.client.deactivate(); }
}

E13 Basic JavaScript concepts
  • Types: the primitives are string, number, bigint, boolean, undefined, null and symbol. Everything else is an object, including arrays and functions. typeof null === 'object' is a historical quirk.
  • Closures: a function remembers the variables of the scope where it was defined, even after that scope has returned. Closures are used for private state, factories and memoisation.
  • this: set by how a function is called. As an object method it is the object. In a plain call it is undefined in strict mode, or window otherwise. call/apply/bind set it explicitly. Arrow functions don't have their own this and inherit it lexically.
  • Promises / async-await: a Promise is a future value that is pending, fulfilled or rejected. async/await is syntactic sugar over promises; use try/catch for errors and Promise.all to run work in parallel.
  • Event loop: JS runs on a single thread with a call stack. When the stack is empty, all microtasks run first (promise callbacks), then the next macrotask (setTimeout, I/O). So setTimeout(fn,0) runs after Promise.resolve().then(fn).
  • == vs ===: == coerces types ('5' == 5 is true, null == undefined is true). === compares value and type with no coercion. Default to ===.

1. Data types

  • Primitives (7): string, number, bigint, boolean, undefined, symbol, null. They are immutable and copied by value.
  • Object (reference) types: objects, arrays, functions, Date, Map, Set and so on. They are copied by reference.

typeof 10n         // "bigint"
typeof 'hi'        // "string"
typeof undefined   // "undefined"
typeof null        // "object"   ← a historical bug
typeof []          // "object"   → use Array.isArray([]) === true

let a = { x: 1 }; let b = a; b.x = 2;

Falsy values: false, 0, -0, 0n, '', null, undefined, NaN. Everything else is truthy, including [], {} and '0'.

2. Scope

  • Global, function and block scope. let and const are block-scoped; var is function-scoped (see E14).
  • Lexical scope: a function sees variables where it is defined, not where it is called.
const city = 'Bengaluru';

  const zone = 'North';
  function inner() { return `${city}-${zone}`; }   // looks up the scope chain
  return inner();
}

3. Closures

A closure is a function bundled with references to its outer variables, which stay alive after the outer function returns.

function createCounter() {
  let count = 0;                       // private state
  return {
    inc: () => ++count,
    get: () => count
  };
}
const c1 = createCounter();
c1.inc(); c1.inc();
console.log(c1.get());   // 2
console.log(c1.count);   // undefined (truly private)

Uses: data privacy and the module pattern, function factories, memoization, debounce, event handlers, and RxJS operators.

function debounce(fn, ms) {
  let t;
  return (...args) => { clearTimeout(t); t = setTimeout(() => fn(...args), ms); };
}

5. Prototypes and inheritance

Every object has an internal [[Prototype]] link. Property lookup walks the prototype chain. class is syntactic sugar over prototypes.

6. Promises and async/await

  return new Promise((resolve, reject) =>
    setTimeout(() => (id > 0 ? resolve({ id, value: 42 }) : reject(new Error('bad id'))), 100));
}

  .then(v => console.log(v))       // 42
  .catch(e => console.error(e))
  .finally(() => console.log('done'));

  try {
    const [a, b] = await Promise.all([fetchSensor(1), fetchSensor(2)]);   // parallel

7. The event loop: microtasks vs macrotasks

JavaScript runs on a single thread. The event loop works like this:

  1. Run the current synchronous code (the call stack).
  2. Drain all microtasks: Promise .then/catch/finally, await continuations, queueMicrotask, MutationObserver.
  3. Render (in browsers), if needed.
  4. Take one macrotask (setTimeout, setInterval, I/O, UI events, MessageChannel), then go back to step 2.
console.log('1: sync');
setTimeout(() => console.log('2: timeout (macrotask)'), 0);
Promise.resolve().then(() => console.log('3: promise (microtask)'));
queueMicrotask(() => console.log('4: queueMicrotask'));
(async () => {
  console.log('5: async fn body runs sync');
  await null;
  console.log('6: after await (microtask)');
})();
console.log('7: sync');

Output:

1: sync
5: async fn body runs sync
7: sync
3: promise (microtask)
4: queueMicrotask
6: after await (microtask)
2: timeout (macrotask)

Why: the synchronous lines run first (1, 5, 7). Then all microtasks run in the order they were queued (3, 4, 6). Then the macrotask runs (2). An endless stream of microtasks can starve rendering and timers. Node.js also has process.nextTick, which runs before promise microtasks.

8. == vs ===

  • === is strict equality: no type coercion. Use it by default.
  • == is loose equality: it coerces types first.
0 == ''            // true   ('' → 0)
0 === ''           // false
'5' == 5           // true
null == undefined  // true   (the one useful case: x == null checks both)
null === undefined // false
null == 0          // false
[] == false        // true   ([] → '' → 0, false → 0)
NaN == NaN         // false  → use Number.isNaN(x)
Object.is(NaN, NaN)// true;  Object.is(0, -0) → false
{} === {}          // false  (different references)

Hoisting

During the creation phase of each scope, JavaScript registers declarations before running code. The code is not physically moved.

console.log(a);   // undefined   (var is hoisted and initialised to undefined)
var a = 10;
console.log(a);   // 10

let b = 20;

console.log(c);   // ReferenceError: Cannot access 'c' before initialization
const c = 30;

console.log(d);   // ReferenceError: d is not defined   (never declared, a different message)

Temporal Dead Zone (TDZ)

The TDZ is the period from the start of the block until the let/const declaration line runs.

let x = 'outer';
{
  // TDZ for the inner x starts here. It shadows the outer x even before its declaration.
  console.log(x);    // ReferenceError (not 'outer'!)
  let x = 'inner';
}

typeof undeclaredVar;   // "undefined" (safe)
typeof y;               // ReferenceError: y is in its TDZ
let y = 1;

function f(p = q, q = 1) {}   // f() → ReferenceError: q is accessed in its TDZ (default params are evaluated left to right)

The classic loop closure question

for (var i = 0; i < 3; i++) {
  setTimeout(() => console.log('var:', i), 0);
}
// var: 3
// var: 3
// var: 3

// let: 1
// let: 2

Why: var i is one function-scoped variable shared by all callbacks. By the time the timeouts run (macrotasks, after the loop finishes), i is 3. let j creates a new binding for each iteration, so each closure captures its own value.

}

Function declarations vs function expressions

function greet() { console.log('hello'); }

Precedence quiz:

console.log(typeof foo);   // "function"
var foo = 1;
function foo() {}
console.log(typeof foo);   // "number"

Why: during creation, the function declaration initialises foo, and the var foo declaration is ignored because the name already exists. At runtime, foo = 1 reassigns it.

Best practice

Use const by default, let when you must reassign, and never var in modern code. ESLint has the no-var and prefer-const rules for this, and they are commonly enabled in Angular projects.

  • Why does global var matter? var x at the top level becomes window.x and can clash with other scripts. let and const live in a separate declarative scope.

  • Pull (REST): WebClient (reactive) or OpenFeign/RestClient calling the vendor APIs. For periodic sync use @Scheduled or Quartz/ShedLock in a cluster. Track a lastSyncedAt value or cursor to do incremental pulls.

Key concerns to discuss

  • Authentication: API keys, OAuth2 client credentials, mutual TLS. Store secrets in a vault, never in code.
  • Mapping: an anti-corruption layer that translates vendor fields into our canonical domain model. Use MapStruct or a dedicated mapper. Make field mappings configurable per vendor where possible.
  • Validation: mandatory fields, value ranges (for example, AQI from 0 to 500), timestamps (convert to UTC, reject future-dated readings), units, and enums. Use Bean Validation plus custom rules.
  • Retries: exponential backoff with jitter. Retry only idempotent calls and transient errors (timeouts, 5xx, 429). Do not retry 4xx validation errors.
  • Rate limits: a client-side limiter (Resilience4j RateLimiter), respect Retry-After, batch requests, and use incremental fetches (since=lastSyncTime, cursor or ETag).
  • Circuit breaker and bulkhead: stop hammering a failing vendor, and isolate thread pools so one vendor cannot take down the service.
  • Idempotency: use a natural key (vendor + externalId + timestamp) with a unique constraint and upsert. Webhooks are redelivered and Kafka is at-least-once, so duplicates will happen.
  • Store raw and normalised: raw JSON (in a JSONB column, object storage or a Kafka topic) for audit, debugging, and reprocessing when mapping logic changes. The normalised tables serve queries and the UI.
  • Ordering and late data: use event time rather than processing time. Handle out-of-order data with last-write-wins on event_ts.
  • Schema evolution: a tolerant reader (@JsonIgnoreProperties(ignoreUnknown = true)), version adapters, and contract tests.
  • Monitoring: Micrometer counters (fetched, accepted, rejected), a "last successful sync" gauge, an alert when data is stale for more than N minutes, and a correlation ID in logs. Show data health on an ops dashboard.
  • Testing: WireMock with recorded vendor responses, Testcontainers, and a sandbox vendor environment.

@Component
@RequiredArgsConstructor
@Slf4j
public class AqiVendorClient {

    @CircuitBreaker(name = "aqiVendor", fallbackMethod = "fallback")
    @RateLimiter(name = "aqiVendor")
    @Retry(name = "aqiVendor")                 // backoff configured in application.yml; retries on IOException/5xx/429
    public List<VendorReading> fetchSince(Instant since) {
        return vendorWebClient.get()
                .uri(uri -> uri.path("/v1/readings").queryParam("since", since.toString()).build())
                .retrieve()
                .bodyToFlux(VendorReading.class)
                .collectList()
                .block(Duration.ofSeconds(30));   // blocking is fine inside a scheduler thread
    }

    private List<VendorReading> fallback(Instant since, Throwable t) {
        log.warn("AQI vendor unavailable since={}, cause={}", since, t.toString());
        return List.of();                       // skip this cycle; the watermark is not advanced

}

// 2) Scheduled poller with a watermark (incremental sync), safe across instances
@Component
@RequiredArgsConstructor
public class AqiSyncJob {
    private final AqiVendorClient client;
    private final IngestionService ingestion;
    private final SyncStateRepository syncState;

    @Scheduled(fixedDelayString = "${integration.aqi.poll-ms:60000}")
    @SchedulerLock(name = "aqiSync", lockAtMostFor = "PT5M")   // ShedLock: only one instance runs it
    public void sync() {
        Instant since = syncState.getWatermark("AQI").orElse(Instant.now().minus(Duration.ofHours(1)));
        List<VendorReading> batch = client.fetchSince(since);
        if (batch.isEmpty()) return;
        ingestion.ingest("AQI", batch);
        syncState.saveWatermark("AQI", batch.stream().map(VendorReading::observedAt)
                                        .max(Comparator.naturalOrder()).orElse(since));
    }
}

// 3) Ingestion: raw store → validate → map → idempotent upsert → publish
@Service
@RequiredArgsConstructor
public class IngestionService {
    private final RawPayloadRepository rawRepo;
    private final SensorReadingRepository readingRepo;
    private final DeadLetterRepository dlq;
    private final ReadingMapper mapper;
    private final Validator validator;
    private final KafkaTemplate<String, SensorReadingEvent> kafka;
    private final MeterRegistry metrics;

    @Transactional
    public void ingest(String source, List<VendorReading> batch) {
        for (VendorReading r : batch) {
            rawRepo.save(RawPayload.of(source, r.externalId(), toJson(r)));          // keep raw for audit/replay

            SensorReading reading = mapper.toCanonical(r);                           // units → SI, time → UTC
            Set<ConstraintViolation<SensorReading>> errors = validator.validate(reading);
            if (!errors.isEmpty()) {
                dlq.save(DeadLetter.of(source, r.externalId(), errors.toString()));
                metrics.counter("ingest.rejected", "source", source).increment();
                continue;
            }
            // Idempotent: unique (source, external_id) → INSERT ... ON CONFLICT DO NOTHING / upsert
            boolean inserted = readingRepo.insertIfAbsent(reading) == 1;
            if (inserted) {
                metrics.counter("ingest.accepted", "source", source).increment();
                // For strict consistency use the transactional outbox pattern instead of a direct send
                kafka.send("sensor.readings.normalized", reading.sensorId(), SensorReadingEvent.from(reading));
            }
        }
    }
}

    • 9–11 side lighter: same as above, but the lighter one is odd; if balanced, it is 11.
  • If 1,2,3,4 > 5,6,7,8: the odd ball is one of 1–4 (heavy) or one of 5–8 (light). Weighing 2: 1,2,5 vs 3,6,9 (9 is known good).
    • Balanced: it is 4 (heavy), 7 (light) or 8 (light). Weigh 7 vs 8. The lighter one is odd; if balanced, it is 4 (heavy).
    • Left heavier: it is 1 (heavy), 2 (heavy) or 6 (light). Weigh 1 vs 2. The heavier one is odd; if balanced, it is 6 (light).
    • Right heavier: it is 3 (heavy) or 5 (light). Weigh 3 vs 9. If 3 is heavier, 3 is the heavy ball; if balanced, 5 is the light ball.
  • If 1,2,3,4 < 5,6,7,8: use the same steps with heavy and light swapped.

Why it's possible: there are 12 × 2 = 24 possible answers (which ball, heavy or light), and 3 weighings with 3 outcomes each give 3³ = 27 distinguishable results. Each weighing must split the remaining possibilities roughly into thirds.

Label the balls 1–12. Weighing 1: 1 2 3 4 vs 5 6 7 8.

Case A: balanced. The odd ball is among 9–12; balls 1–8 are known good.

  • Weighing 2: 9 10 11 vs 1 2 3 (three good balls).
    • Balanced → ball 12 is odd. Weighing 3: 12 vs 1 tells you whether it's heavy or light.
    • 9 10 11 heavier → the odd ball is 9, 10 or 11 and is heavy. Weighing 3: 9 vs 10: the heavier one is odd; if balanced, 11 is heavy.
    • 9 10 11 lighter → the same, but light: the lighter of 9 and 10, or 11.

Case B: left side (1 2 3 4) heavier. Either one of 1–4 is heavy or one of 5–8 is light; 9–12 are good.

  • Weighing 2: 1 2 5 vs 3 6 9.
    • Balanced → the odd ball is 4 (heavy), or 7 or 8 (light). Weighing 3: 7 vs 8: the lighter is odd; if balanced, 4 is heavy.
    • Left heavier → 1 or 2 is heavy, or 6 is light. Weighing 3: 1 vs 2: the heavier is odd; if balanced, 6 is light.
    • Right heavier → 3 is heavy or 5 is light. Weighing 3: 3 vs 9: if 3 is heavier it's the odd (heavy) ball; if balanced, 5 is light.

Case C: left side lighter. Mirror case B with "heavy" and "light" swapped (one of 1–4 is light or one of 5–8 is heavy; same weighings).

How to present it in an interview: state the 24 vs 27 bound first, then explain the trick in weighing 2 of case B. Moving balls between pans and bringing in a known-good ball makes each outcome point to a different group of suspects. Interviewers care more about this structured reasoning than about a memorised tree.

Likely follow-ups:

  • If you know the odd ball is heavier? Up to 3³ = 27 balls: split into thirds each time.
  • Max balls in w weighings when heavy/light is unknown? (3ʷ − 3) / 2, which gives 12 for w = 3.
  • With an extra ball known to be good? 13 balls can be solved in 3 weighings.
E27 Puzzle: remove exactly half the water from a full cylindrical glass. Other rounds (Question List)
  • Tilt the glass slowly and let water pour out. Stop when the water surface touches the rim on one side and the very edge of the base on the other side.
  • That diagonal water surface passes through the cylinder's centre. Because a cylinder is symmetric about its centre, the plane cuts it into two equal volumes, so exactly half the water remains.
  • This does not work for a tapered (conical) glass. It is not symmetric about its centre, so the two parts would not be equal.

Answer: tilt the glass and pour slowly until the water surface runs exactly from the rim on one side to the bottom edge of the base on the other side, with the base just about to show. Stop there: exactly half the water is left.

Why it works: the water surface is then a plane through the cylinder's centre point (it joins the top edge on one side to the bottom edge directly opposite). A cylinder is point-symmetric about its centre, so that plane cuts it into two congruent pieces of equal volume: the water that stays and the empty space that was poured out.

Step by step

  1. Hold the glass over a sink and tilt it slowly.
  2. Keep pouring until the water line touches the edge of the base on the far side while still touching the rim on the pouring side.
  3. Stop and set the glass upright. The remaining water reaches exactly half the height.

Limits

  • It only works for a true cylinder. In a tapered glass (wider at the top) the same position leaves less than half, because more of the volume sits near the rim.
  • A ruler is the alternative: volume ∝ height in a cylinder, so measure the height and pour until the water is at half of it.

What interviewers look for: a solution without measuring tools, a justification (symmetry), and awareness of the assumption (straight sides). Saying "it fails for a tapered glass" shows you check assumptions, the same habit as checking edge cases in code.

Likely follow-ups:

  • How to leave one third? Not possible by tilting alone; you'd need a measurement.
  • Glass with a thick base? Use the bottom of the water column, not the outside of the glass.
  • Why not estimate by eye? It isn't precise, and the question asks for exactly half.
