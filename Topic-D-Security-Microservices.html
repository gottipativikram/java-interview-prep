D1 Authentication vs authorization in Java/Spring Boot. Hexaware
  • Authentication checks who you are (username/password, JWT, OAuth2 login). If it fails you get 401 Unauthorized.
  • Authorization checks what you are allowed to do (roles/authorities such as ROLE_ADMIN or incident:write). If it fails you get 403 Forbidden.
  • Authentication always comes first. In Spring Security, the AuthenticationManager authenticates the user and puts an Authentication object in the SecurityContextHolder. Authorization (authorizeHttpRequests, @PreAuthorize) then reads that object's getAuthorities().

Authentication (AuthN) answers "Who are you?". It checks an identity claim against something you can verify: a password, a signed token, a certificate, or an OTP. Authorization (AuthZ) answers "What are you allowed to do?". It runs after authentication and compares the authenticated principal's roles, authorities, scopes, or attributes against the rules for a resource.

Aspect Authentication Authorization
Question Who are you? What can you do?
Happens First After authentication succeeds
Input Credentials (username/password, JWT, client cert, API key) Principal + authorities + resource + action
Failure HTTP status 401 Unauthorized (really "unauthenticated") 403 Forbidden
Spring component AuthenticationManager, AuthenticationProvider, UserDetailsService, JwtDecoder AuthorizationManager, AuthorizationFilter, @PreAuthorize, hasRole()
Spring exception AuthenticationException (BadCredentialsException, InsufficientAuthenticationException) AccessDeniedException (AuthorizationDeniedException in 6.3+)
Result stored in SecurityContextHolder → Authentication object Decision only (granted/denied); nothing stored

   │ details      : remote IP, session id                   │

                 stored in SecurityContext

  • AuthN flow: a filter pulls credentials out of the request and builds an unauthenticated Authentication token, such as UsernamePasswordAuthenticationToken(username, password). The filter hands it to AuthenticationManager.authenticate(). On success it gets back an authenticated token with authorities, and that token goes into SecurityContextHolder.
  • AuthZ flow: AuthorizationFilter (the last filter in the chain) asks an AuthorizationManager<RequestAuthorizationContext> whether the current Authentication meets the URL rule. Later, method-security interceptors do the same check for @PreAuthorize and similar annotations.

Smart City example: a traffic operator logs into the command-centre UI with a username and password, and that is authentication. Their JWT carries ROLE_OPERATOR. They can GET /api/incidents but get a 403 on DELETE /api/incidents/{id}, which needs ROLE_ADMIN. That second check is authorization.

Likely follow-ups:

  • Why is 401 called "Unauthorized" if it means unauthenticated? It's a naming mistake in the HTTP spec. 401 means "send valid credentials" and should come with a WWW-Authenticate header. 403 means "I know who you are, and the answer is no".
  • Where is the Authentication stored between requests? In a stateful app, HttpSessionSecurityContextRepository keeps it in the HTTP session. In a stateless JWT app nothing is stored: every request re-authenticates from the token.
  • Is OAuth2 authentication or authorization? OAuth2 is a delegated authorization framework. OpenID Connect (OIDC) adds authentication on top of it with the ID token.
  • Can ThreadLocal context break with async code? Yes. Use DelegatingSecurityContextExecutor or SecurityContextHolder.MODE_INHERITABLETHREADLOCAL, or pass the context explicitly.
D2 How do you implement authentication & authorization in your project? Hexaware

Classes involved: SecurityFilterChain (the configuration), AuthenticationManager → DaoAuthenticationProvider → UserDetailsService (loads the user from the DB) and PasswordEncoder (BCrypt), a JwtAuthFilter extends OncePerRequestFilter, and SecurityContextHolder (holds the authenticated user for the current request).

Login:   POST /auth/login -> AuthenticationManager.authenticate(UsernamePasswordAuthenticationToken)
         -> UserDetailsService.loadUserByUsername -> PasswordEncoder.matches -> issue JWT (access + refresh)
Request: Bearer JWT -> JwtAuthFilter (validate signature/expiry) -> load authorities
         -> SecurityContextHolder.setAuthentication -> authorizeHttpRequests / @PreAuthorize -> controller
@Configuration
@EnableWebSecurity
@EnableMethodSecurity
@RequiredArgsConstructor
public class SecurityConfig {
    private final JwtAuthFilter jwtAuthFilter;

    @Bean
    SecurityFilterChain filterChain(HttpSecurity http) throws Exception {
        return http
            .csrf(csrf -> csrf.disable())                       // stateless REST API
            .sessionManagement(s -> s.sessionCreationPolicy(SessionCreationPolicy.STATELESS))
            .authorizeHttpRequests(auth -> auth
                .requestMatchers("/auth/**", "/actuator/health").permitAll()
                .requestMatchers(HttpMethod.DELETE, "/api/incidents/**").hasRole("ADMIN")
                .requestMatchers("/api/incidents/**").hasAnyRole("OPERATOR", "ADMIN")
                .anyRequest().authenticated())
            .addFilterBefore(jwtAuthFilter, UsernamePasswordAuthenticationFilter.class)
            .build();
    }

    @Bean PasswordEncoder passwordEncoder() { return new BCryptPasswordEncoder(); }

    @Bean
    AuthenticationManager authenticationManager(AuthenticationConfiguration cfg) throws Exception {
        return cfg.getAuthenticationManager();
    }
}
@Component
@RequiredArgsConstructor
public class JwtAuthFilter extends OncePerRequestFilter {
    private final JwtService jwtService;
    private final UserDetailsService userDetailsService;

    @Override
    protected void doFilterInternal(HttpServletRequest req, HttpServletResponse res, FilterChain chain)
            throws ServletException, IOException {
        String header = req.getHeader(HttpHeaders.AUTHORIZATION);
        if (header != null && header.startsWith("Bearer ")
                && SecurityContextHolder.getContext().getAuthentication() == null) {
            String token = header.substring(7);
            String username = jwtService.extractUsername(token);
            UserDetails user = userDetailsService.loadUserByUsername(username);
            if (jwtService.isValid(token, user)) {
                var auth = new UsernamePasswordAuthenticationToken(user, null, user.getAuthorities());
                auth.setDetails(new WebAuthenticationDetailsSource().buildDetails(req));
                SecurityContextHolder.getContext().setAuthentication(auth);
            }
        }
        chain.doFilter(req, res);
    }
}

Authorization in web apps generally:

  • Roles vs authorities. A role is a coarse authority with the ROLE_ prefix (hasRole("ADMIN")). An authority is a fine-grained permission (hasAuthority("incident:write")).
  • URL-based. Set in authorizeHttpRequests inside the filter chain, as shown above.
  • Method-based. @PreAuthorize / @PostAuthorize on service methods, enabled with @EnableMethodSecurity.
  • Domain/data-level. For example, "an operator can only see incidents in their own zone". Implement it with SpEL that calls a bean, or with query filters.

AuthController.login()
   │ authenticationManager.authenticate(
   │     UsernamePasswordAuthenticationToken.unauthenticated(user, pwd))
   ▼
ProviderManager  (implements AuthenticationManager)
   │ loops over List<AuthenticationProvider>; calls the first one whose supports(tokenClass) is true
   │ if none succeed → delegates to parent AuthenticationManager (if any)
   ▼
DaoAuthenticationProvider  (supports UsernamePasswordAuthenticationToken)
   │ 1. userDetailsService.loadUserByUsername(username)  → UserDetails (or UsernameNotFoundException)
   │ 2. preAuthenticationChecks: locked? disabled? expired?

   ▼

Timing-attack defence: when the user isn't found, DaoAuthenticationProvider still runs a dummy BCrypt check. Responses then take the same time whether or not the username exists, and UsernameNotFoundException is hidden as BadCredentialsException (hideUserNotFoundExceptions=true).

2.6 JwtService (jjwt 0.12 API)

@Service
public class JwtService {

    private final SecretKey key;
    private final Duration accessTtl;
    private final String issuer;

    public JwtService(@Value("${app.jwt.secret}") String base64Secret,
                      @Value("${app.jwt.access-token-ttl}") Duration accessTtl,
                      @Value("${app.jwt.issuer}") String issuer) {
        this.key = Keys.hmacShaKeyFor(Decoders.BASE64.decode(base64Secret)); // HS256 needs >= 32 bytes
        this.accessTtl = accessTtl;
        this.issuer = issuer;
    }

    public String generateAccessToken(UserDetails user) {
        Instant now = Instant.now();
        List<String> roles = user.getAuthorities().stream()
                .map(GrantedAuthority::getAuthority)
                .toList();
        return Jwts.builder()
                .id(UUID.randomUUID().toString())        // jti, needed if you ever want to revoke a token
                .issuer(issuer)
                .subject(user.getUsername())
                .claim("roles", roles)
                .issuedAt(Date.from(now))
                .expiration(Date.from(now.plus(accessTtl)))
                .signWith(key)                           // algorithm inferred from key → HS256
                .compact();
    }

    /** Verifies signature + exp + iss. Throws JwtException (ExpiredJwtException, SignatureException...) on failure. */
    public Claims parseAndValidate(String token) {
        return Jwts.parser()
                .verifyWith(key)
                .requireIssuer(issuer)
                .clockSkewSeconds(30)
                .build()
                .parseSignedClaims(token)    // rejects unsigned (alg=none) tokens
                .getPayload();
    }

    public String extractUsername(Claims claims) {
        return claims.getSubject();
    }

    @SuppressWarnings("unchecked")
    public List<String> extractRoles(Claims claims) {
        return claims.get("roles", List.class);
    }
}

2.7 JwtAuthFilter extends OncePerRequestFilter

OncePerRequestFilter makes sure the filter runs once per request, even when the request is forwarded or dispatched again for errors or async work.

@Component
@RequiredArgsConstructor
public class JwtAuthFilter extends OncePerRequestFilter {

    private static final String BEARER = "Bearer ";
    private final JwtService jwtService;

    @Override
    protected boolean shouldNotFilter(HttpServletRequest request) {
        return request.getServletPath().startsWith("/api/auth/");   // login/refresh don't need a token
    }

    @Override
    protected void doFilterInternal(HttpServletRequest request,
                                    HttpServletResponse response,
                                    FilterChain chain) throws ServletException, IOException {

        String header = request.getHeader(HttpHeaders.AUTHORIZATION);
        if (header == null || !header.startsWith(BEARER)) {
            chain.doFilter(request, response);          // no token → stays anonymous → AuthorizationFilter decides
            return;
        }

        String token = header.substring(BEARER.length());
        try {
            Claims claims = jwtService.parseAndValidate(token);

            if (SecurityContextHolder.getContext().getAuthentication() == null) {
                List<SimpleGrantedAuthority> authorities = jwtService.extractRoles(claims).stream()
                        .map(SimpleGrantedAuthority::new)
                        .toList();

                // Stateless: we trust the signed claims and skip the DB lookup.
                // To pick up "user disabled" immediately, load UserDetails here (costs one DB/cache hit).
                UsernamePasswordAuthenticationToken auth =
                        UsernamePasswordAuthenticationToken.authenticated(
                                jwtService.extractUsername(claims), null, authorities);
                auth.setDetails(new WebAuthenticationDetailsSource().buildDetails(request));

                SecurityContext context = SecurityContextHolder.createEmptyContext();
                context.setAuthentication(auth);
                SecurityContextHolder.setContext(context);
            }
        } catch (ExpiredJwtException ex) {
            request.setAttribute("auth_error", "TOKEN_EXPIRED");    // read by AuthenticationEntryPoint (see D3)
        } catch (JwtException | IllegalArgumentException ex) {
            request.setAttribute("auth_error", "TOKEN_INVALID");
        }
        chain.doFilter(request, response);
    }
}

Why chain.doFilter even on failure? The context stays unauthenticated. AuthorizationFilter then throws AccessDeniedException for protected URLs, ExceptionTranslationFilter sees an anonymous user, and calls the AuthenticationEntryPoint, which returns a clean 401. Error handling stays in one place.

Pitfall: when JwtAuthFilter is a @Component, Spring Boot also registers it as a normal servlet filter, so it runs twice: once outside the security chain and once inside it. Stop that with a FilterRegistrationBean that sets setEnabled(false) (below), or don't annotate the filter and create it with new in the config.

2.9 AuthController: login endpoint

public record LoginRequest(@NotBlank String username, @NotBlank String password) {}
public record TokenResponse(String accessToken, String refreshToken, long expiresInSeconds) {}

@RestController
@RequestMapping("/api/auth")
@RequiredArgsConstructor
public class AuthController {

    private final AuthenticationManager authenticationManager;
    private final JwtService jwtService;
    private final RefreshTokenService refreshTokenService;   // stores hashed refresh tokens in DB/Redis (see D5)

    @PostMapping("/login")
    public ResponseEntity<TokenResponse> login(@Valid @RequestBody LoginRequest req) {
        Authentication auth = authenticationManager.authenticate(
                UsernamePasswordAuthenticationToken.unauthenticated(req.username(), req.password()));
        // Throws BadCredentialsException / DisabledException → handled by @RestControllerAdvice (this is in the MVC layer)

        UserDetails user = (UserDetails) auth.getPrincipal();
        String access = jwtService.generateAccessToken(user);
        String refresh = refreshTokenService.issue(user.getUsername());
        return ResponseEntity.ok(new TokenResponse(access, refresh, 900));
    }
}
@RestControllerAdvice
public class AuthExceptionAdvice {
    @ExceptionHandler(BadCredentialsException.class)
    public ProblemDetail badCredentials() {
        return ProblemDetail.forStatusAndDetail(HttpStatus.UNAUTHORIZED, "Invalid username or password");
    }
    @ExceptionHandler(DisabledException.class)
    public ProblemDetail disabled() {
        return ProblemDetail.forStatusAndDetail(HttpStatus.UNAUTHORIZED, "Account disabled");
    }
}

2.10 Production alternative: OAuth2 Resource Server (no custom filter)

When an external IdP issues the tokens (Keycloak, Azure AD, Okta), you don't write a filter or a JwtService. Spring's BearerTokenAuthenticationFilter with a NimbusJwtDecoder validates RS256 signatures against the IdP's JWKS endpoint.

spring:
  security:
    oauth2:
      resourceserver:
        jwt:
          issuer-uri: https://keycloak.smartcity.local/realms/smartcity   # discovers jwks_uri, validates iss + exp
@Bean
SecurityFilterChain resourceServer(HttpSecurity http) throws Exception {
    http.csrf(AbstractHttpConfigurer::disable)
        .sessionManagement(sm -> sm.sessionCreationPolicy(SessionCreationPolicy.STATELESS))
        .authorizeHttpRequests(a -> a.anyRequest().authenticated())
        .oauth2ResourceServer(o -> o.jwt(j -> j.jwtAuthenticationConverter(keycloakRolesConverter())));
    return http.build();
}

@Bean
Converter<Jwt, AbstractAuthenticationToken> keycloakRolesConverter() {
    return jwt -> {
        Map<String, Object> realmAccess = jwt.getClaimAsMap("realm_access");
        @SuppressWarnings("unchecked")
        Collection<String> roles = realmAccess == null ? List.of()
                : (Collection<String>) realmAccess.getOrDefault("roles", List.of());
        List<GrantedAuthority> authorities = roles.stream()
                .map(r -> (GrantedAuthority) new SimpleGrantedAuthority("ROLE_" + r.toUpperCase()))
                .toList();
        return new JwtAuthenticationToken(jwt, authorities, jwt.getClaimAsString("preferred_username"));
    };
}

2.11 How authorization works in web apps

Layer 1: URL rules (authorizeHttpRequests), checked by AuthorizationFilter through a RequestMatcherDelegatingAuthorizationManager. Rules are checked in order, first match wins, so put specific rules before general ones and finish with anyRequest().

Layer 2: method security (@PreAuthorize). This gives finer, business-level checks such as "an operator can only edit incidents in their own zone". See D4.

Layer 3: domain/data-level filtering. Queries scoped to the user, e.g. WHERE zone_id IN (:userZones), or Hibernate filters and row-level security.

Roles vs authorities

Role Authority
What it is Coarse-grained job function Fine-grained permission
Example ROLE_ADMIN, ROLE_OPERATOR incident:write, sensor:read, SCOPE_profile
In code hasRole("ADMIN") → checks for authority "ROLE_ADMIN" hasAuthority("incident:write") → exact string match
Underneath Also just a GrantedAuthority, with the ROLE_ prefix convention GrantedAuthority

Common pattern: users get roles, roles map to permissions (a role→permission table), and both go into the authorities. Code checks permissions, which keeps role changes out of the code. RoleHierarchy lets ADMIN > SUPERVISOR > OPERATOR, so admins inherit everything automatically:

@Bean
static RoleHierarchy roleHierarchy() {
    return RoleHierarchyImpl.fromHierarchy("""
        ROLE_ADMIN > ROLE_SUPERVISOR
        ROLE_SUPERVISOR > ROLE_OPERATOR
        """);
}

Likely follow-ups:

  • Why addFilterBefore(UsernamePasswordAuthenticationFilter.class)? It's a well-known anchor in the chain. The authentication has to be in the context before AuthorizationFilter runs, and before form login would try anything.
  • Why BCrypt and not SHA-256? BCrypt is salted and deliberately slow, with a tunable cost. SHA-256 is fast, so it can be brute-forced on GPUs. Argon2 and PBKDF2 are also acceptable.
  • How do you support two auth mechanisms (JWT for UI, basic for actuator)? Define two SecurityFilterChain beans with different securityMatchers and @Order.
  • What replaced WebSecurityConfigurerAdapter? Component-based config: SecurityFilterChain beans, WebSecurityCustomizer, and the AuthenticationManager from AuthenticationConfiguration.
D3 Handling exceptions in authentication and authorization. Hexaware
  • 401: implement AuthenticationEntryPoint. It runs when an unauthenticated user hits a protected resource (missing, invalid or expired token).
  • 403: implement AccessDeniedHandler. It runs when the user is authenticated but lacks the required role.
  • Why @ControllerAdvice doesn't catch these: security filters run before the DispatcherServlet, so exceptions thrown there never reach the controller layer. ExceptionTranslationFilter turns them into calls to the entry point and the handler. One exception: method-security AccessDeniedException thrown from a @PreAuthorize inside the controller or service can reach @ControllerAdvice. For JWT parsing errors in your own filter, catch them and write the response yourself, or delegate to a HandlerExceptionResolver.
http.exceptionHandling(ex -> ex
    .authenticationEntryPoint((req, res, e) -> {
        res.setStatus(HttpServletResponse.SC_UNAUTHORIZED);
        res.setContentType("application/json");
        res.getWriter().write("{\"error\":\"Unauthorized\",\"message\":\"" + e.getMessage() + "\"}");

    .accessDeniedHandler((req, res, e) -> {
        res.setStatus(HttpServletResponse.SC_FORBIDDEN);
        res.setContentType("application/json");

3.1 Where security exceptions come from

Request ─► [Security filters ............................] ─► DispatcherServlet ─► Controller
            │                                         │           │
            │  JwtAuthFilter (our code)               │           └─ @PreAuthorize → AccessDeniedException
            │  BearerTokenAuthenticationFilter        │              (thrown inside MVC; @ControllerAdvice
            │     → AuthenticationException           │               CAN see this one, see 3.4)
            │  ExceptionTranslationFilter ◄───────────┤
            │     catches exceptions thrown BELOW it  │
            │  AuthorizationFilter → AccessDeniedException

ExceptionTranslationFilter logic:

try { chain.doFilter() }              // runs AuthorizationFilter and everything after
catch (AuthenticationException e)  → sendStartAuthentication() → AuthenticationEntryPoint.commence()   → 401
catch (AccessDeniedException e)
      if user is anonymous / remember-me → sendStartAuthentication() → AuthenticationEntryPoint → 401
      else                               → AccessDeniedHandler.handle()                         → 403

It only catches exceptions thrown after it in the chain. Anything thrown by a filter before it, our JwtAuthFilter included, never reaches it. That is why our filter doesn't throw. It records the reason and lets AuthorizationFilter reject the request.

3.2 Why @ControllerAdvice misses filter exceptions

@ControllerAdvice/@ExceptionHandler are run by the HandlerExceptionResolver that DispatcherServlet owns. Security filters run before the request reaches DispatcherServlet, in the servlet container's filter chain. An exception thrown in a filter climbs back up to Tomcat, which forwards to /error (Boot's BasicErrorController). You get a generic error body, and the advice never sees it.

Tomcat filter chain  ─► DelegatingFilterProxy ─► FilterChainProxy ─► ... ─► DispatcherServlet ─► @ControllerAdvice
                         ▲ exception thrown here never reaches here ──────────────────────────────┘

Options:

  1. Recommended: a custom AuthenticationEntryPoint and AccessDeniedHandler that write JSON.
  2. Inject HandlerExceptionResolver (qualifier handlerExceptionResolver) into the entry point or filter and call resolver.resolveException(req, res, null, ex). That forwards the exception into your @RestControllerAdvice, so all error formatting lives in one place.

@Component

    private final ObjectMapper mapper;

    @Override
    public void commence(HttpServletRequest request, HttpServletResponse response,
                         AuthenticationException authException) throws IOException {
        String code = Optional.ofNullable((String) request.getAttribute("auth_error")).orElse("UNAUTHENTICATED");
        String detail = switch (code) {
            case "TOKEN_EXPIRED" -> "Access token expired. Use the refresh token to get a new one.";
            case "TOKEN_INVALID" -> "Access token is malformed or its signature is invalid.";

        pd.setProperty("timestamp", Instant.now().toString());

        response.setContentType(MediaType.APPLICATION_PROBLEM_JSON_VALUE);
        mapper.writeValue(response.getOutputStream(), pd);
    }
}

4.4 Proxy limitations (frequently asked)

  1. Self-invocation: this.delete(id) from inside the same class skips the proxy, so no security check runs. Fixes: move the method to another bean, inject the bean's own proxy (@Lazy self-injection), or use AspectJ weaving (@EnableMethodSecurity(mode = AdviceMode.ASPECTJ)).
  2. Visibility: proxies only intercept public methods (CGLIB can technically handle protected/package methods, but don't rely on it). private and final methods are never intercepted.
  3. Only Spring beans: objects you create with new aren't proxied.
  4. @PostAuthorize runs after side effects: if the method changed the database, the change has already happened, unless a surrounding @Transactional rolls it back. Don't put it on mutating methods.
  5. Order with @Transactional: both are AOP advisors. Method security runs first by default (AuthorizationInterceptorsOrder), so a denied call never opens a transaction.
  6. Interface vs class: annotations on interface methods work, but annotate one place consistently.

  • URL security or method security? Both. URL rules give coarse protection at the edge. Method security puts the business rules next to the logic and also protects non-HTTP entry points such as Kafka listeners and schedulers.
  • What's the difference between hasRole('ADMIN') and hasAuthority('ADMIN')? hasRole adds the ROLE_ prefix (it checks ROLE_ADMIN). hasAuthority checks the exact string.

D5 How does JWT work? Co. 2
  • Structure: header.payload.signature, each part Base64URL-encoded.
    • Header holds the algorithm, e.g. {"alg":"HS256","typ":"JWT"}.
    • Payload holds claims: sub, roles, iat, exp, iss.
    • Signature is HMACSHA256(header + "." + payload, secret), or RS256 with a private key (services verify with the public key).
  • Signed, not encrypted. Anyone can read the payload, so never put secrets in it. The signature only proves the token was not tampered with.
  • Stateless. The server keeps no session. Every request carries Authorization: Bearer <token>, and each service checks the signature and exp locally. This scales well across microservices.
  • Expiry and refresh. Keep the access token short-lived (5–15 min). Use a longer-lived refresh token, stored server-side or in Redis so it can be revoked, to get a new access token from /auth/refresh. Rotate refresh tokens on each use.
  • Revocation is hard because tokens are stateless. Options: short TTL, a Redis blacklist of jti values, or a token version stored on the user.

5.1 Structure

A JWT (RFC 7519) is three Base64URL-encoded parts joined by dots: header.payload.signature.

eyJhbGciOiJSUzI1NiIsImtpZCI6ImsxIn0 . eyJzdWIiOiJvcDEiLCJyb2xlcyI6WyJPUEVSQVRPUiJdLCJleHAiOjE3...} . Qm9ndXNTaWduYXR1cmU...
└──────────── HEADER ──────────────┘   └──────────────────── PAYLOAD (claims) ─────────────────┘   └── SIGNATURE ──┘

HEADER  {"alg":"RS256","typ":"JWT","kid":"k1"}       ← kid picks the key from the JWKS
PAYLOAD {"iss":"https://keycloak/realms/smartcity",
         "sub":"op1", "aud":"incident-api",
         "exp":1767225600, "iat":1767224700, "nbf":1767224700, "jti":"7f3c...",
         "roles":["OPERATOR"], "zoneId":"Z-07"}
SIGNATURE = sign( base64url(header) + "." + base64url(payload), key )
  • Encoded, not encrypted. Anyone can Base64-decode the payload, so never put passwords, Aadhaar numbers, or PII in it. If the content must be confidential, use JWE (encrypted JWT).
  • Registered claims: iss (issuer), sub (subject), aud (audience), exp (expiry), nbf (not before), iat (issued at), jti (unique ID). Private/custom claims: roles, zoneId, tenant.

5.2 HS256 vs RS256 (and ES256)

HS256 (HMAC + SHA-256) RS256 (RSA + SHA-256) / ES256 (ECDSA)
Key type One shared secret Private key signs, public key verifies
Who can verify Anyone holding the secret, who can therefore also forge tokens Anyone with the public key; only the issuer can sign
Distribution The secret has to be copied to every service, which is risky Public keys published at a JWKS endpoint (/.well-known/jwks.json)
Key rotation Hard: every service must update together Easy: publish a new kid, keep the old one for a while
Speed Faster Slower (RSA); ES256 is faster and gives smaller signatures
Use when A single monolith signs and verifies its own tokens Microservices, external IdP (Keycloak, Auth0, Azure AD)

5.3 Validation steps (what a resource server must do)

1. Split into 3 parts; Base64URL-decode header & payload            → malformed? reject
2. Check header.alg is in an ALLOW-LIST (e.g. only RS256)           → never trust "alg" blindly; reject "none"
3. Pick the key by kid from the cached JWKS (refetch on unknown kid) → unknown? reject
4. Verify signature over header.payload                              → mismatch? reject
5. exp > now - skew ;  nbf <= now + skew                              → expired / not yet valid
6. iss == expected issuer                                            → token from another IdP? reject
7. aud contains this API                                             → token meant for another service? reject
8. (optional) jti not in revocation list; token type == "access"
9. Map claims → GrantedAuthorities → SecurityContext

Spring's NimbusJwtDecoder built from issuer-uri covers steps 1–6. Add audience validation like this:

@Bean
JwtDecoder jwtDecoder(@Value("${spring.security.oauth2.resourceserver.jwt.issuer-uri}") String issuer) {
    NimbusJwtDecoder decoder = JwtDecoders.fromIssuerLocation(issuer);
    OAuth2TokenValidator<Jwt> audience = new JwtClaimValidator<List<String>>(
            JwtClaimNames.AUD, aud -> aud != null && aud.contains("incident-api"));
    decoder.setJwtValidator(new DelegatingOAuth2TokenValidator<>(
            JwtValidators.createDefaultWithIssuer(issuer), audience));
    return decoder;
}

5.4 Expiry, refresh tokens and rotation

Access tokens are short-lived (5–15 min) because a stateless token can't easily be revoked. A refresh token is long-lived (hours to days), opaque or a JWT, stored server-side (hashed), and used only at /auth/refresh.

           login
Client ───────────────► Auth: issue AT(15m) + RT1(7d)   [store hash(RT1), family=F1]
  ... AT expires ...
Client ─ /refresh RT1 ─► Auth: RT1 valid & unused?
                           yes → mark RT1 used, issue AT' + RT2 (same family F1)   ← ROTATION
Attacker ─ /refresh RT1 (stolen, replayed) ─► Auth: RT1 already used!
                           → REUSE DETECTED → revoke whole family F1 → user must log in again
@Service
@RequiredArgsConstructor
public class RefreshTokenService {
    private final StringRedisTemplate redis;
    private static final Duration TTL = Duration.ofDays(7);

    public String issue(String username) {
        String token = Base64.getUrlEncoder().withoutPadding()
                .encodeToString(KeyGenerators.secureRandom(32).generateKey());
        redis.opsForValue().set("rt:" + sha256(token), username, TTL);
        return token;
    }

    /** Rotates: the old token is deleted atomically; a second use returns empty. */
    public Optional<String> consume(String token) {
        String username = redis.opsForValue().getAndDelete("rt:" + sha256(token));
        return Optional.ofNullable(username);
    }

    private static String sha256(String s) {
        try {
            byte[] d = MessageDigest.getInstance("SHA-256").digest(s.getBytes(StandardCharsets.UTF_8));
            return HexFormat.of().formatHex(d);
        } catch (NoSuchAlgorithmException e) { throw new IllegalStateException(e); }
    }
}

(Full reuse detection needs a token family ID so you can revoke every descendant token. The sketch above only shows single-use rotation.)

5.7 Common vulnerabilities

  1. alg: none: an attacker strips the signature and sets alg=none. Defence: an algorithm allow-list. jjwt's parseSignedClaims() rejects unsigned tokens.
  2. Algorithm confusion (RS256→HS256): the attacker signs with HS256 using the server's public key as the HMAC secret. A library that picks the verification method from the header accepts it. Defence: fix the expected algorithm and key type.
  3. Weak HMAC secret: brute-forced offline with hashcat. Use ≥256-bit random secrets.
  4. Not validating aud/iss: a token issued for service A gets accepted by service B.
  5. kid/jku injection: the header points to an attacker's key URL. Never fetch keys from URLs inside the header.
  6. Sensitive data in the payload (it's only Base64).
  7. Long-lived access tokens with no revocation.
  8. Tokens leaking in URLs (query strings end up in logs), in logs generally, or in error messages. Mask the Authorization header in logs.

Likely follow-ups:

  • JWT vs session ID? JWTs are self-contained and stateless, which scales across services with no session store, but they're hard to revoke and larger. Sessions are simple to revoke but need sticky sessions or a shared store (Spring Session + Redis).
  • What's an ID token vs an access token? ID token (OIDC) = who logged in, meant for the client. Access token = permission to call an API, meant for the resource server. Never send the ID token to APIs.
  • What's PKCE? Proof Key for Code Exchange: the SPA sends code_challenge = SHA256(verifier) on authorize and the verifier on token exchange, so a stolen auth code is useless. It's required for public clients.
  • How big should a JWT be? Keep it under ~4–8 KB. Proxies and servers limit header size, so don't stuff in hundreds of permissions.

Problems solved (pick one you can defend):

  • Clock skew between K8s nodes caused random 401s → set the validator clock skew to 60 s and enabled NTP sync.
  • JWKS fetch on every pod start hit Keycloak hard during scaling → cached JWKS (Nimbus does this by default) and fixed the key-rotation runbook.
  • Big tokens: fine-grained permissions as claims pushed headers over 8 KB → kept only roles in the token and resolved permissions from a Redis cache.
  • Migrating from custom JWT to Keycloak: for one release the gateway accepted both issuers (JwtIssuerAuthenticationManagerResolver).

Likely follow-ups:

  • Why validate in each service if the gateway already did? Defence in depth. If someone gets inside the cluster network they shouldn't be able to call services with forged headers.
  • How do Kafka consumers know who triggered an event? We put initiatedBy and correlationId in the event payload or headers. Consumers don't re-authenticate users; they trust the broker, which uses SASL/mTLS plus ACLs.
  • How would you force-logout a compromised user? Disable the user in Keycloak and revoke their sessions/refresh tokens. The access token expires in ≤5 min, and a jti deny-list covers the gap if that window is too long.
D7 Security layers for REST APIs; best practices; securing internal APIs. Other rounds (Question List)
  • Transport: HTTPS/TLS everywhere. Use mTLS between internal services, or a service mesh such as Istio.
  • Edge: the API Gateway is the single entry point. It handles JWT validation, rate limiting (Redis RequestRateLimiter), IP allow-lists and a WAF.
  • Identity: OAuth2/OIDC (Keycloak). Users use the auth-code + PKCE flow. Service-to-service calls use the client credentials flow. API keys go to third-party or IoT device clients, scoped and rotated.
  • Application:
    • Restrictive CORS (allowedOrigins set to your UI domain only, never * together with credentials).
    • Input validation with @Valid and Bean Validation.
    • Parameterized queries via JPA to prevent SQL injection.
    • Output encoding.
    • CSRF protection is only needed for cookie-based sessions.
  • Data: never log tokens, passwords or PII (mask them). Encrypt sensitive columns. Return DTOs, not entities.
  • Secrets: Vault, AWS Secrets Manager, or Kubernetes secrets with an encrypted Config Server. Never put secrets in Git.
  • Ops: follow the OWASP Top 10, scan dependencies (OWASP Dependency-Check, Snyk), add security headers, expose only health and info actuator endpoints, and keep audit logs.
  • Internal APIs: don't expose them publicly. Put them in a private network or VPC, reachable only through the gateway, and still verify tokens (zero trust).

Securing internal APIs that are also exposed to clients:

  • Publish them only through the gateway, on a separate route prefix (/partner/v1/**), with their own auth (OAuth2 client credentials, or API key + IP allow-list), quotas, and an OpenAPI contract.

Likely follow-ups:

  • Why is disabling CSRF OK for JWT APIs? CSRF works because browsers attach cookies automatically. A bearer token in the Authorization header is never attached automatically. Once you put the token in a cookie, you need CSRF protection again.
  • How do you keep the DB password out of application.yml? Vault with spring.config.import=vault://, or K8s Secrets mounted as env vars; rotate with Vault's dynamic DB credentials.
  • How do you prevent IDOR? Never trust IDs from the client alone. Check ownership or zone in the service layer, and scope queries with the caller's identity.
  • What is mTLS? Both client and server present X.509 certificates and verify each other, which gives mutual authentication at the transport layer. A service mesh automates certificate issuance and rotation.
D8 What are microservices; key things to take care of. Hexaware

Microservices split an application into small, independently deployable services. Each one owns a single business capability and its own data, and they communicate over APIs or events.

Key things to take care of:

  • Boundaries: use domain-driven design (DDD), keep each service cohesive, and give each one its own database.
  • Communication: choose sync or async deliberately, version your APIs, and design for idempotency.
  • Resilience: timeouts, retries, circuit breakers, bulkheads and fallbacks.
  • Data consistency: use the Saga or Outbox pattern instead of distributed transactions.
  • Observability: centralized logs (ELK), metrics (Prometheus/Grafana), tracing with correlation IDs.
  • Security: gateway authentication, propagated JWTs, service-to-service authentication.
  • Config & discovery: Config Server, Eureka or Kubernetes DNS.
  • DevOps: a CI/CD pipeline per service, Docker/Kubernetes, health checks, contract tests.

Definition: microservices are an architectural style where an application is a set of small, independently deployable services. Each one is built around a business capability, owns its data, runs in its own process, and talks to the others over lightweight protocols (HTTP/gRPC/messaging). A small team can build, deploy, and scale each service independently.

Likely follow-ups:

  • How big should a microservice be? Big enough to own one business capability, small enough for one team to understand and redeploy safely. Size by cohesion, not lines of code.
  • What's a distributed monolith? Services that must be deployed together or share a DB, with chatty synchronous chains between them. It has all the costs of microservices and none of the benefits.
  • When would you not use microservices? Small team, early product, unclear domain boundaries, no DevOps maturity.

10.1 Two styles

SYNCHRONOUS (request/response)                ASYNCHRONOUS (event/message)
A ──HTTP/gRPC──► B                            A ──publish──► [Kafka topic] ──► B
A waits (blocks/awaits) for B's answer        A continues immediately; B processes later
Criterion Sync (REST/gRPC) Async (Kafka/RabbitMQ)
Coupling Temporal coupling: B must be up Decoupled in time; the broker buffers
Latency to caller Immediate response Eventual; caller doesn't get B's result inline
Failure handling Timeouts, retries, circuit breakers Retries, DLT, replay; broker durability
Consistency Easier read-your-writes Eventual consistency
Scalability under bursts B must scale with A Queue smooths load; consumers scale independently
Fan-out A calls each consumer One event, many consumers (pub/sub)
Debugging Simpler call chain Harder; needs tracing across the broker
Best for Queries, validations that need an answer now ("is this user active?") State-change notifications, long jobs, integration, high-volume streams

10.4 gRPC

gRPC carries Protocol Buffers (binary, schema-first) over HTTP/2. It gives multiplexing, streaming (unary, server, client, bidirectional), generated clients, and fast serialisation. It suits internal high-throughput, low-latency calls (e.g. sensor-service → rules engine). Downsides: browsers can't call it directly (you need gRPC-Web), payloads aren't human-readable, and it needs HTTP/2-aware load balancing.   • Feign vs RestClient? Feign is declarative and integrates with Spring Cloud LoadBalancer and circuit breakers. RestClient is built in, with explicit control and no extra dependency. Both are fine; be consistent.

D11 Circuit breaker. Hexaware

A circuit breaker stops calling a failing service so that failures don't cascade, and returns a fallback instead.

It has three states:

  • CLOSED: calls go through normally. The breaker tracks the failure rate.
  • OPEN: the failure rate went over the threshold. Calls fail fast to the fallback for the wait duration.
  • HALF_OPEN: after the wait, a few trial calls are allowed. If they succeed the breaker goes back to CLOSED; if they fail it returns to OPEN.
CLOSED --(failure rate > 50%)--> OPEN --(wait 10s)--> HALF_OPEN --(trial ok)--> CLOSED
                                   ^-------------(trial fails)---------|
@CircuitBreaker(name = "userService", fallbackMethod = "userFallback")
public UserDto getUser(Long id) { return userClient.getUser(id); }

private UserDto userFallback(Long id, Throwable ex) {
    return new UserDto(id, "Unknown", "N/A");   // or a cached value
}

11.1 Why

Without a breaker, when service B is slow, every call from A waits until timeout, so A's threads pile up and A goes down too: a cascading failure. A circuit breaker fails fast once B is clearly unhealthy, gives B time to recover, and probes it periodically.

11.2 State machine

                failure rate ≥ threshold OR slow-call rate ≥ threshold
                (evaluated over sliding window, after minimumNumberOfCalls)
     ┌────────┐ ─────────────────────────────────────────────► ┌────────┐
     │ CLOSED │                                                │  OPEN  │  all calls rejected
     │ calls  │ ◄──────────┐                                   │        │  immediately with
     │ pass   │            │                                   └───┬────┘  CallNotPermittedException
     └────────┘            │ trial calls OK                        │       → fallback
          ▲                │ (failure rate < threshold)            │ waitDurationInOpenState elapses
          │           ┌────┴──────┐                                │
          └───────────│ HALF_OPEN │◄───────────────────────────────┘
                      │ permit N  │
                      │ trial     │──── trial calls fail ────► back to OPEN
                      │ calls     │
                      └───────────┘
  Extra states: DISABLED (always allow), FORCED_OPEN (always reject), METRICS_ONLY

11.3 Sliding windows

  • COUNT_BASED: the last N calls (a ring buffer). Example: size 10 with 5 failures = 50% failure rate.
  • TIME_BASED: calls in the last N seconds, stored as N one-second buckets. Better when traffic is uneven.
  • minimumNumberOfCalls: no decision is made until this many calls are recorded, so 1 failure out of 1 call doesn't open the circuit.
  • Slow calls: calls longer than slowCallDurationThreshold count toward slowCallRateThreshold. The breaker can open on latency alone, before any errors appear.

D12 Retry mechanism. Hexaware
  • Retry is for transient failures such as network blips and 503s. Don't retry 4xx errors or business errors.
  • Use exponential backoff with jitter so retries don't create a thundering herd.
  • Only retry idempotent operations, or make writes idempotent with an idempotency key.
  • Put Retry inside the CircuitBreaker so that retries count toward the failure rate.
@Retry(name = "trafficApi", fallbackMethod = "fallback")

  • Spring Retry is an alternative: @EnableRetry, then @Retryable(retryFor = IOException.class, maxAttempts = 3, backoff = @Backoff(delay = 500, multiplier = 2)) with a @Recover method.
  • Kafka: use @RetryableTopic(attempts = "4", backoff = @Backoff(delay = 1000, multiplier = 2)). Failed messages go to retry topics and finally to a DLT (@DltHandler) for alerting or manual replay. Alternatively use DefaultErrorHandler with DeadLetterPublishingRecoverer.

12.1 When to retry

Retry only transient failures: connection reset, timeouts, 503, 429 (honour Retry-After), Kafka NotLeaderForPartition. Don't retry permanent failures (400, 401, 403, 404, validation errors), because the result will never change.

Only retry idempotent operations, or make them idempotent first. GET, PUT, and DELETE are idempotent by HTTP semantics. A POST that creates an incident isn't. A retry after a timeout (where the first request actually succeeded) creates a duplicate. Fix it with an Idempotency-Key header that the server stores together with the result, or with a unique business key.

12.2 Backoff and jitter

Fixed:        |--500ms--|--500ms--|--500ms--|       → synchronized clients hammer B together
Exponential:  |-500-|---1000---|-------2000-------| → gives B time to recover
+ Jitter:     each wait = random(0.5x .. 1.5x)       → spreads retries; avoids the "thundering herd"

Retry storms multiply: with 3 layers that each retry 3 times, one user request becomes 27 calls to the bottom service. Retry at one layer (usually the one closest to the failing dependency), and cap the total time with timeouts.

12.4 Order: retry vs circuit breaker

Resilience4j's default aspect order (outermost first):

Retry ( CircuitBreaker ( RateLimiter ( TimeLimiter ( Bulkhead ( yourMethod ) ) ) ) )
  • Retry outside the circuit breaker (the default, recommended): every attempt is recorded by the breaker. Once the breaker opens, the next retry gets CallNotPermittedException straight away. Make that exception non-retryable (don't list it in retry-exceptions, or put it in ignore-exceptions) so you don't retry against an open circuit.
  • The fallback is attached to the outermost decorator you put fallbackMethod on. Usually that's only the circuit breaker, or the retry if you want the fallback after every attempt has failed.
  • Order can be changed with resilience4j.retry.retry-aspect-order and resilience4j.circuitbreaker.circuit-breaker-aspect-order (a higher value means higher priority, i.e. it runs outermost).

12.6 Kafka consumer retries: non-blocking retry topics + DLT

A blocking retry (DefaultErrorHandler with FixedBackOff) stops the whole partition while it retries one bad record. @RetryableTopic moves the failed record to delay topics, so the main topic keeps flowing:

incident.events ──fail──► incident.events-retry-0 (1s) ──fail──► -retry-1 (2s) ──fail──► -retry-2 (4s) ──fail──► incident.events-dlt
                                                                                                                  │
                                                                                     @DltHandler: alert, persist, manual replay
@Component
@Slf4j
@RequiredArgsConstructor
public class NotificationListener {

    private final NotificationService service;

    @RetryableTopic(
            attempts = "4",                                     // 1 original + 3 retries
            backoff = @Backoff(delay = 1000, multiplier = 2.0, maxDelay = 10000),
            dltTopicSuffix = "-dlt",
            exclude = {DeserializationException.class, IllegalArgumentException.class}, // straight to DLT
            autoCreateTopics = "true")
    @KafkaListener(topics = "incident.events", groupId = "notification-service")
    public void onIncident(IncidentEvent event) {
        service.notifyForIncident(event);   // throws → goes to the next retry topic
    }

    @DltHandler
    public void onDlt(IncidentEvent event,
                      @Header(KafkaHeaders.RECEIVED_TOPIC) String topic,
                      @Header(KafkaHeaders.EXCEPTION_MESSAGE) String error) {
        log.error("DLT {} event={} error={}", topic, event.eventId(), error);
        // save to failed_events table + raise alert; ops can replay after fixing
    }
}

(@Backoff here is org.springframework.retry.annotation.Backoff in Spring Kafka 3.x.) Note that retry topics break strict ordering for the retried key. If ordering matters, use a blocking retry with a short backoff instead.

Likely follow-ups:

  • How many retries? Usually 2–3 for sync calls, with the total bounded by the caller's timeout or SLA. More retries just add latency.
  • What is a retry budget? Cap retries to a percentage of traffic (e.g. ≤10%) so retries can't overload a struggling service.
  • How do you make a POST idempotent? The client sends an Idempotency-Key (UUID). The server stores key → response under a unique constraint and returns the stored response on a repeat.
  • What's in the DLT and how do you reprocess it? The original record plus exception headers. A small admin tool or consumer republishes it to the main topic once the bug is fixed.
D13 If Microservice B is down, what should A do? Hexaware
  1. Timeouts: never wait forever. Set connect and read timeouts, and use a Resilience4j @TimeLimiter.
  2. Retry a few times with backoff, but only for transient errors.
  3. Circuit breaker + fallback: fail fast and return a default, a cached last-known response (Redis), or a partial response.
  4. Go async: if B's work can wait, publish to Kafka or a queue. B consumes the message when it recovers. The user gets "202 Accepted, processing".
  5. Graceful degradation: for example, the incident dashboard still loads but shows "weather data unavailable".
  6. Bulkhead: isolate the thread pools for calls to B so A's other features keep working.
  7. Alerting/monitoring: health checks, Prometheus alerts on circuit state, Kubernetes restarts the pods, and multiple B replicas behind a load balancer.

Principle: A must degrade gracefully, never hang, and never cascade the failure. Layer the techniques:

Part A: Distributed caching

Why distributed rather than local? With 6 pods of incident-service, a local cache (Caffeine) gives 6 different copies: inconsistent, invalidated separately, and each pod warms up cold. A distributed cache (Redis/Hazelcast) is shared by all instances and survives pod restarts.

Two-level cache: L1 Caffeine in-process (microseconds, small, short TTL) + L2 Redis (sub-ms network hop, shared). This works well for very hot reference data such as zones and device types.

Caching patterns:

Pattern Flow Pros / Cons
Cache-aside (lazy loading) App reads the cache → on a miss, reads the DB → writes the cache. On update: write the DB, evict the cache Most common; only caches what's used. The first read is slow; there's a stale window
Read-through The cache library loads from the DB on a miss Simpler app code; needs cache-provider support
Write-through Write the cache and the DB synchronously Cache always fresh; slower writes
Write-behind (write-back) Write the cache; flush to the DB asynchronously Fast writes; risk of data loss
Refresh-ahead Refresh hot keys before their TTL runs out No miss spikes; extra load

Common problems:

  • Cache stampede / dogpile: a hot key expires and 1,000 requests hit the DB. Fixes: @Cacheable(sync = true) (per-JVM lock), a distributed lock, refresh-ahead, randomised TTLs.
  • Cache penetration: requests for IDs that don't exist always miss. Fixes: cache null results briefly, a Bloom filter.
  • Cache avalanche: many keys expire at once. Fix: TTL jitter.
  • Consistency: evicting on update is better than updating the cache. For cross-service invalidation, publish events.
  • Hot keys and big values: shard the key, compress, avoid values over 100 KB.

D17 What is Kafka and its working flow. Hexaware

Kafka is a distributed, durable, high-throughput event streaming platform built on an append-only log.

Producer --(key)--> Topic "sensor.readings" [P0][P1][P2]  (on Brokers, replicated)
                                 |    |    |
                   Consumer Group "analytics": C1<-P0,P1   C2<-P2
                   Consumer Group "alerts":    C3<-P0,P1,P2   (each group gets all messages)
  • Producer sends records to a topic. The key decides the partition (hash(key) % partitions), so records with the same key, such as the same sensor ID, land in the same partition and keep their order.
  • Topic is split into partitions, which are the unit of parallelism. Ordering is guaranteed only within a partition.
  • Broker is a Kafka server. A cluster holds the partitions. Each partition has a leader plus followers (replication factor of 3 is typical). acks=all together with min.insync.replicas=2 gives durability.
  • Consumer group: each partition is consumed by exactly one consumer in a group. Adding consumers (up to the partition count) scales consumption. Different groups each read every message independently.
  • Offsets are a consumer's position in a partition, committed to __consumer_offsets. Messages are retained by time or size, not deleted on read, so they can be replayed.
  • Reliability: idempotent producers and transactions give exactly-once semantics. Manual offset commits combined with idempotent consumers give safe processing.

  • Broker: a Kafka server that stores partitions and serves reads and writes.
  • Topic: a named stream of records, e.g. incident.events.
  • Partition: an ordered, append-only, immutable log. Partitions are the unit of parallelism and ordering. Each record has an offset, its position in the partition.
  • Segment: each partition is stored as segment files on disk (.log, .index, .timeindex). Old segments get deleted or compacted.
  • Replication: each partition has one leader (it handles all reads and writes by default) and followers that copy it. ISR (In-Sync Replicas) = replicas caught up within replica.lag.time.max.ms. If the leader dies, a new leader is elected from the ISR.
  • KRaft: since Kafka 3.3 it's production-ready, and in Kafka 4.0 it's the only mode. Metadata lives in an internal Raft-replicated __cluster_metadata topic managed by controller nodes. ZooKeeper is gone, so it's simpler to operate, fails over faster, and supports millions of partitions.

17.2 Producer flow

send(record) → serializer → partitioner → RecordAccumulator (batch per partition)
            → Sender thread → leader broker → write to log → followers fetch → ack
  • Partitioning: with a key, murmur2(key) % numPartitions, so the same key always goes to the same partition, which keeps ordering per key (e.g. all events for incident 42 stay in order). With no key, the sticky partitioner fills a batch for one partition before moving to the next.
  • Ordering: guaranteed only within a partition. Adding partitions later changes the key→partition mapping, so plan partition counts up front.
  • acks:
    • acks=0: fire and forget. Fastest, can lose data.
    • acks=1: the leader wrote it. Lost if the leader dies before followers copy it.
    • acks=all (-1): all ISR replicas have it. Combine with min.insync.replicas=2 and RF=3: the write survives one broker failure, and if the ISR shrinks below 2 the producer gets NotEnoughReplicasException instead of silently losing durability.
  • Idempotent producer (enable.idempotence=true, the default since Kafka 3.0): the broker dedupes retries using producer ID + sequence number, so there are no duplicates from producer retries and ordering is kept with max.in.flight.requests.per.connection ≤ 5.
  • Throughput tuning: batch.size, linger.ms, compression.type=lz4/zstd.

17.3 Consumer groups and rebalancing

  • Consumers in the same group split the partitions: each partition goes to exactly one consumer in the group. Parallelism is capped at the partition count (with 6 partitions, a 7th consumer sits idle).
  • Different groups each get every message (pub/sub). incident-service and reporting-service both read sensor.alerts on their own.
  • A group coordinator (a broker) tracks membership through heartbeats (session.timeout.ms, heartbeat.interval.ms) and poll calls (max.poll.interval.ms). If processing takes longer than max.poll.interval.ms, the consumer is kicked out and a rebalance happens.
  • Rebalancing reassigns partitions when consumers join or leave or partitions change.
    • Eager (old): everyone stops and gives up every partition, a "stop the world" pause.
    • Cooperative incremental (CooperativeStickyAssignor): only the moved partitions are revoked.
    • Static membership (group.instance.id): a pod restart within the session timeout doesn't trigger a rebalance.
    • KIP-848 (Kafka 4.0): a new consumer rebalance protocol with server-side assignment.

17.4 Offsets and commit strategies

Committed offsets live in the internal __consumer_offsets topic, per (group, topic, partition). The committed value is the next offset to read.

Strategy How Risk
Auto-commit (enable.auto.commit=true, every 5 s) Commits in the background during poll() A crash after commit but before processing → loss; a crash before commit → duplicates
Manual after processing (Spring AckMode.RECORD/BATCH, the Spring default is BATCH) Commit once the records are processed At-least-once: duplicates on a crash before commit, so make the consumer idempotent
AckMode.MANUAL(_IMMEDIATE) Call ack.acknowledge() in code Full control
Commit offsets in the DB transaction Store offset with the result in the same DB Effectively exactly-once into that DB

17.5 Delivery semantics

  • At-most-once: commit before processing. Can lose messages.
  • At-least-once: process, then commit. Can duplicate. This is the usual choice, paired with idempotent consumers.
  • Exactly-once (EOS): idempotent producer + transactions (transactional.id), consumer isolation.level=read_committed. Gives atomic consume-transform-produce within Kafka (Kafka Streams processing.guarantee=exactly_once_v2). Side effects outside Kafka (DB, SMS) still need idempotency or an outbox.

17.6 Retention and compaction

  • Delete policy: keep records for retention.ms (default 7 days) or retention.bytes, then delete whole segments. Consumers can replay anything inside the retention window by resetting offsets.
  • Compact policy (cleanup.policy=compact): keep the latest value per key (a tombstone, i.e. a null value, deletes the key). Good for "current state" topics such as device.status or changelogs.
  • Kafka is fast because of sequential disk writes, the OS page cache, zero-copy (sendfile), batching, and compression.

Both. Services call each other directly over the network (Feign/WebClient, using a service name), but they rely on shared infrastructure to do it:

  • Service registry (Eureka/Kubernetes DNS): finds instances by name. No hard-coded IPs.

@Service
@RequiredArgsConstructor
public class IncidentService {

    private final IncidentRepository incidentRepository;
    private final OutboxRepository outboxRepository;
    private final UserFeignClient userClient;
    private final IncidentMapper mapper;
    private final SlaPolicy slaPolicy;
    private final ObjectMapper objectMapper;

    @PreAuthorize("@zoneGuard.canAccess(#req.zoneId(), authentication)")
    @Transactional
    public IncidentDto create(CreateIncidentRequest req, String idemKey) {
        UserDto reporter = userClient.getUser(req.reporterId());       // Feign + circuit breaker
        if (!reporter.active()) {
            throw new BusinessValidationException("Reporter is inactive");
        }
        Incident incident = mapper.toEntity(req);
        incident.setStatus(IncidentStatus.NEW);
        incident.setSlaDueAt(slaPolicy.dueAt(req.categoryCode(), req.severity()));
        Incident saved = incidentRepository.save(incident);

        outboxRepository.save(OutboxEvent.of("Incident", saved.getId(), "IncidentCreated",
                toJson(mapper.toEvent(saved))));                       // same TX as the insert
        return mapper.toDto(saved);
    }

        catch (JsonProcessingException e) { throw new IllegalStateException(e); }
    }

D22 API response is slow: primary investigation. Hexaware
  • Measure first, don't guess. Use APM or tracing (Zipkin) to see which span is slow: gateway, service code, DB, or a downstream call. Check whether it is slow always or only under load (p95/p99 in Grafana).
  • DB (most common cause):
    • check query time in logs (spring.jpa.show-sql or the Hibernate statistics)
    • N+1 queries (fix with JOIN FETCH or @EntityGraph)
    • missing indexes
    • fetching too much data (use pagination and projections)
  • External calls: slow downstream services or missing timeouts. Fix with parallel calls (CompletableFuture/WebClient) or caching.
  • Resources:
    • Thread pool exhaustion (Tomcat threads) or HikariCP connection pool exhaustion: look for "connection is not available" errors.
    • CPU, memory, GC pauses (GC logs, heap dump).
    • Thread dumps for locks or blocking.
  • Payload: large JSON responses. Fix with compression, pagination, or returning fewer fields.

Common fixes:

  • N+1 → JOIN FETCH / @EntityGraph / @BatchSize / DTO projections
  • Missing index → add a composite or covering index
  • Big results → pagination (keyset for deep pages), projections, compression
  • Sequential downstream calls → parallel (CompletableFuture / WebClient zip), cache, or precompute with events
  • Pool exhaustion → keep transactions short, don't make remote calls inside transactions, tune the pool (maximum-pool-size ≈ what the DB can handle, not "bigger is better")
  • Heavy work in the request path → move it async (Kafka, @Async) and return 202
  • GC → right-size the heap, cut allocations, use G1/ZGC
  • High-concurrency I/O → virtual threads (Java 21, spring.threads.virtual.enabled=true)

Example story: "The incident dashboard API's p95 went from 300 ms to 3 s after a release. Zipkin showed 120 SELECT spans per request. Likely follow-ups:

D23 Delay caused by a stored procedure / SQL query: identify and fix. Other rounds (Question List)

Identify:

  • the DB slow query log (MySQL), pg_stat_statements (Postgres), or AWR/SQL Profiler (Oracle/SQL Server)
  • APM traces, and Hibernate SQL logs with timings

Analyze: run EXPLAIN / EXPLAIN ANALYZE (the execution plan) and look for:

  • full table scans
  • wrong join order
  • high row estimates versus actual rows
  • sorts or temp tables spilling to disk
  • functions on indexed columns (WHERE DATE(created_at) = ... kills the index)

Fix:

  • Indexes: composite indexes in the right column order, covering indexes.
  • Queries: avoid SELECT *. Rewrite correlated subqueries as joins or EXISTS. Filter early.
  • Paging: use pagination (keyset paging for big tables).
  • Statistics: update stats or ANALYZE, rebuild fragmented indexes.
  • Stored procedure internals: remove row-by-row cursors and use set-based logic. Watch for parameter sniffing.
  • Writes: batch them (hibernate.jdbc.batch_size).
  • Reads: cache frequently read results. Use materialized views or summary tables for reports. Archive or partition old data (for example, sensor readings by month).
  • Verify: re-run the execution plan and compare timings before and after.

23.1 Identify the slow statement

  1. Confirm the DB is where the time goes. A trace span or JDBC timing (datasource-proxy/p6spy) shows the slow SQL or the {call proc(?)}.
  2. DB-side tooling:
    • PostgreSQL: pg_stat_statements (top queries by total_exec_time, mean_exec_time), log_min_duration_statement = 500ms, auto_explain (logs plans of slow queries, including the ones inside functions with auto_explain.log_nested_statements=on), pg_stat_activity (running and blocked queries), pg_locks.
    • MySQL: slow query log (long_query_time), performance_schema, SHOW PROCESSLIST.
    • SQL Server: Query Store, sys.dm_exec_query_stats, Extended Events, actual execution plans.
    • Oracle: AWR/ASH reports, V$SQL, DBMS_XPLAN.DISPLAY_CURSOR.
  3. Inside a stored procedure: find which statement is slow. Add timing logs (RAISE NOTICE clock_timestamp() in PL/pgSQL, SET STATISTICS TIME ON in T-SQL), use nested-statement plan logging, or run each statement on its own with representative parameters.

What to look for in a plan:

  • Seq Scan / Table Scan / Full Table Scan on large tables with selective filters → missing or unusable index.
  • Estimated vs actual rows far apart (estimate 10, actual 2M) → stale statistics, which lead to the wrong join type.
  • Nested Loop with a large outer side, Hash Join spilling to disk, Sort spilling (external merge Disk) → work_mem, indexes, query shape.
  • Key Lookup / bookmark lookup (SQL Server), many heap fetches → make it a covering index.
  • High Buffers: shared read → IO-bound. loops=N multiplies the cost.

Saga: choreography vs orchestration

CHOREOGRAPHY (events, no central coordinator)
incident-svc ──IncidentApproved──► workorder-svc ──WorkOrderCreated──► crew-svc ──CrewAssigned──► incident-svc
                                                                         │ failure
                                       workorder-svc ◄──CrewUnavailable──┘  → compensate: cancel work order
                                       incident-svc  ◄──WorkOrderCancelled── → set incident ON_HOLD
 + loose coupling, simple for 2–4 steps     − flow is implicit and hard to follow, cyclic deps risk

ORCHESTRATION (central saga orchestrator sends commands)
                    ┌──────────── Dispatch Saga Orchestrator ────────────┐
                    │ 1. CreateWorkOrder → workorder-svc   (reply OK)    │
                    │ 2. AssignCrew      → crew-svc        (reply FAIL)  │
                    │ 3. compensate: CancelWorkOrder → workorder-svc     │
                    │ 4. MarkIncidentOnHold → incident-svc               │
                    └────────────────────────────────────────────────────┘
 + explicit flow, easy to monitor and change, good for many steps    − orchestrator is extra; risk of a "god service"
 Tools: Camunda/Zeebe, Temporal, Axon, Eventuate Tram, or a hand-rolled state table + Kafka

Saga rules: every step must be idempotent, compensations must be semantic undo operations (cancel, refund), not DB rollbacks, and a saga gives no isolation, so watch out for dirty reads (use a "PENDING" state and semantic locks).

  • Stateless: the server keeps no session. Each request carries everything needed to authenticate it, usually a JWT in the Authorization header. Any instance can serve any request, so the service scales out easily behind a load balancer.
  • Stateful: the server keeps the session (HttpSession, JSESSIONID cookie). Then you need either sticky sessions or a shared session store such as Spring Session + Redis, so that the session survives when an instance restarts or a request lands on another instance.

Where state lives In the token/client On the server / session store
Horizontal scaling Easy, any instance Needs sticky sessions or shared store
Logout / revoke Hard: use short expiry, refresh tokens, a denylist Easy: invalidate the session
Payload per request Larger (token) Small cookie
Typical fit REST APIs, microservices, mobile/SPA (Angular) Server-rendered web apps, admin portals
  • When each fits: use stateless JWT (e.g. Spring Security OAuth2 resource server) for microservices behind an API gateway. Use stateful sessions when you need instant revocation or are building a classic MVC app. In that case, store the sessions in Redis.

A stateless service keeps no client-specific data between requests: every request carries what's needed (for example a JWT), so any instance can serve it. A stateful service remembers the client between requests, typically in an HttpSession held in that server's memory.

Stateless (JWT) Stateful (server session)
Where state lives In the token, with the client On the server (memory or a session store)
Scaling behind a load balancer Any instance can serve any request Needs sticky sessions or a shared session store
Logout / revocation Hard: the token stays valid until expiry (short expiry + refresh tokens, or a deny-list) Easy: invalidate the session

Making a Spring Boot API stateless (Spring Security 6):

@Bean
SecurityFilterChain api(HttpSecurity http, JwtAuthFilter jwtFilter) throws Exception {
    return http
        .csrf(csrf -> csrf.disable())
        .sessionManagement(s -> s.sessionCreationPolicy(SessionCreationPolicy.STATELESS))
        .authorizeHttpRequests(a -> a.requestMatchers("/auth/**").permitAll().anyRequest().authenticated())
        .addFilterBefore(jwtFilter, UsernamePasswordAuthenticationFilter.class)
        .build();
}

If you must keep sessions across several instances, avoid sticky sessions (a pod restart logs users out) and share sessions in Redis with Spring Session:

# dependencies: spring-session-data-redis + spring-boot-starter-data-redis
spring:
  session:
    timeout: 30m
  data:
    redis:
      host: redis
      port: 6379

Stateful parts are still normal: databases, Kafka and caches are stateful by nature. "Stateless" is about the application tier, so pods can be killed, scaled and rolled out without losing user state.

Likely follow-ups:

  • How do you log out with JWT? Short access-token expiry (5–15 min), revoke the refresh token, and optionally keep a Redis deny-list of token IDs (jti) until they expire.
  • Downsides of sticky sessions? Uneven load, sessions lost when an instance dies, harder rolling deploys.
  • Is stateless always better? For APIs, usually; long multi-step workflows still persist state, just outside the instance (DB or Redis).
