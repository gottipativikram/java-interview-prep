Production & Troubleshooting Scenarios

F1 Your application suddenly throws OutOfMemoryError in production. How will you identify the root cause and fix it?
  1. Read the exact message: Java heap space, Metaspace, GC overhead limit exceeded and unable to create native thread each have a different cause.
  2. Make sure the JVM writes a dump when it fails: -XX:+HeapDumpOnOutOfMemoryError -XX:HeapDumpPath=/dumps. If the pod is still alive, take one yourself with jcmd <pid> GC.heap_dump /dumps/heap.hprof.
  3. Open the dump in Eclipse MAT. Use the Leak Suspects report and the Dominator Tree to find what retains the most memory, for example a static Map cache, an unbounded List, or ThreadLocals that are never cleared.
  4. Compare the trend of Actuator jvm.memory.used in Grafana with the deployment timeline.
  5. Fix the code, for example with a bounded Caffeine cache, streaming or pagination instead of findAll(), or closing resources. Only then size the heap correctly (-XX:MaxRAMPercentage=75 in Kubernetes).
  6. Add an alert on heap usage above 85% after GC.

Symptoms & first checks

  • Read the exact OOM message, because each one means something different: Java heap space, GC overhead limit exceeded, Metaspace, unable to create native thread, Direct buffer memory. A pod that is OOMKilled (exit code 137) with no Java OOM in the logs is a container memory problem, not a heap problem.
  • kubectl describe pod <pod> shows Last State, Reason and restart count. In Grafana, check jvm_memory_used_bytes{area="heap"}. A sawtooth whose floor keeps rising means a leak. A sudden spike means one large request.
  • Look at what changed recently: a deployment, a traffic spike, or a new report or export feature.

Step-by-step investigation

  1. Make sure the next OOM leaves evidence: -XX:+HeapDumpOnOutOfMemoryError -XX:HeapDumpPath=/dumps -XX:+ExitOnOutOfMemoryError. Mount /dumps on a PVC so the dump survives the restart.
  2. If the pod is still alive, take a live dump: kubectl exec <pod> -- jcmd 1 GC.heap_dump /dumps/heap.hprof, then kubectl cp it out.
  3. For a quick look without a full dump, run jcmd 1 GC.class_histogram | head -30 twice, a few minutes apart. Classes whose instance counts keep growing are your suspects.
  4. Open the dump in Eclipse MAT and run the Leak Suspects report. Then use the Dominator Tree and Path to GC Roots (exclude weak refs) to find who holds the memory, for example a static HashMap, a Hibernate PersistenceContext, or a ThreadLocal.
  5. Check the GC logs (-Xlog:gc*) to see whether full GCs ran back-to-back before the crash.
  6. For a Metaspace or native OOM, use jcmd 1 VM.metaspace and jcmd 1 VM.native_memory summary (this needs -XX:NativeMemoryTracking=summary).

Likely follow-ups:

  • Why use ExitOnOutOfMemoryError? After an OOM the JVM is in an undefined state. Exiting lets Kubernetes restart the pod cleanly.
  • Heap dump on a 4 GB heap freezes the pod? Yes. The JVM pauses during the dump. Take it from a pod that is out of rotation, or remove the pod from the Service first.
  • How do you tell a leak from under-sizing? With a leak, the old-gen floor keeps rising after each full GC. With under-sizing, the floor stays flat but sits close to the maximum.
F2 Multiple users are updating the same data simultaneously and wrong data is getting stored. How will you handle this concurrency issue?
  1. Confirm it is a lost update: two transactions read the same version and the last write wins.
  2. Optimistic locking (the default choice): add a @Version column. Hibernate adds WHERE version=? to the update and throws ObjectOptimisticLockingFailureException. Return 409 to the user or retry.
  3. Pessimistic locking when contention is high, for example a wallet balance: @Lock(LockModeType.PESSIMISTIC_WRITE), which issues SELECT ... FOR UPDATE.
  4. Prefer an atomic SQL update to read-modify-write: UPDATE account SET bal = bal - :amt WHERE id=:id AND bal >= :amt.
  5. Across several instances, use a distributed lock (Redis/Redisson) only when the database cannot enforce the rule.
@Entity class Incident { @Id Long id; @Version Long version; String status; }

Symptoms & first checks

  • This is the classic lost update: two requests read the same row, both modify it, and the last write silently overwrites the first. Typical examples are incorrect counters, overwritten status changes, and parking-slot double booking.
  • Check the code for a read-modify-write pattern (findById → set → save) with no versioning. Check the transaction isolation level (the PostgreSQL default is READ COMMITTED). Check for any synchronized block, which does nothing across multiple pods.

Step-by-step investigation

  1. Reproduce with concurrency: a JMeter or Gatling test, or a JUnit test that fires 50 CompletableFuture calls against the same ID.
  2. Turn on SQL logging (logging.level.org.hibernate.SQL=DEBUG) and confirm the UPDATE has no version predicate.
  3. Check the audit columns or pg_stat_activity for overlapping transactions on the same row.
  4. Decide on a strategy based on how much contention there is.

Cause How to confirm Fix
No optimistic lock UPDATE ... WHERE id=? only @Version
Counter computed in Java x = get(); set(x+1) Atomic SQL SET x = x + 1
JVM lock in a multi-pod setup synchronized / ReentrantLock DB lock or Redis lock
Check-then-insert race Duplicate rows appear Unique constraint plus handling the conflict

Fix / prevention For low contention, use optimistic locking:

@Entity
public class ParkingSlot {
    @Id private Long id;
    private String status;
    @Version private Long version;   // Hibernate adds "AND version=?"
}

@ExceptionHandler(ObjectOptimisticLockingFailureException.class)
ProblemDetail conflict() {
    return ProblemDetail.forStatusAndDetail(HttpStatus.CONFLICT,
            "Record was modified by another user, reload and retry");
}

For high contention or critical sections, use a pessimistic lock (SELECT ... FOR UPDATE):

public interface SlotRepository extends JpaRepository<ParkingSlot, Long> {
    @Lock(LockModeType.PESSIMISTIC_WRITE)
    @QueryHints(@QueryHint(name = "jakarta.persistence.lock.timeout", value = "3000"))
    @Query("select s from ParkingSlot s where s.id = :id")
    Optional<ParkingSlot> findForUpdate(@Param("id") Long id);

    @Modifying
    @Query("update Wallet w set w.balance = w.balance - :amt where w.id = :id and w.balance >= :amt")
    int debit(@Param("id") Long id, @Param("amt") BigDecimal amt);   // atomic, returns 0 if insufficient
}

Call findForUpdate inside a @Transactional service method. Send the version to the UI (or as an ETag / If-Match header) so a stale form gets a 409 instead of overwriting newer data. For cross-service locks, use Redisson RLock with a lease time.

Likely follow-ups:

  • Optimistic or pessimistic? Optimistic when conflicts are rare, because it takes no locks and scales well. Pessimistic when conflicts are frequent or a retry is expensive.
  • Would SERIALIZABLE help? Yes, but PostgreSQL then raises serialization failures that you must retry, and throughput drops.
  • Retry on an optimistic lock failure? Only for server-side merges that are safe to repeat, for example @Retryable(retryFor = ObjectOptimisticLockingFailureException.class). For user edits, return 409 and let the user reload.
F3 One API is taking 20 seconds response time only in production, but locally it works fine. How will you debug it?
  1. Look at the trace (Zipkin/Jaeger, Micrometer Tracing) to see which span takes the time: database, a downstream HTTP call, or the service's own code.
  2. Check Actuator /actuator/metrics/http.server.requests?tag=uri:/api/x for p95/p99 latency. Also check hikaricp.connections.pending, because waiting for a connection is a common cause.
  3. Database: production has far more data than local. Run EXPLAIN ANALYZE on the query and look for a missing index or a sequential scan. Enable pg_stat_statements to find slow queries.
  4. Take 3–4 jstack <pid> dumps a few seconds apart while the request runs, to see where threads are blocked (socket read, lock, pool wait).
  5. Check what differs in production: DNS or network latency, missing timeouts on RestClient/WebClient, SSL handshakes, logging set to DEBUG.
  6. Fix it (index, timeout, caching, async), then confirm with a load test.

Symptoms & first checks

  • "Only in prod" almost always comes down to data volume, network hops, or resource limits, not the code itself.
  • In Grafana, look at http_server_requests_seconds for that URI: is it p50 or only p99, and is it every request or only some? A consistent ~20 s often points to a timeout plus retry (for example 2 × 10 s), DNS, or a waiting connection pool.
  • Open a slow trace in Zipkin, Jaeger or Tempo. The span breakdown shows immediately whether the time goes to the DB, a downstream HTTP call, or the service itself.

Step-by-step investigation

  1. Trace: find the span that takes most of the 20 s.
  2. If it is the DB: run EXPLAIN (ANALYZE, BUFFERS) on the captured SQL against prod-sized data. Check pg_stat_statements for mean time and pg_stat_activity for locks (wait_event_type = 'Lock').
  3. Check the connection pool: hikaricp_connections_pending and hikaricp_connections_acquire_seconds. If threads are waiting for a connection, the pool is too small or connections are being leaked.
  4. Check for N+1 queries: enable spring.jpa.properties.hibernate.generate_statistics=true briefly and look at the query count per request.
  5. While a slow call is in flight, take thread dumps: kubectl exec <pod> -- jcmd 1 Thread.print, three times, 5 s apart. Threads stuck in SocketInputStream.read mean a slow downstream. Threads stuck in HikariPool.getConnection mean pool starvation.
  6. Check CPU throttling: rate(container_cpu_cfs_throttled_periods_total[5m]). A 500m limit with a busy JVM causes stalls.
  7. Profile on the pod: asprof -d 30 -e wall -f /tmp/wall.html 1. A wall-clock profile shows where the time goes, including time spent blocked.

Likely follow-ups:

  • No tracing in place? Log per-step timings with a request ID, or temporarily use /actuator/httpexchanges together with SQL timing logs.
  • Can you profile prod safely? Yes. JFR (jcmd 1 JFR.start duration=60s filename=/tmp/r.jfr) and async-profiler both have low overhead.
  • What if it is slow only for one tenant or city? That points to data skew. That tenant has far more rows, so its plan or index differs.
F4 CPU usage suddenly increased to 95% in production server. What steps will you take to investigate?
  1. Find the process: top, or kubectl top pod. Check whether the spike lines up with a deployment, a traffic peak or a batch job.
  2. Find the busy threads: top -H -p <pid>. Convert the thread ID to hex (printf '%x' <tid>) and match it to nid=0x... in the jstack <pid> output.
  3. Take several thread dumps. If the same stack keeps showing up, that is usually the culprit: an infinite loop, regex backtracking, heavy JSON serialization or a busy-wait.
  4. Check whether GC is the cause with jstat -gcutil <pid> 1000. Frequent full GCs burn CPU.
  5. Profile with JFR (jcmd <pid> JFR.start duration=60s filename=cpu.jfr) or async-profiler to get a flame graph.
  6. Mitigate first (scale out with HPA, roll back), then fix the code and add CPU alerts.

Symptoms & first checks

  • Confirm whether the CPU belongs to the Java process or something else: top, then kubectl top pod.
  • Check whether traffic also went up (rate(http_server_requests_seconds_count[1m])). If load is unchanged, it is a bug.
  • Check GC: high GC CPU means a memory problem, not a compute problem (see F7). Look at jvm_gc_pause_seconds and process_cpu_usage.

Step-by-step investigation

  1. Find the hot threads: top -H -p <pid> and note the TIDs with the highest CPU.
  2. Convert each TID to hex: printf '%x\n' 12345 gives 3039.
  3. Take a thread dump with jstack <pid> or jcmd <pid> Thread.print > td.txt, then grep -A 20 'nid=0x3039' td.txt. This shows the exact stack that is burning CPU.
  4. Repeat 3–4 times. If the same frames keep appearing, that is the hotspot.
  5. For a statistical view, use asprof -d 30 -e cpu -f /tmp/cpu.html <pid> (a flame graph) or JFR, analysed in JDK Mission Control under Method Profiling.
  6. In Kubernetes: kubectl exec -it <pod> -- sh, then run the same jcmd commands. If top is missing, use kubectl debug with an ephemeral container.

Likely root causes

Cause How to confirm Fix
Infinite or tight loop (e.g. while retry with no sleep) Same frame in every dump Fix the loop, add backoff
Catastrophic regex backtracking Stack sits in java.util.regex.Pattern$... Rewrite the regex, validate input length

HashMap corruption from concurrent access (legacy) Hot in HashMap.put/get ConcurrentHashMap

        .maxAttempts(5)

  • What is nid in a thread dump? The native OS thread ID in hex, which maps to the TIDs shown by top -H.
  • What if CPU is high but no app thread is hot? Check GC Thread, C2 CompilerThread (JIT warm-up just after deploy), and logging threads (synchronous logging at DEBUG level).
F5 Your application is creating too many threads and server becomes slow. How will you identify thread leak?
  1. Watch the Actuator metric jvm.threads.live and jvm.threads.states over time. Steady growth without a plateau means a leak.
  2. Run jcmd <pid> Thread.print (or jstack) and group the threads by name. A large count of pool-N-thread-M threads points to a new ExecutorService being created per request.
  3. Typical causes: Executors.newFixedThreadPool() inside a method and never shut down, new Thread() in a loop, an HTTP client created per call, @Async running on the default executor.
  4. Fix it with one shared, bounded ThreadPoolTaskExecutor bean with names that show where the threads come from. Use shutdown() in @PreDestroy.
  5. Java 21 virtual threads are an option, but Java 17 needs bounded pools.
@Bean ThreadPoolTaskExecutor reportExecutor() {
  var ex = new ThreadPoolTaskExecutor();
  ex.setCorePoolSize(8); ex.setMaxPoolSize(16); ex.setQueueCapacity(500);
  ex.setThreadNamePrefix("report-"); return ex;
}

Symptoms & first checks

  • jvm_threads_live_threads keeps rising without levelling off. This eventually leads to OutOfMemoryError: unable to create native thread, high context switching, and memory pressure (each thread reserves stack memory, about 1 MB by default).
  • Correlate the growth with traffic. A leak grows per request or per job run and never falls back.

Step-by-step investigation

  1. Count the threads: jcmd <pid> Thread.print | grep -c '^"', or ls /proc/<pid>/task | wc -l.
  2. Group them by name prefix to see which pool is leaking:
    jcmd 1 Thread.print | grep '^"' | sed -E 's/^"([^"]*[^0-9-])[-0-9]*".*/\1/' | sort | uniq -c | sort -rn | head
    Typical culprits: pool-123-thread-1 (an Executors.newXxx() created per call), OkHttp ..., kafka-producer-network-thread, HttpClient-...-SelectorManager, SimpleAsyncTaskExecutor-4567.
  3. Take two dumps 10 minutes apart and diff the counts.
  4. Look at the thread states. Many WAITING (parking) threads on LinkedBlockingQueue.take means idle pools that were never shut down. Many BLOCKED threads means contention.
  5. Search the code for Executors.new, new Thread(, HttpClient.newHttpClient(), new KafkaProducer, WebClient.create() inside methods, and custom Executor beans.

@Async falling back to SimpleAsyncTaskExecutor (a new thread per task) SimpleAsyncTaskExecutor-N with growing N Define a ThreadPoolTaskExecutor
HTTP/Kafka client instantiated per call OkHttp/kafka-producer threads multiply Singleton client beans

Fix / prevention

@Configuration
@EnableAsync
public class AsyncConfig {
    @Bean(name = "taskExecutor")
    public ThreadPoolTaskExecutor taskExecutor() {
        ThreadPoolTaskExecutor ex = new ThreadPoolTaskExecutor();
        ex.setCorePoolSize(8);
        ex.setMaxPoolSize(16);
        ex.setQueueCapacity(500);                       // bounded
        ex.setThreadNamePrefix("city-async-");          // name it so it can be found in a dump
        ex.setRejectedExecutionHandler(new ThreadPoolExecutor.CallerRunsPolicy());
        ex.setWaitForTasksToCompleteOnShutdown(true);
        ex.setAwaitTerminationSeconds(30);
        ex.initialize();
        return ex;
    }
}

Sizing rule of thumb: CPU-bound work gets about cores + 1 threads. IO-bound work gets cores × (1 + wait/compute). Always bound the queue. Expose executor_active_threads and executor_queued_tasks through Micrometer's ExecutorServiceMetrics, and alert on the live-thread trend.

Likely follow-ups:

  • Why CallerRunsPolicy? It applies backpressure: the submitting thread slows down instead of the task being dropped or memory growing without limit.
  • Does Spring Boot auto-configure an executor? Yes, applicationTaskExecutor. It backs off if you define your own Executor bean, which is a common source of surprises.
  • Would virtual threads help? On Java 21, spring.threads.virtual.enabled=true makes threads cheap. But you still need to bound concurrency to the DB and downstream services, for example with a semaphore or bulkhead.
F6 One scheduled job is processing duplicate records multiple times. How will you prevent duplicate processing?
  1. Find out why. Either several pods run the same job, the previous run is still going when the next one starts, or records are not marked as processed atomically.
  2. Use a status column and claim rows atomically: SELECT ... FOR UPDATE SKIP LOCKED, then set status='PROCESSING' in the same transaction.
  3. Make the processing idempotent with a unique constraint on a business key or an idempotency key, so a duplicate insert fails safely.
  4. For clustered deployments, use ShedLock so only one instance runs the job.
  5. Use fixedDelay instead of fixedRate so runs do not overlap.
SELECT * FROM events WHERE status='NEW' ORDER BY id LIMIT 100 FOR UPDATE SKIP LOCKED;

Symptoms & first checks

  • Duplicate notifications, double billing, or repeated Kafka events from one source row.
  • First decide which kind of duplication this is: (a) the same job running on several pods (see F20), (b) runs overlapping on one pod, (c) a record picked again because its status update did not commit, or (d) a retry after a partial failure.
  • Check the logs for the same record ID handled by different pods or threads, and check the job's timing against its interval.

Step-by-step investigation

  1. Add log fields jobRunId, podName, recordId, then grep for the duplicated IDs.
  2. Check the scheduler type. fixedRate can overlap with a slow previous run when a multi-threaded scheduler is used. fixedDelay waits for the previous run to finish.
  3. Check the transaction boundaries. Is status set to PROCESSED in the same transaction as the work, or after an external call that can fail?
  4. Check whether the selection query is WHERE status='NEW' with no row claiming, so two workers read the same rows.

Fix / prevention Claim rows atomically, so each row is picked by exactly one worker:

public interface AlertRepository extends JpaRepository<Alert, Long> {
    @Query(value = """
        SELECT * FROM alert
        WHERE status = 'NEW'
        ORDER BY created_at
        LIMIT :batch
        FOR UPDATE SKIP LOCKED
        """, nativeQuery = true)
    List<Alert> claimBatch(@Param("batch") int batch);
}

@Scheduled(fixedDelayString = "${jobs.alert.delay:30000}")
@Transactional
public void processAlerts() {
    for (Alert a : repo.claimBatch(200)) {
        notifier.send(a);              // idempotent: uses a.getId() as the idempotency key
        a.setStatus(Status.PROCESSED);
    }
}

Add a consumer-side guard as well:

CREATE TABLE processed_event (event_id VARCHAR(64) PRIMARY KEY, processed_at TIMESTAMPTZ DEFAULT now());
-- INSERT ... ON CONFLICT DO NOTHING; skip the record if 0 rows were inserted

For Kafka, enable enable.idempotence=true on the producer and keep a dedup table keyed by event ID on the consumer, because delivery is at-least-once.

Likely follow-ups:

  • Why SKIP LOCKED? Workers skip rows another transaction has already locked, so they share the work without blocking each other.
  • Can you get exactly-once? Only within one store or transaction. End to end, aim for at-least-once delivery plus idempotent processing.
  • Long batch holding locks? Commit in small chunks, or use a claim column (status='IN_PROGRESS', claimed_by, claimed_at) with a reaper that resets stale claims.
F7 Garbage collection time suddenly increased and application became slow. How will you troubleshoot?
  1. Enable GC logs: -Xlog:gc*:file=/logs/gc.log:time,uptime:filecount=5,filesize=20m. Analyse them with GCEasy or GCViewer, looking at pause times, frequency and full GCs.
  2. Run jstat -gcutil <pid> 1000. If old gen stays near 100% after each GC, there is a leak or the heap is too small.
  3. Take a heap dump (jcmd <pid> GC.heap_dump) and use MAT to find the objects that fill old gen.
  4. Use JFR's allocation profiling to find code that allocates heavily, such as large temporary collections, string concatenation in loops or loading whole result sets.
  5. Tune only after fixing the code: G1 (the default in Java 17) with -XX:MaxGCPauseMillis=200 and the right -Xmx/MaxRAMPercentage. Consider ZGC for large heaps.
  6. Check that the container memory limit is not causing throttling or OOMKills.

Symptoms & first checks

  • In Grafana, look at rate(jvm_gc_pause_seconds_sum[5m]) and jvm_gc_pause_seconds_max, alongside latency spikes. Check jvm_gc_memory_allocated_bytes_total: a rising allocation rate means more garbage is being produced.
  • Check jvm_memory_used_bytes{area="heap",id="G1 Old Gen"} after GC. If old gen does not drop, that is a leak (see F1).

Step-by-step investigation

  1. Enable and read the GC logs: -Xlog:gc*,safepoint:file=/logs/gc.log:time,uptime,level,tags:filecount=5,filesize=20m.
  2. Quick live view: jstat -gcutil <pid> 1000. Watch whether O (old %) stays high and FGC increases.
  3. Upload the GC log to GCeasy or GCViewer. Look for frequent full GCs, to-space exhausted or Evacuation Failure, Humongous Allocation, and long Pause Remark.
  4. Profile allocations: asprof -e alloc -d 30 -f alloc.html <pid>, or JFR (Allocation by class and TLAB views in JMC), to find who allocates the most.
  5. Check jcmd <pid> VM.flags for the effective heap. Is -Xmx too small for current traffic? Is it a container whose limit changed?
  6. Grep for explicit System.gc() calls, which some libraries make, and RMI DGC.

Cause How to confirm Fix
Memory leak keeps old gen full Post-GC old gen keeps rising Heap dump plus MAT, fix the reference
Heap too small for the load Old gen OK, frequent young GCs Increase MaxRAMPercentage or memory limit
High allocation rate (big DTOs, string concatenation, loading full lists) Alloc profile dominated by a few sites Stream or paginate, reuse buffers

Fix / prevention

env:
  - name: JAVA_TOOL_OPTIONS
    value: >-
      -XX:+UseG1GC -XX:MaxGCPauseMillis=200
      -XX:MaxRAMPercentage=75
      -Xlog:gc*:file=/logs/gc.log:time,uptime:filecount=5,filesize=20m

For large heaps that need low pause times, consider -XX:+UseZGC (production-ready since JDK 15; generational ZGC from JDK 21). In code, avoid findAll() into memory, use projections, stream large exports, and set bounds on caches.

Alert rule:

rate(jvm_gc_pause_seconds_sum[5m]) > 0.1   # more than 10% of wall time spent in GC

Likely follow-ups:

  • G1 or ZGC? G1 is the balanced default. ZGC keeps pauses under a millisecond on large heaps, at some cost in throughput and memory.
  • Does a bigger heap always help? No. If there is a leak, it only delays the OOM, and with a parallel collector a bigger heap can make pauses longer.
  • What is a safepoint pause? A pause in which all threads are stopped. Long time-to-safepoint can come from counted loops, and shows up with -Xlog:safepoint.
F8 Large Excel/file processing causes application crash due to memory issue. How will you optimize it?
  1. Find the cause: loading the whole file into memory (XSSFWorkbook, Files.readAllBytes, MultipartFile.getBytes()).
  2. Read in streaming mode: Apache POI event model / XSSFReader (SAX), the excel-streaming-reader library, or EasyExcel. For CSV, read line by line with BufferedReader/Files.lines.
  3. Write large Excel files with SXSSFWorkbook(100), which keeps only 100 rows in memory.
  4. Process in chunks (for example 1,000 rows) with JDBC batch inserts. Spring Batch with a chunk-oriented step gives restartability.
  5. Move it to async: upload to S3/MinIO, return 202 with a job ID, and process in a background worker.
  6. Limit the upload size with spring.servlet.multipart.max-file-size.

F10 One API works for small data but fails for huge data. What performance improvements will you do?
  1. Add pagination: Pageable, or keyset pagination for deep pages. Never return unbounded lists.
  2. Fix the queries: use projections or DTOs instead of whole entities, remove N+1 queries (JOIN FETCH, @EntityGraph, hibernate.default_batch_fetch_size), add indexes, and run EXPLAIN ANALYZE.
  3. Stream large exports with Stream<T> plus @Transactional(readOnly=true) and a fetch size, or StreamingResponseBody, so they do not build a list in memory.
  4. Move heavy work to async processing (202 plus job status, or Kafka).
  5. Compress responses: server.compression.enabled=true.
  6. Cache hot reads with Redis.
  7. Tune timeouts and pool sizes, then confirm with a load test (Gatling).

Symptoms & first checks

  • Timeouts (gateway 504), OOM, or very large response payloads when the data grows. Example: a "get all sensor readings for a city" endpoint that returns 2 million rows.

  3. Profile CPU and allocation. Often the time goes to Jackson serialising huge object graphs, or to mapping entities to DTOs.
  4. Check heap during the call. A full list held in memory means OOM risk.

F11 Two microservices are communicating and one dependent service is down. How will your service handle the failure without impacting users?
  1. Set connect and read timeouts on every outbound call so threads do not hang.
  2. Add a Resilience4j circuit breaker so the service fails fast once the dependency's error rate crosses a threshold.
  3. Add a fallback: cached data (Redis), a default response or a degraded feature. For example, show the last known sensor status.
  4. Use a bulkhead (a separate thread pool or semaphore) so one slow dependency cannot use up all request threads.
  5. For writes, go asynchronous: publish to Kafka and let the consumer process when the dependency recovers.
  6. Have Kubernetes readiness probes remove unhealthy pods, and alert on circuit breaker state changes.

Symptoms & first checks

  • Without protection, calls to the dead service hang until a timeout (or forever if no timeout is set). Tomcat threads pile up, and the calling service also stops responding. That is a cascading failure.

    • What are the circuit breaker states? Check /actuator/circuitbreakers or resilience4j_circuitbreaker_state.

  1. Confirm that timeouts are configured on the HTTP client. A missing read timeout is the most common gap.
  2. Check whether the call is synchronous on the critical path, or whether it could be asynchronous through Kafka.
  3. Decide what the user should see when the dependency fails: cached or last-known data, a default value, a partial response, or "request accepted, will be processed".
  4. Apply resilience patterns in layers, then test with chaos (scale the dependency to 0 replicas).

Symptoms & first checks

  • "Random" usually means some pods, some times, or some requests. Find out which:

F14 One API is receiving too many requests and server becomes overloaded. How will you implement rate limiting?
  1. Decide the key (per user, API key, or IP) and the limit, for example 100 requests per minute.
  2. Prefer enforcing it at the edge: Spring Cloud Gateway RequestRateLimiter with Redis (token bucket, shared across instances), or NGINX/Ingress limit_req.

  4. Return 429 Too Many Requests with a Retry-After header.

public class RateLimitFilter extends OncePerRequestFilter {
    private final Map<String, Bucket> buckets = new ConcurrentHashMap<>();  // bound with Caffeine in prod

    private Bucket newBucket() {
        return Bucket.builder()
                .addLimit(Bandwidth.builder().capacity(100).refillGreedy(100, Duration.ofMinutes(1)).build())
                .build();
    }

    @Override
    protected void doFilterInternal(HttpServletRequest req, HttpServletResponse res, FilterChain chain)
            throws ServletException, IOException {
        String key = Optional.ofNullable(req.getHeader("X-API-Key")).orElse(req.getRemoteAddr());
        ConsumptionProbe probe = buckets.computeIfAbsent(key, k -> newBucket()).tryConsumeAndReturnRemaining(1);
        if (probe.isConsumed()) {
            res.setHeader("X-RateLimit-Remaining", String.valueOf(probe.getRemainingTokens()));
            chain.doFilter(req, res);
        } else {
            res.setStatus(HttpStatus.TOO_MANY_REQUESTS.value());
            res.setHeader("Retry-After", String.valueOf(probe.getNanosToWaitForRefill() / 1_000_000_000));
        }

  5. Still make the job idempotent as a safety net.

@Scheduled(cron = "0 */5 * * * *")

Alternatively, use a Kubernetes CronJob with concurrencyPolicy: Forbid for heavy batch jobs, which also isolates their resource usage from the API pods.

Likely follow-ups:

F24 One query works fast initially but becomes slow after data grows to millions of records. What optimizations will you do?
  1. Run EXPLAIN ANALYZE and look for sequential scans, sorts that spill to disk and stale statistics. Run ANALYZE, and check autovacuum.

F25 Duplicate records are inserted during concurrent transactions. How will you avoid it?

  2. The database is the real guard. Add a unique constraint on the business key, for example (vehicle_no, event_time) or an idempotency key.

F26 A transaction partially updates data and application crashes in middle. How will you maintain consistency?
  1. Within one database, put all related writes in one @Transactional service method. The database rolls back everything if the process crashes before commit.
  2. Watch for the common pitfalls. By default only unchecked exceptions trigger rollback, so use rollbackFor = Exception.class for checked ones. Self-invocation bypasses the proxy. Do not catch and swallow exceptions inside the method.
  3. Keep remote calls and Kafka publishes out of the database transaction. Use the transactional outbox: write the event to an outbox table in the same transaction, then publish it with a relay (Debezium CDC or a poller).
  4. Across services, use a Saga with compensating actions.
  5. For batch jobs, use Spring Batch chunk commits plus restartable job metadata, so a restart resumes from the last committed chunk.
  6. Make operations idempotent so retries are safe.

Symptoms & first checks

  • An order exists without its line items, or a stock decrement happened without the order. A crash or OOMKill happened during the operation.
  • Key insight: if all writes were inside one local DB transaction, a crash cannot leave partial data, because uncommitted work is rolled back by the DB. Partial state therefore means the writes were not atomic.

Step-by-step investigation

  1. Map every write in the flow and the transaction it ran in. Use logging.level.org.springframework.transaction=DEBUG (or org.springframework.orm.jpa.JpaTransactionManager=DEBUG) to see begin and commit boundaries.
  2. Look for these patterns:
    • Methods called via this. (self-invocation, so no proxy and no transaction).
    • @Transactional on private methods.
    • REQUIRES_NEW that commits early.
    • A caught exception that is swallowed.
    • A checked exception that does not trigger rollback.
  3. Look for non-DB side effects: Kafka publish, REST call, file or S3 write, Redis update.
  4. Check batch jobs: was each chunk committed independently with no restart state?

F27 Deadlock occurs frequently in database during peak traffic. How will you analyze and fix it?
  1. Get the deadlock details. PostgreSQL writes both statements to the server log (deadlock detected). Set log_lock_waits=on. MySQL: SHOW ENGINE INNODB STATUS (LATEST DETECTED DEADLOCK), or innodb_print_all_deadlocks=ON.
  2. Find the pattern. It is usually two transactions locking the same rows in opposite order, or missing indexes that cause wide range or gap locks.
  3. Fix it by locking in a consistent order (for example sort the IDs before updating), keeping transactions short, and doing no remote calls inside them.
  4. Add indexes on the WHERE and FK columns so fewer rows get locked.
  5. Use optimistic locking (@Version) where it fits, or SELECT ... FOR UPDATE SKIP LOCKED for queue-like tables.
  6. Retry deadlock victims (CannotAcquireLockException / DeadlockLoserDataAccessException) with Spring Retry and backoff.

Symptoms & first checks

  • PostgreSQL: ERROR: deadlock detected … Process 123 waits for ShareLock on transaction 456; blocked by process 789.
  • MySQL: Deadlock found when trying to get lock; try restarting transaction.
  • Spring surfaces these as CannotAcquireLockException or PessimisticLockingFailureException.
  • Correlate with peak traffic, batch jobs running at the same time, or a new code path.

Step-by-step investigation

  1. Get both statements. In PostgreSQL, the server log shows both queries when log_lock_waits = on (logs waits longer than deadlock_timeout, default 1 s). In MySQL:
    SHOW ENGINE INNODB STATUS\G         -- section: LATEST DETECTED DEADLOCK
SET GLOBAL innodb_print_all_deadlocks = ON;  -- log every one, not just the latest
    This shows each transaction's held locks, waited-for locks, index, and lock mode (including gap and next-key locks).
  2. See live blocking:
    SELECT a.pid, pg_blocking_pids(a.pid) AS blocked_by, a.query
FROM pg_stat_activity a WHERE cardinality(pg_blocking_pids(a.pid)) > 0;
  3. Map statements to code using the trace ID or application name. Usually two code paths update the same rows in opposite order, for example a transfer A→B and B→A, or a batch updating ascending while the API updates a parent then its child.
  4. Check foreign keys without indexes. In PostgreSQL, FK checks take row locks on the parent. In MySQL, a missing index makes InnoDB lock far more rows (range or table scans).

F28 Pagination API becomes slow for huge tables. How will you optimize database performance?
  1. Cause: OFFSET 500000 LIMIT 20 still scans and discards 500k rows, and Spring Data Page also runs a COUNT(*) on every request.
  2. Use keyset (seek) pagination: WHERE (created_at, id) < (:lastTs, :lastId) ORDER BY created_at DESC, id DESC LIMIT 20, backed by a matching composite index.
  3. Return Slice instead of Page to avoid the count query, or cache or estimate the total (PostgreSQL reltuples).
  4. Select only the needed columns through a DTO projection, and do not fetch collections with paging (Hibernate HHH90003004 warns about in-memory pagination).

F41 Kafka consumers are processing same message multiple times. How will you make processing idempotent?

Kafka gives at-least-once delivery by default, so duplicates will happen. Make the consumer idempotent:

  1. Give every event a unique eventId (UUID) in a header or the payload.
  2. Keep a processed_events(event_id PK) table and insert into it in the same DB transaction as the business update. A duplicate key means skip.
  3. Or use natural idempotency: an upsert (INSERT ... ON CONFLICT DO UPDATE), a status transition guard (WHERE status='PENDING'), or a version check.
  4. Reduce how often duplicates happen: commit offsets after processing (AckMode.RECORD/MANUAL), and tune max.poll.interval.ms so rebalances don't replay batches.
  5. For Kafka-to-Kafka flows, use transactions (transactional.id, isolation.level=read_committed).
@Transactional
public void handle(Event e) {
    if (processedRepo.insertIfAbsent(e.id()) == 0) return; // ON CONFLICT DO NOTHING
    service.apply(e);
}

Symptoms & first checks

  • Duplicate rows (two challans for one violation, an SMS sent twice), or counters/aggregates higher than expected.
  • Look at the consumer logs around the time of the duplicates for Revoking previously assigned partitions, CommitFailedException, or max.poll.interval.ms exceeded.
  • Remember that Kafka gives at-least-once delivery by default. Duplicates are normal; the consumer has to tolerate them.

  1.     private final ChallanRepository challans;

        this.jdbc = jdbc; this.challans = challans;

    @Transactional
    public void process(ViolationEvent e) {
        int inserted = jdbc.update("""
            INSERT INTO processed_event(consumer_group, event_id) VALUES (?, ?)
            ON CONFLICT DO NOTHING""", "billing", e.eventId());
        if (inserted == 0) return;                // duplicate -> skip silently
        challans.save(Challan.from(e));           // same TX as dedupe row
    }
}

  • Redis or DB for dedupe? Use the DB when the side effect is in the same DB, because that gives you atomicity. Redis is faster but not atomic with the DB write.

F44 Kafka broker goes down during high traffic. How will your system handle it?

The goal is that this is a non-event if we designed for it:

  1. Topics use replication.factor=3 and min.insync.replicas=2. When a broker dies, the controller elects new partition leaders from the ISR.
  2. Producers use acks=all and enable.idempotence=true (the default in Kafka 3.x). They retry until delivery.timeout.ms without creating duplicates or reordering.
  3. Clients get a bootstrap list of several brokers and refresh metadata automatically.
  4. If the producer still fails, write to an outbox table or local buffer and alert. Don't drop data.
  5. Consumers rebalance, reconnect to the new leaders, and resume from committed offsets.
  6. Monitor UnderReplicatedPartitions and OfflinePartitionsCount, and keep unclean.leader.election.enable=false.

Symptoms & first checks

  • Producers log NotLeaderOrFollowerException or NETWORK_EXCEPTION and retry. Latency spikes briefly, and the UnderReplicatedPartitions and OfflinePartitionsCount metrics rise.

  3. Check the broker logs (server.log) for OOM, disk full (log.dirs), long GC, or the ZooKeeper session / KRaft fencing. Use kubectl describe pod kafka-1 for eviction or node failure.
  4. On the client side, check the producer metrics record-error-rate, record-retry-rate, buffer-available-bytes, and bufferpool-wait-time. If the buffer is full, send() blocks up to max.block.ms.
  5. Consumers: if the broker hosting the group coordinator dies, the group fails over to a new coordinator and rebalances. Watch for a lag bump.

F45 Events are processed out of order causing wrong business logic. How will you maintain ordering?
  1. Kafka only guarantees order within a partition, so use the entity ID (e.g. incidentId) as the message key. All events for that entity go to the same partition.
  2. On the producer, enable.idempotence=true keeps order during retries (allowed with max.in.flight.requests.per.connection ≤ 5).
  3. On the consumer, don't hand records to an unordered thread pool. Use container concurrency (one thread per partition) or key-ordered parallelism (Confluent Parallel Consumer).
  4. Be careful with retry topics and DLTs: non-blocking retries break ordering. For strictly ordered flows, use blocking retries.
  5. Defend against stale events anyway: store a version or event timestamp and ignore anything older than the current state.

F47 Retry mechanism causes duplicate event processing. How will you avoid duplicates?
  1. Producer side: enable.idempotence=true and acks=all. Broker-side sequence numbers remove duplicates caused by network retries.
  2. Consumer side: an idempotent handler. Store eventId in a processed table in the same transaction as the update, or use upserts and state guards.
  3. Make side effects idempotent too. Pass an idempotency key to the payment, SMS, or notification provider.
  4. Retry only the failing step, not the whole flow. Don't re-publish events from a retry loop.
  5. For consume-transform-produce, use Kafka transactions (@Transactional with a KafkaTransactionManager, consumers on read_committed) for exactly-once within Kafka.
  6. Make sure the retry happens before the offset commit and stays under max.poll.interval.ms, or a rebalance will replay the batch.

Symptoms & first checks

  • Two notifications, a double ledger entry, or the same event visible in both orders and orders-retry-0.

@Component
public class NotificationListener {
    private final IdempotencyStore store;   // DB table or Redis with status
    private final SmsGateway sms;

    public NotificationListener(IdempotencyStore store, SmsGateway sms) {
        this.store = store; this.sms = sms;
    }

    @RetryableTopic(attempts = "4",
        backoff = @Backoff(delay = 2000, multiplier = 2.0),
        exclude = InvalidEventException.class,
        topicSuffixingStrategy = TopicSuffixingStrategy.SUFFIX_WITH_INDEX_VALUE)
    @KafkaListener(topics = "notification-requests", groupId = "notifier")
    public void handle(NotificationRequest req) {
        if (store.isCompleted(req.requestId())) return;           // already done
        sms.send(req.phone(), req.text(), req.requestId());        // provider dedupes on this key
        store.markCompleted(req.requestId());
    }

    @DltHandler
    public void dlt(NotificationRequest req,
                    @Header(name = KafkaHeaders.DLT_EXCEPTION_MESSAGE, required = false) String err) {
        store.markFailed(req.requestId(), err);
    }
}

There is a gap between send and markCompleted, and the provider-side idempotency key closes it. The consumed offset and the produced record then commit atomically. EOS does not cover DB writes or HTTP calls, so those still need dedupe tables (F41).

  • Retry storms? Use exponential backoff with jitter, a max-attempts limit, and a circuit breaker on the downstream.

@Component
public class OutboxRelay {
    private final JdbcTemplate jdbc;
    private final KafkaTemplate<String, String> kafka;

    public OutboxRelay(JdbcTemplate jdbc, KafkaTemplate<String, String> kafka) {
        this.jdbc = jdbc; this.kafka = kafka;
    }

    @Scheduled(fixedDelay = 500)
    @Transactional
    public void relay() throws Exception {
        List<Map<String, Object>> rows = jdbc.queryForList("""
            SELECT id, aggregate_id, payload FROM outbox
            WHERE published_at IS NULL ORDER BY created_at
            LIMIT 100 FOR UPDATE SKIP LOCKED""");
        for (Map<String, Object> r : rows) {
            kafka.send("payment-events", (String) r.get("aggregate_id"), (String) r.get("payload"))
                 .get(10, TimeUnit.SECONDS);                       // wait for broker ack
            jdbc.update("UPDATE outbox SET published_at = now() WHERE id = ?", r.get("id"));
        }
    }
}

Add a reconciliation job as the safety net: find payments that are SUCCESS with no notification older than N minutes, and republish. Avoid 2PC/XA, because Kafka doesn't support it and it couples availability. For multi-step flows with compensation (for example, refund if the challan update fails), use a saga.

F54 Network partition occurs between services in distributed system. How will system behave?

By CAP, during a partition we choose consistency or availability for each use case:

  1. Callers fail fast. Timeouts and circuit breakers open, and fallbacks serve cached or degraded data (availability).
  2. For strongly consistent operations (payments, unique allocation), reject or queue the request instead of guessing.
  3. Async flows keep working: producers buffer or write to the outbox, Kafka holds events, and consumers catch up after the partition heals.
  4. Clustered stores: Kafka keeps acks=all writes only on the side with ISR quorum. min.insync.replicas stops writes on the minority side. Redis Sentinel/Cluster or etcd use quorum to avoid split-brain.
  5. After healing: idempotent replay, reconciliation jobs, and conflict resolution (version or last-write-wins where acceptable).
  6. Test it with chaos tools (Chaos Mesh, Toxiproxy).

Symptoms & first checks

  • Timeouts or connection resets between a subset of pods, AZs, or a DC and the cloud. Some instances can reach the DB or Kafka and others cannot. Circuit breakers open, and you may see split-brain (two leaders).
  • CAP: during a partition, each component either refuses requests (stays Consistent) or serves possibly stale or divergent data (stays Available). The answer is to design that choice per component, not to leave it to chance.

Step-by-step investigation

  1. Map the partition boundaries. From a pod: kubectl exec -it pod -- curl -m 2 http://svc:8080/actuator/health, nc -zv kafka-0 9092, and nslookup svc. Check NetworkPolicies, Istio/mesh config, and cloud security groups.
  2. Kafka: run kafka-topics.sh --describe --under-replicated-partitions, and check whether the controller quorum (KRaft) still has a majority. Producers on the minority side get NotEnoughReplicas/timeouts with acks=all, min.insync.replicas=2.
  3. PostgreSQL HA (Patroni): run patronictl list. A primary that loses the DCS (etcd) leader key demotes itself, which prevents two primaries.
  4. Redis Sentinel/Cluster: is a minority-side master still accepting writes? Check with INFO replication.
  5. Look at the Resilience4j metrics: circuit breaker state, retry counts, and bulkhead saturation.

1. Redisson RLock, for cross-service, short critical sections:

@Service
public class SignalPlanService {
    private final RedissonClient redisson;
    private final SignalPlanRepository repo;

    public SignalPlanService(RedissonClient redisson, SignalPlanRepository repo) {
        this.redisson = redisson; this.repo = repo;
    }

    public void updatePlan(long junctionId, PlanChange change) throws InterruptedException {
        RLock lock = redisson.getLock("lock:junction:" + junctionId);
        // wait max 2s; leaseTime -1 => watchdog auto-renews while this JVM holds it
        if (!lock.tryLock(2, -1, TimeUnit.SECONDS)) {
            throw new IllegalStateException("Junction " + junctionId + " is being updated");
        }
        try {
            long fence = redisson.getAtomicLong("fence:junction:" + junctionId).incrementAndGet();
            repo.applyWithFence(junctionId, change, fence);
        } finally {
            if (lock.isHeldByCurrentThread()) lock.unlock();
        }
    }
}

F59 A service continuously retries failed requests and creates cascading failure. How will you stop it?

This is a retry storm. Retries multiply load on a service that's already struggling.

  1. Immediate fix: open the circuit or disable retries with a config or feature flag, and scale or rate limit the victim service.
  2. Limit retries to 2–3 with exponential backoff and jitter, and only for idempotent requests on transient errors (503, timeouts). Never retry 4xx.
  3. Retry at one layer only, not in the gateway, client, and Kafka all at once (3×3×3 = 27x).
  4. Put a circuit breaker in front of retries (Resilience4j order: Retry wraps CircuitBreaker), so an open circuit stops calls.
  5. Respect Retry-After and set a timeout budget per request.

F68 A batch job failed in middle after processing lakhs of records. How will you restart safely without duplicates?
  1. Use Spring Batch's restartability. JobRepository stores the ExecutionContext and commit count per chunk, so restarting the same JobInstance (same identifying parameters) resumes from the last committed chunk.
  2. Use chunk-oriented processing (e.g. 500 per chunk). Each chunk's writes and checkpoint commit in one transaction.
  3. Use readers that save their position (JdbcPagingItemReader with a sort key, saveState=true), or a processed flag or status column.
  4. Make writers idempotent (upsert or ON CONFLICT), so a partially written chunk is safe to redo.
  5. Use faultTolerant().skip(...).skipLimit(...) and retry for bad records, and log skipped items.
  6. Fix the root cause, restart with JobOperator.restart(executionId), then reconcile counts.

Symptoms & first checks

  • The nightly challanSettlementJob failed at about 6.2 lakh of 10 lakh records (DB failover, pod OOMKilled, or a bad record).
  • Check BATCH_JOB_EXECUTION / BATCH_STEP_EXECUTION: status, EXIT_MESSAGE, READ_COUNT, WRITE_COUNT, COMMIT_COUNT, ROLLBACK_COUNT. If the pod was killed, the status may still be STARTED. Spring Batch then refuses to restart (JobExecutionAlreadyRunningException).

Step-by-step investigation / action plan

  1. Find the failure point:
    SELECT step_name, status, read_count, write_count, commit_count, exit_message
FROM batch_step_execution WHERE job_execution_id = :id;
SELECT short_context FROM batch_step_execution_context WHERE step_execution_id = :sid;
    The step ExecutionContext holds the reader checkpoint (e.g. reader.start.after / read.count).
  2. Fix the root cause first: a bad data row (add a skip policy), a DB outage, or memory.
  3. If the execution is stuck in STARTED (the process died), mark it failed. Only do this after confirming no instance is running:
    UPDATE batch_step_execution SET status='FAILED', exit_code='FAILED', end_time=now()
 WHERE job_execution_id=:id AND status='STARTED';
UPDATE batch_job_execution SET status='FAILED', exit_code='FAILED', end_time=now()
 WHERE job_execution_id=:id;
  4. Restart the same JobInstance: either use the same identifying JobParameters (e.g. runDate=2026-10-04) or call jobOperator.restart(executionId). The JobRepository resumes the failed step from the last committed chunk. Completed steps are skipped.
  5. Verify with counts and a duplicate check: SELECT challan_id, count(*) FROM settlement GROUP BY 1 HAVING count(*) > 1;.

Why there are no duplicates: in a chunk-oriented step, reading, processing and writing N items plus updating the ExecutionContext all commit in one transaction. A chunk that was in flight when the job crashed rolls back completely. Chunks that committed are recorded in the checkpoint, so they are never re-read. Side effects outside the transaction (Kafka sends, REST calls, files) can still repeat. That is why the writer must also be idempotent.

@Bean
JdbcPagingItemReader<Challan> reader(DataSource ds) {
    return new JdbcPagingItemReaderBuilder<Challan>()
            .name("challanReader")                 // key prefix in ExecutionContext
            .dataSource(ds).pageSize(1000)
            .selectClause("SELECT id, amount, paid_at")
            .fromClause("FROM challan")
            .whereClause("WHERE paid_at::date = :runDate")
            .parameterValues(Map.of("runDate", LocalDate.parse("2026-10-04")))
            .sortKeys(Map.of("id", Order.ASCENDING))  // unique key -> exact resume
            .rowMapper(new DataClassRowMapper<>(Challan.class))
            .build();
}

@Bean
JdbcBatchItemWriter<Settlement> writer(DataSource ds) {
    return new JdbcBatchItemWriterBuilder<Settlement>()
            .dataSource(ds).beanMapped()
            .sql("""
                 INSERT INTO settlement (challan_id, amount, settled_on)
                 VALUES (:challanId, :amount, :settledOn)
                 ON CONFLICT (challan_id) DO UPDATE
                   SET amount = EXCLUDED.amount, settled_on = EXCLUDED.settled_on
                 """)
            .build();
}

F69 Server restarted automatically at midnight. How will you investigate root cause?
  1. Find out what restarted: the pod, the container, or the node. kubectl describe pod → Last State: Terminated, Reason: OOMKilled / Error, Exit Code (137 = SIGKILL/OOM, 143 = SIGTERM).
  2. kubectl logs <pod> --previous for the last lines before the crash, and kubectl get events --sort-by=.lastTimestamp.
  3. Check whether it's scheduled: cron jobs, a midnight batch or report causing a memory spike, log rotation, backups, a CronJob doing rollout restart, or cluster autoscaler/node upgrade windows.
  4. Liveness probe failures during heavy midnight load can make kubelet kill the container.
  5. VM or bare metal: journalctl -b -1, last reboot, dmesg | grep -i oom, and cloud maintenance events.
  6. Correlate metrics (memory, CPU, GC) around midnight, and enable -XX:+HeapDumpOnOutOfMemoryError.

Symptoms & first checks

  • At 00:00–00:05 the app went down and came back by itself. Users of the night-shift control room saw errors.
  • First decide what restarted: the whole VM/node, the JVM process (systemd service), or the K8s pod/container? Each leaves different evidence. Midnight strongly suggests something scheduled.

Step-by-step investigation / action plan

  1. VM/OS-level reboot:
    last -x reboot shutdown | head        # reboot timestamps
uptime -s
journalctl --list-boots
journalctl -b -1 -e                   # tail of the PREVIOUS boot: who/what triggered shutdown
journalctl -k -b -1 | grep -iE "oom|killed process|panic|watchdog"
    A clean systemd: Stopping... sequence means an orderly reboot (a command or a patch). An abrupt end with no shutdown logs means a crash, power loss, a hypervisor event or a kernel panic.
  2. Scheduled jobs: crontab -l, sudo crontab -l -u root, ls /etc/cron.d /etc/cron.daily, systemctl list-timers --all. Look in /var/log/unattended-upgrades/ or /var/log/dnf.rpm.log for auto-patching with Automatic-Reboot, and at needrestart.
  3. Process-level restart (VM still up): systemctl status app.service (restart count), journalctl -u app.service --since "23:50" --until "00:15". Check dmesg -T | grep -i oom for the OOM killer (exit 137), and whether Restart=always brought it back.
  4. Kubernetes: kubectl get pods -o wide (RESTARTS), kubectl describe pod <p> → Last State: Terminated, Reason: OOMKilled / Error, Exit Code. Then kubectl logs <p> --previous, kubectl get events --sort-by=.lastTimestamp. Check CronJobs: kubectl get cronjob -A (e.g. a kubectl rollout restart), node maintenance windows (EKS/GKE auto-upgrade), cluster-autoscaler or spot interruption.
  5. Correlate in Grafana for 23:30–00:10: memory, CPU, GC, disk, the liveness probe. A midnight batch, report or log rotation can spike load so the liveness probe fails and the kubelet restarts the container.
  6. Cloud console: AWS EC2 scheduled events, the ASG activity history (instance refresh, health-check replacement), CloudTrail for RebootInstances/StopInstances.

Fix / prevention

livenessProbe:
  httpGet: { path: /actuator/health/liveness, port: 8080 }
  periodSeconds: 10
  timeoutSeconds: 3
  failureThreshold: 6
readinessProbe:
  httpGet: { path: /actuator/health/readiness, port: 8080 }

Liveness must not depend on the DB or downstream services. Run batches as separate K8s Jobs with their own limits. Add a PodDisruptionBudget, alert on restarts (increase(kube_pod_container_status_restarts_total[15m]) > 0), and write an RCA with a change-calendar entry.

Likely follow-ups:

  • Exit code 137 vs 143? 137 = SIGKILL (OOM killer, or a kill after the grace period). 143 = SIGTERM (a graceful stop requested).
  • dmesg is empty after a reboot? The kernel ring buffer resets on boot. Use journalctl -k -b -1 (needs a persistent journal, Storage=persistent).
  • How do you make restarts harmless? At least 2 replicas, graceful shutdown (server.shutdown=graceful), a PDB, and idempotent consumers.
F70 Business team says reports show wrong data in production. How will you validate and fix issue?
  1. Get specifics: which report, filters, expected vs actual values, and since when. Get a sample record.
  2. Recompute the number directly from the source tables with SQL and compare it to the report output at each layer: source DB → ETL/view → API → UI.
  3. Usual causes: time zone or date boundaries (UTC vs IST), duplicate rows from joins, NULL handling, soft-deleted records counted, replica lag, stale cache or materialized view, or a failed or partial ETL run.
  4. Check recent changes: deploys, query changes, or upstream data issues.
  5. Fix the logic, add a test with known data, then backfill or recompute the affected period (REFRESH MATERIALIZED VIEW, rerun the job idempotently).
  6. Tell the business which reports were affected and for what dates, and add data quality checks (row counts, totals reconciliation).

Symptoms & first checks

  • An example complaint: "Yesterday's violation count shows 12,430 on the dashboard, but the field team counted about 13,100." Or revenue doesn't match the payment gateway settlement.
  • Get specifics first: which report, filters, date range and timezone, expected vs actual figures, the source of truth they compare against, and when it started. Ask whether all reports are wrong or one, and all wards/tenants or one.

Step-by-step investigation / action plan

  1. Reproduce the number by running the report's exact query (from the logs, the repository code or the BI tool) against prod or a read replica. Is the report displaying wrongly, or is the data itself wrong?
  2. Reconcile against the source layer by layer: raw events (Kafka topic / source table) → staging → aggregate table/materialized view → API → UI. Find the layer where the count first diverges.
    SELECT (created_at AT TIME ZONE 'Asia/Kolkata')::date AS d, count(*), count(DISTINCT violation_id)
FROM violation WHERE created_at >= '2026-10-03' GROUP BY 1 ORDER BY 1;
    If count ≠ count(DISTINCT), you have duplicates.
  3. Check freshness: when did the ETL/Spring Batch job last succeed (batch_job_execution)? When was the materialized view last refreshed? Is there a Redis cache TTL, read replica lag (now() - pg_last_xact_replay_timestamp()), or Kafka consumer lag?
  4. Check recent changes: deployments, query or mapping changes, schema migrations (Flyway history), new master data (ward boundaries, fine slabs).
  5. Use the sample-record approach: pick 5 records the business says are missing or wrong, then trace each one end to end by ID.
  6. Fix, backfill and communicate: correct the logic, recompute the affected period (idempotent re-run), state which reports or dates were affected, and get the business to sign off on the corrected numbers.
