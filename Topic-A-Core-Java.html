A1 What is the use of Docker?
  • Docker packages an app with its runtime, libraries and config into an image. You run that image as a lightweight, isolated container. The goal is "build once, run anywhere".
  • It removes "works on my machine" problems because dev, QA and prod all run the same image.
  • Containers share the host OS kernel, so they start in seconds and use far fewer resources than VMs.
  • In our microservices setup, each Spring Boot service has its own Dockerfile. We run local dependencies (Postgres, Kafka, Redis) with Docker Compose, and in production Kubernetes orchestrates the containers.

Docker packages an application together with everything it needs to run (JRE, OS libraries, config, the app itself) into an image. An image is a standard, unchangeable, layered artifact. A container is a running instance of that image. Docker fixes the "works on my machine" problem: the same image runs the same way on a laptop, in CI, on a VM, or in Kubernetes.

How it works under the hood

  • Containers are not VMs. They share the host kernel and are isolated using Linux kernel features:
    • Namespaces isolate what a process can see: pid, net, mnt, uts, ipc, user.
    • cgroups limit what a process can use: CPU, memory, I/O.
    • A union filesystem (overlay2) stacks read-only image layers and adds a thin writable layer per container.
  • Each Dockerfile instruction (FROM, COPY, RUN) creates a cached layer. Put rarely-changing layers (dependencies) before often-changing ones (your jar) so rebuilds are fast.
  • On Windows and macOS, Docker Desktop runs a lightweight Linux VM (WSL2 / HyperKit) because containers need a Linux kernel.

Typical uses in a Spring Boot / microservices project

  1. Package each microservice (traffic-service, incident-service, etc.) as its own image.
  2. Local development with docker compose: Postgres, Kafka, Redis and Keycloak start with one command.
  3. CI/CD: build the image once, then promote the same image through dev → QA → prod. Only env vars and config change between environments.
  4. Orchestration: Kubernetes/OpenShift schedules containers, scales them, and restarts them when they fail.
  5. Integration tests with Testcontainers, which start a real Postgres/Kafka in Docker for each test run.

Gotchas

  • JVM memory in containers. Older JVMs (before 8u191 / 10) read the host's RAM and ignored cgroup limits, so containers got OOM-killed. Modern JVMs are container-aware (-XX:+UseContainerSupport, on by default). Size the heap with -XX:MaxRAMPercentage instead of a hard-coded -Xmx.
  • Containers are ephemeral. Anything written inside the container is lost when it is removed. Use volumes for persistent data.
  • ENTRYPOINT ["java", ...] (exec form) makes Java PID 1, so it receives SIGTERM and Spring Boot shuts down gracefully. Shell form (ENTRYPOINT java -jar) wraps it in sh, which may not forward the signal.
  • Don't bake secrets into images. Inject them through env vars or a secrets manager.
  • Spring Boot can build images without a Dockerfile: mvn spring-boot:build-image (Cloud Native Buildpacks). It also supports layered jars, so dependencies sit in a separate cached layer.

Likely follow-ups:

  • Image vs container? An image is the read-only template (like a class). A container is a running instance with a writable layer (like an object).
  • CMD vs ENTRYPOINT? ENTRYPOINT is the fixed executable. CMD supplies default arguments, which docker run arguments override.
  • How do containers talk to each other? Over a user-defined Docker network, using service names as DNS hostnames (e.g. db:5432 in compose).
  • Docker vs Kubernetes? Docker builds and runs containers. Kubernetes orchestrates many containers across nodes: scheduling, scaling, self-healing, service discovery.

The overall reason was to bring functional-style programming to Java and make code more concise and easier to parallelise on multi-core machines.

Java 8 (March 2014, LTS) was the biggest language change since generics in Java 5. The main motive was multi-core hardware: Java needed a concise way to express behaviour as data (functional style) so that bulk operations on collections could be parallelised easily. Other languages (Scala, C#, JavaScript) already had lambdas, and Java code was verbose by comparison (anonymous inner classes everywhere).

import java.time.*;
import java.util.*;
import java.util.stream.*;

record Incident(String zone, int severity, LocalDateTime at) {}

public class Java8Demo {
    public static void main(String[] args) {
        List<Incident> incidents = List.of(
            new Incident("North", 3, LocalDateTime.now().minusHours(2)),
            new Incident("South", 5, LocalDateTime.now().minusMinutes(10)),
            new Incident("North", 4, LocalDateTime.now()));

        // Before Java 8: loops + mutable maps. With streams:
        Map<String, Long> countByZone = incidents.stream()
            .filter(i -> i.severity() >= 3)                    // Predicate lambda
            .collect(Collectors.groupingBy(Incident::zone,     // method reference
                                           Collectors.counting()));
        System.out.println(countByZone); // e.g. {South=1, North=2}

        Optional<Incident> worst = incidents.stream()
            .max(Comparator.comparingInt(Incident::severity)); // static interface method
        worst.map(Incident::zone).ifPresent(System.out::println); // South
    }
}

Gotchas

  • Streams are lazy: nothing runs until a terminal operation. A stream can be consumed only once.
  • parallelStream() uses the common ForkJoinPool. Blocking I/O inside it starves the whole JVM's pool. It is rarely a win for small collections.
  • A lambda can capture only effectively final local variables.
  • Don't use Optional for fields, method parameters, or collections. It was designed for return types.

Likely follow-ups:

  • Intermediate vs terminal operations? Intermediate ops (map, filter, sorted) are lazy and return a Stream. Terminal ops (collect, forEach, reduce, count) start the pipeline.
  • map vs flatMap? map is 1→1. flatMap is 1→many and flattens Stream<Stream<T>> into Stream<T>.
  • Lambda vs anonymous class? A lambda has no own this (it uses the enclosing instance), doesn't create a new scope for variable shadowing, and uses invokedynamic instead of a separate class file.
  • findFirst vs findAny? findAny may return any element and is faster in parallel streams. findFirst respects encounter order.
A3 What are the important features introduced in Java 18, and how are they used?

Java 18 (March 2022) is a non-LTS release. In production we use the LTS versions, 17 or 21 (21 added virtual threads, record patterns and pattern matching for switch).

  • JEP 400, UTF-8 by default: Charset.defaultCharset() is now UTF-8 on every OS, so FileReader and similar no longer behave differently on Windows.
  • JEP 408, Simple Web Server: run jwebserver -p 8000 to serve static files for quick testing (also available via the SimpleFileServer API).
  • JEP 413, @snippet in Javadoc: code examples in Javadoc that can be validated.
  • JEP 418, internet-address resolution SPI: plug in a custom DNS resolver in place of the built-in one used by InetAddress.
  • JEP 421, finalization deprecated for removal: use try-with-resources or Cleaner instead of finalize().
  • Others: JEP 416 (core reflection reimplemented on method handles), Vector API (3rd incubator), Foreign Function and Memory API (2nd incubator), pattern matching for switch (2nd preview).

1. JEP 400 – UTF-8 by default

Before 18, the default charset (Charset.defaultCharset(), used by FileReader, FileWriter, new String(bytes), InputStreamReader without a charset) depended on the OS locale. On Windows it was often windows-1252. A file written on Windows could therefore be garbled when read on Linux. From 18, the default is UTF-8 everywhere.

import java.io.*;
import java.nio.charset.Charset;

public class CharsetDemo {
    public static void main(String[] args) throws IOException {
        System.out.println(Charset.defaultCharset());            // UTF-8 on Java 18+
        System.out.println(System.getProperty("native.encoding")); // OS encoding, e.g. Cp1252
        try (var w = new FileWriter("out.txt")) {                 // now UTF-8 by default
            w.write("Bengaluru – ಬೆಂಗಳೂರು");
        }
    }
}
  • To restore the old behaviour, use -Dfile.encoding=COMPAT.
  • Best practice remains to pass the charset explicitly, e.g. Files.readString(path, StandardCharsets.UTF_8).
  • Console output (System.out) still uses the console's encoding. That is separate from the default charset.

2. JEP 408 – Simple Web Server

A minimal, static-file-only HTTP/1.1 server for prototyping, testing, and sharing files. It is not for production: no HTTPS, GET/HEAD only.

4. JEP 418 – Internet-Address Resolution SPI

InetAddress used to be hard-wired to the OS resolver. Java 18 adds a service-provider interface (java.net.spi.InetAddressResolverProvider) so you can plug in your own resolver. Uses: custom DNS (DNS-over-HTTPS), Project Loom (non-blocking resolution), and tests that map hostnames to fixed IPs without editing /etc/hosts. Providers are registered via ServiceLoader (META-INF/services/java.net.spi.InetAddressResolverProvider).

5. JEP 421 – Deprecate finalization for removal

Object.finalize() is unpredictable (it may never run, or run late), slows GC, can resurrect objects, and causes security issues. It is now @Deprecated(forRemoval = true). You can run with --finalization=disabled to test whether your app depends on it. Replacements: try-with-resources (AutoCloseable) and java.lang.ref.Cleaner.

import java.lang.ref.Cleaner;

public class NativeResource implements AutoCloseable {
    private static final Cleaner CLEANER = Cleaner.create();
    private final Cleaner.Cleanable cleanable;

    public NativeResource() {
        // the state/action must NOT reference 'this' or it will never become unreachable
        cleanable = CLEANER.register(this, () -> System.out.println("released"));
    }
    @Override public void close() { cleanable.clean(); } // deterministic path
}

6. Others

  • JEP 416: reflection now uses method handles internally. This is mostly invisible to you, except for a slight change in stack traces and performance.
  • JEP 420 (preview): switch patterns such as case Circle c -> ... and guards (when is the final syntax from 21).
  • JEP 417 / 419: incubators for SIMD vector math and for calling native code without JNI. FFM became final in Java 22.

Likely follow-ups:

  • Why would you not use Java 18 in production? It's non-LTS, with only six months of updates. Use 17 or 21 LTS.
  • What major features are in Java 21 LTS? Virtual threads (JEP 444), record patterns, pattern-matching switch (final), sequenced collections, and generational ZGC.
  • What breaks with JEP 400? Code that relied implicitly on a non-UTF-8 platform charset, e.g. reading legacy windows-1252 files without specifying the charset.
  • Can jwebserver serve a REST API? No. It serves static files only, via GET/HEAD. You'd use HttpServer handlers or Spring Boot for that.
A4 Can we override the main method in Java? Explain why or why not.
  • No. main is static, and static methods belong to the class, so they can't be overridden. A subclass can only declare its own static main, which hides the parent's version.
  • We can overload main (e.g. main(int x)), but the JVM only calls public static void main(String[] args).
  • (Java 21+ preview features allow instance main methods, but that is a different topic.)

No. main is static, and static methods belong to the class, not to an instance. Overriding is runtime dispatch based on the object's type, and static methods have no object to dispatch on. They are bound at compile time to the reference type.

What you can do:

Action Possible? Note
Override main No Static. A subclass declaring the same static main hides it (method hiding).
Overload main Yes e.g. main(int x). The JVM only calls public static void main(String[]).
Hide main in a subclass Yes java Child runs Child's main. java Parent runs Parent's.
Make main final Yes Then a subclass can't even hide it.
Inherit main Yes If Child has no main, java Child runs Parent's inherited static main. 
class Parent {
    public static void main(String[] args) { System.out.println("Parent main"); }
}
class Child extends Parent {
    // Not an override: this HIDES Parent.main. @Override here would be a compile error.
    public static void main(String[] args) { System.out.println("Child main"); }

    public static void main(int x) { System.out.println("overload " + x); } // overload, OK
}
  • If Child declares void main(String[] a) (non-static) while Parent has static main → compile error: "overriding method is static / instance method cannot override static method".
  • Valid main variants: final public static void main(String... args), static public void main(String[] a), and synchronized/strictfp modifiers.
  • Newer Java: JEP 445/463/477/495 (previews in Java 21–24), finalized in Java 25 (JEP 512), allow instance void main() methods in simple programs. Even then, the launcher picks the method; it is not polymorphic overriding.

Likely follow-ups:

  • Can main be private? It compiles, but the launcher fails with "Main method not found... please define as public static void main".
  • Why is main static? So the JVM can call it without creating an object (it doesn't know which constructor to call).
  • What if main throws an exception? The main thread dies, the default uncaught-exception handler prints the stack trace, and the JVM exits with a non-zero status (if no non-daemon threads remain).
A5 Explain the main OOP concepts in Java. G2
  • Encapsulation: private fields with public getters and setters; the object controls its own state.
  • Abstraction: expose what an object does and hide how, using abstract classes or interfaces.
  • Inheritance: reuse and extend behaviour with extends, giving an IS-A relationship.
  • Polymorphism: one interface, many forms. Overloading is resolved at compile time, overriding at runtime.
  • Supporting ideas: association, aggregation and composition (HAS-A relationships).

Java is built around classes (blueprints) and objects (instances with state + behaviour). The four pillars:

Gotchas

  • Java has no multiple inheritance of state (classes), only of type and behaviour (interfaces with default methods).
  • Encapsulation is not "getters and setters for every field". A setter with no validation is barely better than a public field.
  • Inheritance breaks encapsulation: a subclass depends on the superclass's implementation details (the fragile base class problem).

Likely follow-ups:

  • Abstraction vs encapsulation? Abstraction is design-level (which operations to expose). Encapsulation is implementation-level (hiding data and enforcing invariants).
  • Why no multiple class inheritance? To avoid the diamond problem with state and constructor ambiguity.
  • Is Java 100% object-oriented? No. It has primitives (int, boolean...) and static members.
A6 How do you achieve abstraction in Java? Write a class structure/program to demonstrate it. G2
  • Use abstract classes for partial abstraction (they can have state, constructors and concrete methods).
  • Use interfaces for full contracts (they can also have default and static methods). A class can implement many interfaces.
interface Notifier { void send(String msg); }

abstract class BaseNotifier implements Notifier {
    protected final String recipient;
    BaseNotifier(String recipient) { this.recipient = recipient; }
    public void log(String msg) { System.out.println("Sending to " + recipient + ": " + msg); }
}

class SmsNotifier extends BaseNotifier {
    SmsNotifier(String phone) { super(phone); }
    @Override public void send(String msg) { log(msg); /* call SMS gateway */ }
}

class EmailNotifier extends BaseNotifier {
    EmailNotifier(String email) { super(email); }

Demo: Smart City sensor devices (template method + interface)

import java.time.Instant;
import java.util.List;

// Contract (capability)
interface Calibratable {
    void calibrate();
}

// Partial abstraction with shared state + template method
abstract class SensorDevice {
    private final String deviceId;               // shared state
    protected SensorDevice(String deviceId) { this.deviceId = deviceId; }

    // Template method: fixed algorithm, steps supplied by subclasses
    public final Reading capture() {
        double raw = readRaw();                  // abstract step
        double value = normalize(raw);           // hook (overridable)
        return new Reading(deviceId, type(), value, Instant.now());
    }

    protected abstract double readRaw();         // HOW is hidden in subclasses
    protected abstract String type();
    protected double normalize(double raw) { return raw; }

    public String getDeviceId() { return deviceId; }
}

record Reading(String deviceId, String type, double value, Instant at) {}

class AirQualitySensor extends SensorDevice implements Calibratable {
    AirQualitySensor(String id) { super(id); }
    @Override protected double readRaw() { return 182.4; }     // e.g. read from serial port
    @Override protected String type() { return "AQI"; }
    @Override protected double normalize(double raw) { return Math.min(raw, 500); }
    @Override public void calibrate() { System.out.println("AQI sensor zeroed"); }
}

class TrafficCounter extends SensorDevice {
    TrafficCounter(String id) { super(id); }
    @Override protected double readRaw() { return 1240; }      // vehicles/hour
    @Override protected String type() { return "TRAFFIC"; }
}

public class AbstractionDemo {
    public static void main(String[] args) {
        List<SensorDevice> devices = List.of(new AirQualitySensor("AQ-01"), new TrafficCounter("TC-07"));
        for (SensorDevice d : devices) {                  // client knows only the abstraction
            System.out.println(d.capture());
            if (d instanceof Calibratable c) c.calibrate(); // pattern matching (Java 16+)
        }
        // new SensorDevice("x");  // compile error: SensorDevice is abstract; cannot be instantiated
    }
}

Gotchas

  • An abstract class can have a constructor. It runs when a subclass is instantiated.
  • abstract cannot be combined with final, private or static on a method (none of those can be overridden).
  • A class with even one abstract method must be declared abstract. An abstract class may also have zero abstract methods (to prevent instantiation).
  • Anonymous class instantiation is allowed: new SensorDevice("x") { ... }.

Likely follow-ups:

  • Abstract class or interface after Java 8? Interface for the contract, abstract class when you need state or constructors. Often both: an interface plus an AbstractXxx skeleton (e.g. List + AbstractList).
  • Can an interface have a constructor? No. It has no instance state to initialise.
  • Can an abstract class implement an interface without implementing its methods? Yes. The first concrete subclass must implement them.
A7 Why were functional interfaces introduced, what is one, and how do you define one? Other rounds (Question List)
  • A functional interface has exactly one abstract method (SAM). It can also have any number of default and static methods.
  • They were introduced in Java 8 to give lambdas and method references a target type, so behaviour can be passed around without anonymous classes.
  • Mark one with @FunctionalInterface (optional, but the compiler then enforces the single-abstract-method rule). Built-in examples: Runnable, Comparator, Function, Predicate.
@FunctionalInterface
interface Validator<T> {
    boolean validate(T t);
    default Validator<T> and(Validator<T> other) { return t -> validate(t) && other.validate(t); }
}
Validator<String> notEmpty = s -> !s.isBlank();

A functional interface is an interface with exactly one abstract method (a SAM, Single Abstract Method). It is the target type for lambda expressions and method references.

Why introduced (Java 8)

  • Java's designers did not want to add function types (like (int)->int) to the type system, because that would complicate generics, erasure and the JVM. Instead, a lambda is converted to an instance of a SAM interface.
  • Backward compatibility: existing single-method interfaces (Runnable, Callable, Comparator, ActionListener) automatically became lambda-friendly with no API change.
  • They enable streams and functional-style APIs (filter(Predicate), map(Function)).

interface FareCalculator {

    static FareCalculator flat(double rate) {           // statics allowed
        return (km, peak) -> km * rate;
    }
    boolean equals(Object o);   // public Object methods do NOT count as abstract
    String toString();
}

    public static void main(String[] args) {
        FareCalculator bus = (km, peak) -> peak ? km * 2.5 : km * 2.0;
        FareCalculator metro = FareCalculator.flat(3).withSurcharge(10);

Rules and gotchas

  • @FunctionalInterface is optional but recommended. The compiler then enforces the single-abstract-method rule, and it documents intent.
  • Default, static and private methods, plus abstract re-declarations of public Object methods (equals, hashCode, toString), don't count. That's why Comparator (which declares equals) is still functional.
  • An interface that inherits one abstract method and declares nothing new is functional (e.g. interface X extends Runnable {}).
  • Lambdas can't throw checked exceptions unless the SAM declares them. That's why Callable.call() throws Exception exists alongside Runnable.
  • A lambda's type is decided by context. The same lambda () -> 42 can be a Supplier<Integer> or a Callable<Integer>.

Likely follow-ups:

  • Is @FunctionalInterface mandatory for lambdas? No. Any SAM interface works. The annotation only adds compile-time checking.
  • Can a functional interface extend another? Yes, as long as the total number of abstract methods (after merging override-equivalent ones) stays one.
  • Why can a lambda only use effectively final locals? It captures a copy of the value, so allowing mutation would cause confusing semantics and data races.
A8 If a functional interface already has one abstract method and another abstract method is added, what happens? Other rounds (Question List)

  • Exceptions: adding default/static methods is fine. Redeclaring a public Object method (e.g. boolean equals(Object o)) does not count as an abstract method.

A9 What is the use of default methods in interfaces? Co. 2
  • They let you add new methods to an interface without breaking existing implementations. This is backward compatibility, for example List.forEach and Collection.stream().
  • They provide a common implementation that classes can optionally override.
  • Diamond rule: if two interfaces provide the same default method, the class must override it and can pick one with A.super.method().

A default method (Java 8) is an interface method with a body, marked default. Implementing classes inherit it and may override it.

Why

  1. Interface evolution / backward compatibility. The JDK needed to add forEach, stream, removeIf, spliterator to Collection/Iterable without breaking millions of existing implementations.
  2. Optional behaviour / convenience methods: Comparator.reversed(), thenComparing(), Map.getOrDefault(), Map.computeIfAbsent().
  3. Fewer "adapter" abstract classes (WindowAdapter-style).
interface Payment {
    void pay(double amount);
    default String currency() { return "INR"; }                    // convenience
    default void payWithReceipt(double amt) {                       // behaviour built on the abstract op
        pay(amt);
        System.out.println("Receipt: " + amt + " " + currency());
    }
}
class UpiPayment implements Payment {
    @Override public void pay(double amount) { System.out.println("UPI " + amount); }
}

Diamond problem: resolution rules (JLS 8.4.8, 9.4.1)

  1. Class wins. A method from a superclass (concrete or abstract) takes priority over any interface default.
  2. More specific interface wins. If B extends A and both define hello(), then B.hello() is chosen.
  3. Otherwise it's ambiguous. The class must override and may pick one explicitly with X.super.method().
interface Camera { default String start() { return "Camera on"; } }
interface Radar  { default String start() { return "Radar on"; } }

// class TrafficUnit implements Camera, Radar {}  // compile error:
//   "types Camera and Radar are incompatible; class TrafficUnit inherits unrelated defaults for start()"

class TrafficUnit implements Camera, Radar {
    @Override public String start() {
        return Camera.super.start() + " + " + Radar.super.start();   // explicit choice
    }
}

class Base { public String start() { return "Base"; } }
class Unit2 extends Base implements Camera { }   // Rule 1: new Unit2().start() -> "Base"

interface SmartCamera extends Camera { default String start() { return "Smart camera on"; } }
class Unit3 implements Camera, SmartCamera { }   // Rule 2: "Smart camera on"

Gotchas

  • A default method cannot override equals, hashCode or toString. That's a compile error, because Object's methods always win (rule 1).
  • Default methods can't be final or synchronized, and they have no access to instance state (interfaces have no fields).
  • X.super.m() works only for a direct super-interface.
  • Unlike C++, there is no diamond problem with state, because interfaces carry behaviour only.

Likely follow-ups:

  • Abstract class vs interface with default methods? Abstract classes hold state and constructors. Interfaces allow multiple inheritance but no state.
  • Can a sub-interface redeclare a default as abstract? Yes. interface X extends Camera { String start(); } forces implementers to provide it again.
  • Java 9 addition? private (and private static) interface methods, so defaults can share helper code.
A10 What is the use of static methods in interfaces?
  • They hold utility/helper methods that belong to the interface, so you don't need a separate *Utils class. Examples: Comparator.comparing(), List.of().
  • They are not inherited by implementing classes and must be called as InterfaceName.method().

Since Java 8, interfaces can have static methods with a body. They belong to the interface itself and are called as InterfaceName.method().

Uses

  • Factory methods that keep related utilities next to the type: List.of(), Map.of(), Map.entry(), Comparator.comparing(), Comparator.naturalOrder(), Function.identity(), Stream.of(), Path.of().
  • They replace companion utility classes (Collections for Collection, Paths for Path).
  • Validation/helper logic that shouldn't be overridden.

Key rules

  • Static interface methods are not inherited by implementing classes or sub-interfaces. Car.isValid(...) and carObj.isValid(...) are compile errors. Static methods in classes are different: they are inherited and can be called via a subclass or an instance.
  • This avoids ambiguity when a class implements two interfaces with the same static method.
  • They are implicitly public unless declared private static (Java 9+). They can't be abstract, default or final.
  • They can't be overridden. A same-signature static method in the implementing class is just an unrelated method.

Likely follow-ups:

  • Why not inherited, unlike class statics? So that implementing multiple interfaces with same-named statics doesn't conflict, and so the call site always names the owner explicitly.
  • Can an interface have a main method? Yes (public static void main), and you can run it with java InterfaceName.
  • Static vs default? Static has no this and isn't polymorphic. Default is an instance method, inherited and overridable.
A11 Can we override private methods?
  • No. Private methods aren't visible to subclasses, so they aren't inherited. A method with the same signature in a subclass is a new, unrelated method: no polymorphism, and @Override gives a compile error.

No. A private method is visible only within its declaring class (and its nest, since Java 11). It is not inherited, so a subclass cannot override it. If the subclass declares a method with the same signature, it is a brand-new, unrelated method.

Consequences:

  • Calls to a private method are statically bound. Calling it from within the parent always invokes the parent's version, even if the runtime object is a subclass.
  • @Override on the subclass method gives a compile error: "method does not override or implement a method from a supertype".
  • Since the subclass method is independent, it can have any access modifier, return type and exceptions.
class Account {
    private void audit() { System.out.println("Account.audit"); }
    public void process() { audit(); }        // statically bound to Account.audit
}
class SavingsAccount extends Account {
    // @Override  -> compile error
    public void audit() { System.out.println("SavingsAccount.audit"); } // new method
}
public class PrivateDemo {
    public static void main(String[] args) {
        Account a = new SavingsAccount();
        a.process();                          // prints "Account.audit" - no polymorphism
        new SavingsAccount().audit();         // "SavingsAccount.audit"
    }
}

Compare: if audit() were protected/public, a.process() would print SavingsAccount.audit (dynamic dispatch). This is the classic trap question.

Edge cases

  • Nested classes: a nested subclass can access the outer class's private method, but still cannot override it.
  • Private methods are implicitly "effectively final". Adding final is legal but redundant.
  • Reflection (setAccessible(true)) can call a private method, but never makes it overridable.

Likely follow-ups:

  • Can we override final methods? No. Compile error "overridden method is final".
  • Can we override protected / package-private methods? Protected yes. Package-private only from a subclass in the same package; in another package it's not inherited, so it's a new method.
  • Why are private methods statically bound? Not inherited means no virtual dispatch is needed, so the compiler can resolve the exact target.
A12 Can we override static methods? Can we override a static method in an interface?
  • Class static methods: no. A subclass static method with the same signature hides the parent's (method hiding). Which one runs is decided by the reference type at compile time.
  • Interface static methods: no. They aren't even inherited by implementing classes. A class can declare a static method with the same signature, but it is completely unrelated, and you still call I.m().
  • Declaring an instance method that matches a parent's static method, or the other way round, is a compile error.

Static methods in classes: no override, only hiding. A static method is resolved at compile time using the reference (declared) type, not the runtime object. A subclass can declare a static method with the same signature, which hides the parent's (see A13).

class Logger {
    static String name() { return "Logger"; }
    String instanceName() { return "Logger"; }
}
class FileLogger extends Logger {
    static String name() { return "FileLogger"; }           // hiding, not overriding
    @Override String instanceName() { return "FileLogger"; } // overriding
}
public class StaticDemo {

        Logger l = new FileLogger();

        System.out.println(l.instanceName());  // "FileLogger" -> runtime type decides
    }
}

  • Why can't statics be overridden? Overriding needs an object for dynamic dispatch (invokevirtual). Statics use invokestatic, resolved from the class.
  • Can we call a static method through a null reference? Yes. ((Logger) null).name() works (with a warning), because no object is dereferenced.

A13 What is method hiding? Co. 2

When a subclass defines a static method with the same signature as a static method in its parent, the subclass method hides the parent's. The call is resolved by the reference type, not the object type.

class P { static void show() { System.out.println("P"); } }
class C extends P { static void show() { System.out.println("C"); } }
P p = new C();
p.show();   // prints "P" (static binding by reference type)

Method hiding happens when a subclass declares a static method with the same signature as a static method in its superclass. The subclass method hides the superclass one. Which one runs depends only on the compile-time (reference) type of the expression, or the class name used.

class Parent {
    static void greet() { System.out.println("Parent.greet"); }
    void show()         { System.out.println("Parent.show"); }
}
class Child extends Parent {
    static void greet() { System.out.println("Child.greet"); }   // hides
    @Override void show(){ System.out.println("Child.show"); }   // overrides
}
public class HidingDemo {

        Child  c = new Child();

        c.greet();      // Child.greet
        Parent.greet(); // Parent.greet
        p.show();       // Child.show    (runtime type Child)
        ((Parent) c).greet(); // Parent.greet - casting changes which static runs
    }
}

A14 What is serialization? How do you prevent a variable from being serialized?
  • Serialization converts an object's state into a byte stream (ObjectOutputStream) so it can be stored or sent over the network. Deserialization rebuilds the object from the bytes.
  • The class must implement Serializable (a marker interface). Declare a serialVersionUID for version control.
  • To exclude a field, mark it transient. On deserialization it gets its default value (null/0/false). static fields are also not serialized, because they belong to the class.
  • In microservices we usually serialize to JSON (Jackson) and exclude fields with @JsonIgnore.
class User implements Serializable {
    private static final long serialVersionUID = 1L;
    private String username;
    private transient String password;   // not serialized
}

Serialization converts an object graph into a byte stream (to store in a file, send over a network, or put in a cache/session). Deserialization rebuilds the object graph from the bytes. In Java you use ObjectOutputStream.writeObject() / ObjectInputStream.readObject(), and the class must implement the marker interface java.io.Serializable.

import java.io.*;

class User implements Serializable {
    private static final long serialVersionUID = 1L;    // version stamp
    private String username;
    private transient String password;                   // NOT serialized
    private static String region = "KA";                 // NOT serialized (class-level)
    private transient int loginCount = 5;                // becomes 0 after deserialization

    User(String u, String p) { username = u; password = p; }
    @Override public String toString() {
        return username + "/" + password + "/" + loginCount + "/" + region;
    }
}

public class SerDemo {
    public static void main(String[] args) throws Exception {
        var bos = new ByteArrayOutputStream();
        try (var out = new ObjectOutputStream(bos)) { out.writeObject(new User("nagesh", "s3cret")); }
        try (var in = new ObjectInputStream(new ByteArrayInputStream(bos.toByteArray()))) {
            System.out.println(in.readObject());   // nagesh/null/0/KA
        }
    }
}

Don't implement Serializable on the field's type Then serializing fails with NotSerializableException (you'd normally mark it transient).

serialVersionUID

  • This is a version number checked during deserialization. If it doesn't match, you get InvalidClassException.
  • If you don't declare one, the JVM computes it from the class structure. Adding even a method can change it and break old serialized data. Always declare it.
  • Compatible changes (adding a field) work with the same UID: missing fields get default values.

Inheritance rules

  • If the parent is not Serializable, its fields aren't saved. On deserialization, the parent's no-arg constructor runs (it must exist and be accessible, or you get InvalidClassException).
  • If the parent is Serializable, all subclasses are too. To block serialization in a subclass, throw NotSerializableException from writeObject.

Singletons and records

  • Deserialization creates a new instance and breaks singletons. Add readResolve() returning the singleton, or use an enum singleton.
  • Records (Java 16+) deserialize through the canonical constructor, so validation runs. That's safer than for ordinary classes.

Security concerns (important)

  • Java deserialization of untrusted data is a well-known remote code execution vector ("gadget chains" in Commons-Collections etc.; many CVEs).
  • Mitigations:
    • Never deserialize untrusted input.
    • Use ObjectInputFilter (JEP 290, Java 9; context-specific filter factories in Java 17, JEP 415), e.g. -Djdk.serialFilter=com.trinity.*;!*.
    • Prefer JSON (Jackson)/Protobuf/Avro for APIs and messaging.
  • Don't serialize secrets. Mark passwords and tokens transient or exclude them.

Likely follow-ups:

  • Serializable vs Externalizable? Serializable is automatic, reflection-based, and needs no constructor. Externalizable is manual, can be faster and smaller, and needs a public no-arg constructor.
  • What does transient final do? The field is set to its default after deserialization and can't be reassigned normally. You'd need readResolve or reflection.
  • Why is Serializable a marker interface? It's an opt-in flag: the serialization machinery checks instanceof Serializable.
  • How does Spring/Kafka serialize? Mostly JSON (Jackson) or Avro/Protobuf, not Java native serialization.
A15 Explain the volatile keyword. G2Other rounds (Question List)
  • volatile guarantees visibility: reads and writes go to main memory, so every thread sees the latest value. It also prevents reordering through a happens-before guarantee.
  • It does not give atomicity. count++ on a volatile field is still a race, so use AtomicInteger or synchronized for that.
  • Typical uses: stop flags, and the instance field in double-checked locking singletons.
private volatile boolean running = true;
public void stop() { running = false; }      // other thread sees it immediately

volatile is a field modifier that makes visibility and ordering guarantees for that variable across threads. It does not provide mutual exclusion or atomicity for compound actions.

The problem it solves

Each core can keep values in registers or caches, and both the JIT and the CPU reorder instructions. Without synchronization, one thread may never see another thread's write:

public class StopFlag {
    private static volatile boolean running = true;   // remove volatile -> loop may never end

    public static void main(String[] args) throws InterruptedException {
        Thread worker = new Thread(() -> {
            long n = 0;
            while (running) { n++; }    // JIT could hoist 'running' into a register if not volatile
            System.out.println("stopped at " + n);
        });
        worker.start();
        Thread.sleep(1000);
        running = false;               // guaranteed to become visible to worker
        worker.join();
    }
}

Guarantees (Java Memory Model, JSR-133)

  1. Visibility. A write to a volatile variable is immediately flushed so other threads see it. A read always gets the latest value from main memory.
  2. Happens-before. A write to volatile v happens-before every subsequent read of v. Everything the writing thread did before the volatile write is visible to a thread after it reads that value. This is the "safe publication" piggyback.
  3. No reordering across the volatile access. The compiler and CPU insert memory barriers (StoreStore/StoreLoad etc.).
  4. Reads and writes of volatile long and double are atomic. Non-volatile 64-bit writes may tear on 32-bit JVMs.

Not atomic: classic trap

private volatile int count = 0;
void inc() { count++; }   // read-modify-write: 3 steps, two threads can both read 5 and write 6

Fix: AtomicInteger.incrementAndGet() (CAS), LongAdder (high contention), or synchronized.

Double-checked locking (needs volatile)

public final class ConfigRegistry {
    private static volatile ConfigRegistry instance;   // volatile is REQUIRED
    private ConfigRegistry() { /* load config */ }

    public static ConfigRegistry getInstance() {
        ConfigRegistry local = instance;               // one volatile read on the fast path
        if (local == null) {
            synchronized (ConfigRegistry.class) {
                local = instance;
                if (local == null) {
                    instance = local = new ConfigRegistry();
                }
            }
        }
        return local;
    }
}

Why volatile? instance = new ConfigRegistry() is really three steps: (1) allocate memory, (2) run the constructor, (3) assign the reference. Without volatile, steps 2 and 3 can be reordered. Another thread could then see a non-null but partially constructed object. Simpler alternatives are the holder-class idiom (lazy, thread-safe class init) or an enum singleton.

Use volatile for: status flags, the one-writer-many-readers pattern, safely publishing immutable objects, and the DCL singleton.

Likely follow-ups:

  • Is volatile enough for a counter? No. count++ isn't atomic. Use AtomicInteger or LongAdder.
  • Can a local variable be volatile? No. Locals are thread-confined (on the stack), so it's a compile error.
  • volatile vs synchronized? volatile = visibility + ordering only. synchronized = visibility + mutual exclusion (atomicity), and it can block.
  • What is happens-before? A JMM guarantee that the effects of action A are visible to action B, e.g. unlock→lock, volatile write→read, Thread.start()→the thread's first action, thread end→join() returns.
A16 What is garbage collection and how is it used? Co. 2
  • The GC is the JVM's automatic memory management. It frees heap objects that are no longer reachable from GC roots (stack references, static fields, active threads).
  • The heap is generational: Young (Eden plus survivor spaces, collected often by minor GC) and Old (long-lived objects, collected by major/full GC).
  • Collectors: Serial, Parallel, G1 (default since Java 9), and ZGC/Shenandoah for low pause times.
  • We don't control when GC runs. System.gc() is only a hint. Our job is to avoid leaks (static collections, unclosed resources, listeners) and tune with flags like -Xms, -Xmx and -XX:+UseG1GC.

Garbage collection (GC) automatically reclaims heap memory occupied by objects that are no longer reachable from any GC root. You don't free() memory. The JVM finds dead objects and recycles their space.

Reachability and GC roots

An object is alive if there is a reference path to it from a root:

  • Local variables and operand stacks of every thread's frames
  • Static fields of loaded classes
  • Active threads
  • JNI references (native code)
  • Monitors held by synchronized
  • Classes loaded by the system/bootstrap class loader

Unreachable cycles (A↔B with no root reference) are collected. Java uses tracing, not reference counting.

Generational hypothesis: most objects die young.

Heap
├── Young Generation
│   ├── Eden          <- new objects allocated here (TLABs: thread-local allocation buffers)
│   ├── Survivor S0   <- survivors copied back and forth; age incremented
│   └── Survivor S1
└── Old (Tenured) Gen <- promoted after surviving N minor GCs (MaxTenuringThreshold, default 15)
Metaspace (native memory) - class metadata, not part of the heap
  • Minor GC: collects the Young gen. Fast, copying collector, stop-the-world (STW) but short.
  • Major/Full GC: collects Old gen (or everything). Expensive and causes long pauses.

Phases (conceptual): Mark (trace from roots) → Sweep (free dead objects) → Compact (defragment), or copy survivors to a fresh space.

How do you "use" it?

  • Mostly you don't call it. Write code that doesn't hold unnecessary references.
  • System.gc() / Runtime.getRuntime().gc() is only a hint. The JVM may ignore it (-XX:+DisableExplicitGC). It usually triggers a Full GC, which is bad in production.
  • Tune with -Xms/-Xmx (heap size), -XX:MaxRAMPercentage (containers), the choice of collector, and pause goals.
  • Observe with -Xlog:gc* (unified logging, Java 9+), jstat -gc <pid>, jcmd <pid> GC.heap_info, VisualVM, Java Flight Recorder/JMC, GCEasy, and Micrometer jvm.gc.pause metrics in Spring Boot Actuator.

Memory leaks still happen in Java

  • Objects stay reachable unintentionally: static Map caches that only grow, unremoved listeners, ThreadLocal in thread pools (call remove()), unclosed resources, and inner classes holding a reference to their outer instance.
  • Diagnose: take a heap dump (jcmd <pid> GC.heap_dump file.hprof or -XX:+HeapDumpOnOutOfMemoryError) and analyse it in Eclipse MAT (dominator tree, retained size).

A17 Output of System.out.println(Double.MIN_VALUE > 0.0d) and why?

  • Double.MIN_VALUE is the smallest positive double (about 4.9E-324), not the most negative one. The most negative double is -Double.MAX_VALUE.

Output: true.

Double.MIN_VALUE is not the most negative double. It is the smallest positive non-zero value a double can represent: 4.9E-324 (2^-1074), a subnormal (denormalized) number. Since it's positive, it is greater than 0.0.

Rules

  1. this(...) or super(...) must be the first statement in the constructor. You can't use both in one constructor.
  2. If neither is written, the compiler inserts super(). If the parent has no no-arg constructor, that's a compile error.
  3. Recursive constructor invocation (A→B→A) is a compile error.
  4. You can't call a constructor like a normal method (Camera("x") is invalid). Only this(...), super(...) or new.

A25 Internal working of HashMap Co. 2Other rounds (Question List)
  • It is backed by an array of buckets (Node<K,V>[] table). The default capacity is 16 and is always a power of 2.
  • put(k, v):
    1. hash = h ^ (h >>> 16). This hash spreading mixes the high bits into the low bits.
    2. Bucket index = (n - 1) & hash.
    3. Empty bucket: insert the node. Otherwise walk the bucket: if a key matches by hash == and equals(), replace the value; if not, append a new node.
  • Load factor 0.75: when size > capacity * 0.75 (e.g. 12 for capacity 16), it resizes to double capacity. Each node either stays at its index or moves to index + oldCap.
  • Treeify: a bucket's list becomes a red-black tree when it reaches 8 nodes and the table has at least 64 buckets. With a smaller table it resizes instead. A tree turns back into a list at 6 nodes. Worst-case lookup goes from O(n) to O(log n).
  • get(k) follows the same hash, then index, then equals path. Average time is O(1).

Structure (Java 8+): an array Node<K,V>[] table of buckets. Each bucket is null, a linked list of Nodes, or a red-black tree of TreeNodes.

static class Node<K,V> implements Map.Entry<K,V> {
    final int hash;   // cached spread hash
    final K key;
    V value;
    Node<K,V> next;
}

put(key, value) step by step

  1. Compute the hash with spreading:
    static final int hash(Object key) {
    int h;
    return (key == null) ? 0 : (h = key.hashCode()) ^ (h >>> 16);
}
    XOR-ing the high 16 bits into the low 16 matters because the index uses only the low bits. Without it, hashCodes that differ only in their high bits (e.g. Float keys, or multiples of 2^16) would all collide.
  2. Lazy init: the table is allocated on the first put (resize()), not in the constructor.
  3. Find the bucket index: index = (n - 1) & hash. With n = 16, n - 1 = 0b1111, so it takes the low 4 bits. That equals hash % n for power-of-two n, but is faster and is never negative.
  4. Empty bucket → place a new Node.
  5. Non-empty bucket → walk the chain. For each node, check p.hash == hash && (p.key == key || key.equals(p.key)).
    • Match → replace the value (the key object stays the same) and return the old value.
    • No match → append at the tail (Java 8; Java 7 inserted at the head).
    • If the chain length reaches TREEIFY_THRESHOLD (8) → treeifyBin: treeify if table.length >= 64, else resize.
    • If the bucket is a TreeNode → putTreeVal (O(log n)).
  6. modCount++ (drives fail-fast iterators). If ++size > threshold, call resize().

resize()

  • Doubles the capacity (newCap = oldCap << 1) and the threshold.
  • Rehash is cheap: since n doubles, each node either stays at index i or moves to i + oldCap, depending on a single bit: (hash & oldCap) == 0. The bucket is split into "lo" and "hi" lists, preserving relative order.
  • Tree bins are split the same way. If a half has ≤ 6 nodes, it's untreeified.
  • Cost: O(n) when it happens, amortized O(1) per put. Pre-size when you know the count: new HashMap<>(expected / 0.75f + 1), or Java 19+ HashMap.newHashMap(expected).

get(key): compute the hash → index → check the first node → then traverse the list (O(k)) or the tree (O(log k)), using hash == then equals.

Tree bins: ordered by hash. On ties, by compareTo if keys are mutually Comparable, else tieBreakOrder (class name, then System.identityHashCode). Treeification is a defence against poor hash functions and hash-flooding attacks. With a good hash the probability of a bucket reaching 8 is ~0.00000006 (Poisson distribution, per the JDK source comments).

Complexity: average O(1) for get/put/remove. Worst case O(log n) in Java 8+ (O(n) in Java 7, or for non-Comparable keys with identical hashes).

Why Java 8 switched from head to tail insertion: in Java 7, concurrent resizes with head insertion could reverse a list and create a cycle, which made get() spin forever at 100% CPU. Tail insertion avoids the cycle, but HashMap is still not thread-safe (lost updates, corrupted size).

Likely follow-ups:

  • Why is capacity a power of two? So that (n-1) & hash replaces the slow %, and so the resize split works with a single bit.
  • Why load factor 0.75? An empirical balance. Higher means more collisions. Lower means more memory and more frequent resizes.
  • Why treeify at 8 but untreeify at 6? The gap (hysteresis) stops a bucket flapping between list and tree around one threshold.
  • Is iteration order guaranteed? No. It can change after a resize. Use LinkedHashMap or TreeMap.
A26 How are HashMap collisions handled? Co. 2
  • A collision means different keys land in the same bucket. HashMap uses separate chaining: the bucket holds a linked list of nodes, with new nodes appended at the tail since Java 8.
  • Lookup inside a bucket compares the hash and then equals().
  • Since Java 8, a long chain (8 or more nodes, table of at least 64) is converted to a red-black tree. This keeps worst-case lookup at O(log n) and protects against hash-flooding attacks.
  • A good hashCode() and resizing keep chains short in the first place.

A collision happens when two different keys land in the same bucket index. That happens either because their hashCodes are equal, or because (n-1) & hash maps different hashes to the same slot.

HashMap uses separate chaining:

  1. Linked list in the bucket (Java 8 appends at the tail). Lookup walks the chain comparing hash first (a cheap int check), then ==, then equals().
  2. Treeification (Java 8): when a single bucket reaches 8 nodes and the table has ≥ 64 buckets, the list becomes a red-black tree (TreeNode), so lookups go from O(k) to O(log k). If the table is smaller than 64, HashMap resizes instead, because spreading entries is the better fix when the table is small.
  3. Untreeify back to a list when a bin drops to ≤ 6 nodes during a resize split.
  4. Resizing reduces collisions overall by doubling the bucket count and spreading the entries.

  • Write a good hashCode() using all the significant fields (Objects.hash(...), or records/Lombok generate it).

The equals/hashCode contract (from Object Javadoc)

  1. Consistency: repeated hashCode() calls return the same value while the fields used in equals don't change.
  2. a.equals(b) ⇒ a.hashCode() == b.hashCode(). This is mandatory.
  3. Equal hash codes do not imply equals (collisions are allowed).
  4. equals must be reflexive, symmetric, transitive, consistent, and x.equals(null) == false.

import java.util.Objects;

public final class Employee {
    private final String name;
    public Employee(String name) { this.name = name; }
    public String getName() { return name; }

    @Override public boolean equals(Object o) {
        if (this == o) return true;
        if (!(o instanceof Employee other)) return false;   // pattern matching (16+)
        return Objects.equals(name, other.name);
    }
    @Override public int hashCode() { return Objects.hashCode(name); }  // or Objects.hash(f1, f2...)
    @Override public String toString() { return "Employee[name=" + name + "]"; }
}

  • Use the same fields in both equals and hashCode.

A32 Concurrent collections and concurrent access in Java. G2
  • Plain collections aren't thread-safe. Collections.synchronizedList/Map locks the whole collection, which makes it a bottleneck.

                while (!(r = queue.take()).equals("EOF")) System.out.println("processed " + r); // blocks if empty
            } catch (InterruptedException e) { Thread.currentThread().interrupt(); }
        });
        producer.start(); consumer.start();
        producer.join(); consumer.join();
    }
}

Other concurrent-access tools: synchronized, ReentrantLock (tryLock, fairness, interruptible), ReadWriteLock/StampedLock (optimistic reads), Atomic* and LongAdder, volatile, CountDownLatch, CyclicBarrier, Semaphore (rate-limiting connections), Phaser, ThreadLocal, and immutability (the simplest form of thread safety).

Gotchas

  • Check-then-act and read-modify-write sequences are races even on thread-safe collections.
  • CopyOnWriteArrayList is terrible for write-heavy workloads (O(n) copy per write).
  • ConcurrentLinkedQueue.size() is O(n) and approximate.
  • In a microservices deployment, in-JVM concurrency doesn't protect against multiple instances. Use DB locks (SELECT ... FOR UPDATE, optimistic @Version), Redis locks (Redisson), or ShedLock for schedulers.

Likely follow-ups:

  • Fail-fast vs fail-safe iterators? Fail-fast throws CME (ArrayList, HashMap). Fail-safe/weakly consistent iterators work on a snapshot or tolerate changes (CopyOnWriteArrayList, CHM).
  • put/take vs offer/poll on a BlockingQueue? put/take block. offer/poll return immediately (false/null) or wait with a timeout.
  • How do you make a thread-safe Set? ConcurrentHashMap.newKeySet(), CopyOnWriteArraySet (read-mostly), or ConcurrentSkipListSet (sorted).

Correct wait/notify pattern: always loop on the condition

public class SignalBoard {
    private String message;                      // shared state guarded by 'this'

    public synchronized void publish(String msg) {
        message = msg;
        notifyAll();                             // wake waiting threads (prefer notifyAll)
    }

    public synchronized String awaitMessage() throws InterruptedException {
        while (message == null) {                // while, NOT if: guards against spurious wakeups
            wait();                              // releases 'this' monitor while waiting
        }
        String m = message;
        message = null;
        return m;
    }

    public static void main(String[] args) throws Exception {
        SignalBoard board = new SignalBoard();
        Thread reader = new Thread(() -> {
            try { System.out.println("Got: " + board.awaitMessage()); }
            catch (InterruptedException e) { Thread.currentThread().interrupt(); }
        });
        reader.start();
        Thread.sleep(500);                       // sleep keeps no lock here; just pauses main
        board.publish("Signal J12 green");
        reader.join();
    }
}

Gotchas

  • sleep() inside a synchronized block holds the lock the whole time. Other threads are blocked. That's a common performance bug.
  • notify() wakes one arbitrary waiting thread and can cause missed signals or deadlock-like stalls if several conditions share one monitor. Prefer notifyAll(), or Condition objects from ReentrantLock (await/signal).
  • On InterruptedException, restore the flag with Thread.currentThread().interrupt() rather than swallowing it.
  • In modern code, prefer higher-level tools: BlockingQueue, CountDownLatch, CompletableFuture. TimeUnit.SECONDS.sleep(1) is more readable than Thread.sleep(1000).

Likely follow-ups:

  • Why is wait() in Object and not Thread? Every object can be a monitor or lock, and a thread waits on a specific object's condition.
  • What is a spurious wakeup? A thread returns from wait() without a notify (allowed by the spec and the OS). That's why you check the condition in a while loop.
  • sleep(0) / yield? Both are scheduler hints. yield() suggests giving up the CPU, but there are no guarantees.

import java.util.*;
import java.util.concurrent.*;

public class CallableDemo {
    public static void main(String[] args) throws InterruptedException {
        ExecutorService pool = Executors.newFixedThreadPool(3);
        Callable<Integer> trafficCount = () -> { Thread.sleep(300); return 1240; };

        try {
            Integer v = f.get(2, TimeUnit.SECONDS);            // blocks up to 2s
            System.out.println("traffic = " + v);

        }

        List<Future<Integer>> all = pool.invokeAll(List.of(trafficCount, aqi)); // wait for all

        }

    }
}

CompletableFuture (Java 8): non-blocking composition

import java.util.concurrent.*;

public class CfDemo {
    public static void main(String[] args) {
        ExecutorService io = Executors.newFixedThreadPool(4);   // don't block the common pool with I/O

        CompletableFuture<Integer> traffic = CompletableFuture.supplyAsync(() -> 1240, io);
        CompletableFuture<Integer> aqi     = CompletableFuture.supplyAsync(() -> 182, io);

        CompletableFuture<String> dashboard = traffic
            .thenCombine(aqi, (t, a) -> "Traffic=" + t + ", AQI=" + a)   // combine two independent tasks
            .thenApply(String::toUpperCase)                              // transform
            .orTimeout(2, TimeUnit.SECONDS)                              // Java 9
            .exceptionally(ex -> "DATA UNAVAILABLE: " + ex.getMessage()); // fallback

        System.out.println(dashboard.join());   // join(): unchecked CompletionException instead of checked
        io.shutdown();
    }
}

Key methods: supplyAsync/runAsync, thenApply (map), thenCompose (flatMap, chains dependent async calls), thenCombine, allOf/anyOf, thenAccept, handle/whenComplete, exceptionally, completeOnTimeout. Without an executor argument, the async methods use ForkJoinPool.commonPool().

  • Use execute() for fire-and-forget tasks, with a configured UncaughtExceptionHandler via a custom ThreadFactory.

A38 What is the SOLID principle? Co. 2
  • S, Single Responsibility: a class should have one reason to change. For example, ReportService shouldn't also send emails.
  • O, Open/Closed: open for extension, closed for modification. Add a new AlertChannel implementation instead of editing a big if/else.
  • L, Liskov Substitution: subtypes must work wherever their base type is used, without breaking behaviour.
  • I, Interface Segregation: prefer many small, focused interfaces over one large interface.
  • D, Dependency Inversion: depend on abstractions, not concrete classes. Spring dependency injection with interface-typed constructor parameters is a direct example.

S – Single Responsibility Principle: a class should have one reason to change.

// BAD: one class validates, persists, and emails
// GOOD: split responsibilities
record Complaint(String id, String text, String email) {}
class ComplaintValidator  { void validate(Complaint c) { if (c.text().isBlank()) throw new IllegalArgumentException(); } }
class ComplaintRepository { void save(Complaint c) { /* JDBC/JPA */ } }
class ComplaintNotifier   { void acknowledge(Complaint c) { /* send email */ } }
class ComplaintService {
    private final ComplaintValidator v = new ComplaintValidator();
    private final ComplaintRepository r = new ComplaintRepository();
    private final ComplaintNotifier n = new ComplaintNotifier();
    void register(Complaint c) { v.validate(c); r.save(c); n.acknowledge(c); } // orchestrates only
}

O – Open/Closed Principle: open for extension, closed for modification.

// BAD: if (type.equals("BUS")) ... else if ("METRO") ... edited for every new type
interface FarePolicy { double fare(double km); }
class BusFare   implements FarePolicy { public double fare(double km) { return 10 + km * 1.5; } }
class MetroFare implements FarePolicy { public double fare(double km) { return 20 + km * 2.0; } }
// New mode (e.g. e-bike)? Add a class; FareCalculator is untouched.
class FareCalculator { double calc(FarePolicy p, double km) { return p.fare(km); } }

L – Liskov Substitution Principle: subtypes must be usable anywhere the base type is, without breaking expectations.

// BAD: class Square extends Rectangle - setWidth also changes height, breaking Rectangle's contract.
// BAD: class ReadOnlyList extends ArrayList { add() throws UnsupportedOperationException }
// GOOD: model capabilities separately
interface Shape { double area(); }
record Rect(double w, double h) implements Shape { public double area() { return w * h; } }
record Sq(double side)          implements Shape { public double area() { return side * side; } }

Signs of a violation: overrides that throw UnsupportedOperationException, strengthen preconditions, or weaken postconditions, and instanceof checks in client code.

I – Interface Segregation Principle: clients shouldn't depend on methods they don't use. Prefer small, focused interfaces.

// BAD: interface Device { void readData(); void rotateCamera(); void changeSignal(); }
interface Readable  { String readData(); }
interface Rotatable { void rotate(int degrees); }
class AirSensor implements Readable { public String readData() { return "AQI=182"; } }
class PtzCamera implements Readable, Rotatable {
    public String readData() { return "frame"; }
    public void rotate(int d) { System.out.println("rotate " + d); }
}

When to choose which

Choose a monolith (often a modular monolith) when:

  • The team is small (fewer than ~10 developers), the domain is new or unclear, or you're building an MVP or startup product.
  • Strong transactional consistency matters, or the ops/DevOps maturity is low.
  • You don't have heavy differential-scaling needs.

Choose microservices when:

  • Several teams need to deploy independently and the domain boundaries are well understood.
  • Modules have very different scaling or availability requirements. In a Smart City platform, for example: IoT sensor ingestion vs reporting vs citizen portal.
  • You need polyglot tech, and you have mature CI/CD, containers/Kubernetes and observability.

Migration path: Strangler Fig pattern. Put a gateway in front of the monolith and carve out one bounded context at a time (e.g. extract notification-service first, because it's loosely coupled).

Anti-pattern to mention: the distributed monolith. These are services that share a database or must be deployed together. You get all the costs of microservices with none of the benefits.

Likely follow-ups:

  • How do you handle transactions across services? The Saga pattern (choreography via events, or orchestration), with compensating actions plus a transactional outbox for reliable publishing.
  • How do services find each other? Service discovery: Eureka, Consul, or Kubernetes Services/DNS, with client- or server-side load balancing.
  • How do you prevent cascading failures? Timeouts, circuit breakers (Resilience4j), bulkheads, retries with backoff, and fallbacks.
  • What is a modular monolith? One deployable unit with strictly separated internal modules (e.g. Spring Modulith). It's the easiest to split later.

Rule: a reference of a parent type can hold a child object (upcast). The reverse needs an explicit downcast, which is only safe if the actual object really is that type.

class A implements I { }

class C extends B { }

Hierarchy: I ← A ← B ← C. So C is-a B, is-an A, is-an I. The reverse is not true.

1 A a = new I(); Compile error "I is abstract; cannot be instantiated". Interfaces can't be instantiated. (Even new I(){} as an anonymous class would give type I, which can't be assigned to A without a cast. That cast would compile but throw ClassCastException, since the anonymous class isn't an A.)
2 I b = new B(); Valid Upcasting: B extends A, which implements I, so B is-an I. Implicit widening reference conversion. Only I's members are accessible via b.
3 C c = new B(); Compile error "incompatible types: B cannot be converted to C". That's downcasting without a cast: not every B is a C. With an explicit cast, C c = (C) new B(); compiles (B and C are related) but throws ClassCastException at runtime, because the actual object is a B, not a C.
4 C c2 = new A(); Compile error "incompatible types: A cannot be converted to C". Same reason: an A is not a C. (C) new A() → compiles, then ClassCastException.

Java doesn't allow redeclaring a local in the same scope, even with a different type. Renamed, e.g. B b3 = new C();, it's perfectly fine. 
public class CastDemo {
    interface I { }
    static class A implements I { }
    static class B extends A { }
    static class C extends B { }

    public static void main(String[] args) {
        I b  = new B();                 // OK
        B b3 = new C();                 // OK - upcast
        I anon = new I() { };           // OK - anonymous class implementing I (not "new I()")
        try {
            C c = (C) new B();          // compiles, fails at runtime
        } catch (ClassCastException e) {
            System.out.println(e.getMessage()); // class CastDemo$B cannot be cast to class CastDemo$C ...
        }
        if (b instanceof C c) { /* safe downcast via pattern matching (16+) */ } else {
            System.out.println("b is not a C");
        }
    }
}

Rules to state in the interview

  • Upcasting (subtype → supertype) is implicit and always safe.
  • Downcasting (supertype → subtype) needs an explicit cast. It compiles only when the types are related (could possibly succeed), and it's checked at runtime (checkcast bytecode) → ClassCastException if wrong.
  • Casting between unrelated classes (e.g. (String) new A()) is a compile error ("incompatible types"). Casting to an interface from a non-final class compiles, because a subclass might implement it.
  • Use instanceof (with pattern matching) before downcasting.

Likely follow-ups:

  • What can you call on I b = new B()? Only members declared in I (and Object), even though the object is a B. Overridden methods still dispatch to B's implementation.
  • Why does (C) new B() compile at all? B and C are in the same hierarchy, so a B reference could point to a C. The compiler defers the check to runtime.
  • Would I i = (I) new String("x") compile? No. String is final and doesn't implement I, so the compiler knows the cast can never succeed.

Maximum array size

  • Theoretically Integer.MAX_VALUE elements, because the index is an int.
  • In practice, HotSpot reserves some header words, so the safe maximum is about Integer.MAX_VALUE - 8 (the JDK's ArrayList/ArraysSupport.SOFT_MAX_ARRAY_LENGTH uses that limit).

  • For more than 2^31 elements, use multiple arrays, long-indexed off-heap memory (the FFM API MemorySegment, final in 22), or memory-mapped files.

Other array declaration gotchas

  • int[] a = new int[]{1,2,3}; and int[] a = {1,2,3}; are both valid. int[] a = new int[3]{1,2,3}; is a compile error (you can't give both a size and an initializer).
  • int a[], b; declares a as an array and b as a plain int. int[] a, b; declares both as arrays.
  • Arrays are covariant: Object[] o = new String[1]; o[0] = 1; compiles but throws ArrayStoreException. Generics are invariant precisely to avoid this.
  • new int[3][] (jagged) is valid. new int[][3] is a compile error.

Likely follow-ups:

  • Why does the negative size compile? The JLS only requires the dimension expression to be of type int. The negative check is a runtime check in the JVM.
  • Can an array size be a long or a char? char/byte/short are promoted to int, so they're allowed. long is a compile error without an explicit (int) cast.
  • Is an array an object? Yes. It lives on the heap, has a length final field, extends Object, and implements Cloneable and Serializable.
  • Why is the max array size MAX_VALUE - 8? Some VMs reserve header words in the array object, and asking for more risks the "exceeds VM limit" OOM.
A42 Thread start() vs run(): which method do you call and why? Other rounds (Question List)
  • Call start(). It asks the JVM to create a new thread, and the JVM then calls run() on that thread.
  • If you call run() yourself, it is just a normal method call. It runs on the current thread, so nothing happens in parallel.
  • If you call start() twice on the same Thread, you get IllegalThreadStateException. A thread can be started only once.
public class StartVsRun {
    public static void main(String[] args) throws InterruptedException {
        Thread t = new Thread(() -> System.out.println("Running in: " + Thread.currentThread().getName()));
        t.run();    // plain method call on main
        t.start();  // new thread
        t.join();
        // t.start(); // would throw IllegalThreadStateException
    }
}
// Output:
// Running in: main
// Running in: Thread-0

You call start(). It asks the JVM to create a new OS-level thread, moves the Thread from NEW to RUNNABLE, and the JVM then calls run() on that new thread. If you call run() yourself, it is an ordinary method call: the code runs on the current thread and no concurrency happens.

public class StartVsRun {
    public static void main(String[] args) throws InterruptedException {
        Runnable task = () -> System.out.println("running on " + Thread.currentThread().getName());

        Thread t1 = new Thread(task, "worker-1");
        t1.run();      // running on main      <- no new thread
        t1.start();    // running on worker-1  <- new thread
        t1.join();

        try {
            t1.start(); // a thread can be started only once
        } catch (IllegalThreadStateException e) {
            System.out.println("second start(): " + e.getClass().getSimpleName());
        }
    }
}
// Output:
// running on main
// running on worker-1
// second start(): IllegalThreadStateException

What start() does internally

  1. Checks the thread status is NEW (threadStatus == 0), otherwise throws IllegalThreadStateException.
  2. Adds the thread to its ThreadGroup and calls the native start0(), which creates the platform thread.
  3. The new thread begins executing Thread.run(), which calls the Runnable you passed (or your overridden run()).

States: NEW → start() → RUNNABLE → (BLOCKED / WAITING / TIMED_WAITING) → TERMINATED once run() returns or throws. A TERMINATED thread cannot be restarted; create a new Thread or, better, submit tasks to an ExecutorService.

In real code you rarely call either directly: you submit a Runnable/Callable to an ExecutorService, which reuses pooled threads. On Java 21+, Thread.ofVirtual().start(task) or Executors.newVirtualThreadPerTaskExecutor() gives cheap virtual threads for blocking I/O work.

Likely follow-ups:

  • Can you override start()? You can, but don't. If you skip super.start() no thread is created.
  • What happens if run() throws? The thread terminates and the exception goes to its UncaughtExceptionHandler (by default printed to stderr).
  • Why prefer Runnable over extending Thread? Your class can still extend something else, and the task is decoupled from how it's executed (pools, executors). See A36.
