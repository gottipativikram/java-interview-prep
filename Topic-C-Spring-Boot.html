C1 What is @SpringBootApplication?

It is a convenience meta-annotation that combines three annotations:

  • @SpringBootConfiguration, a specialised @Configuration, so the class can declare beans.
  • @EnableAutoConfiguration, which turns on auto-configuration based on the classpath and properties.
  • @ComponentScan, which scans the class's own package and its sub-packages.

Put it on the main class in the root package. You can exclude auto-configs with @SpringBootApplication(exclude = DataSourceAutoConfiguration.class).

@SpringBootApplication
public class CityApp {
    public static void main(String[] args) { SpringApplication.run(CityApp.class, args); }
}

@SpringBootApplication is a composed (meta-) annotation that you put on the main class. It turns on the three things almost every Boot app needs:

@Target(ElementType.TYPE)
@Retention(RetentionPolicy.RUNTIME)
@Documented
@Inherited
@SpringBootConfiguration          // = @Configuration (marks the class as a config source; tests use it to find the root config)
@EnableAutoConfiguration          // = @AutoConfigurationPackage + @Import(AutoConfigurationImportSelector.class)
@ComponentScan(excludeFilters = {
        @Filter(type = FilterType.CUSTOM, classes = TypeExcludeFilter.class),
        @Filter(type = FilterType.CUSTOM, classes = AutoConfigurationExcludeFilter.class) })
public @interface SpringBootApplication { ... }
Meta-annotation What it does
@SpringBootConfiguration A specialised @Configuration. There should be only one; @SpringBootTest and test slices find it by walking up the packages from the test class.
@EnableAutoConfiguration Imports AutoConfigurationImportSelector, which loads auto-configuration classes based on the classpath, existing beans and properties. @AutoConfigurationPackage records the main class's package (used by JPA entity scanning and Spring Data repository scanning).
@ComponentScan Scans the main class's package and all sub-packages for @Component stereotypes. The exclude filters stop auto-config classes from being picked up twice through scanning.

Attributes you can set: exclude, excludeName, scanBasePackages, scanBasePackageClasses, proxyBeanMethods.

How auto-configuration is discovered (internals)

  1. SpringApplication.run() creates the ApplicationContext and calls refresh().
  2. During invokeBeanFactoryPostProcessors, ConfigurationClassPostProcessor parses the main class and sees @Import(AutoConfigurationImportSelector.class).
  3. AutoConfigurationImportSelector is a DeferredImportSelector, so it runs after all user @Configuration classes have been processed. That ordering is what lets @ConditionalOnMissingBean back off when you define your own bean.
  4. It loads candidate class names with ImportCandidates.load(AutoConfiguration.class, classLoader), which reads every META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports file on the classpath (one fully qualified class name per line).
    • Boot 2.7 introduced this file. Boot 3.0 dropped support for auto-config entries in spring.factories.
  5. It removes exclusions (exclude, excludeName, spring.autoconfigure.exclude).
  6. Fast pre-filtering with AutoConfigurationImportFilter implementations (OnClassCondition, OnBeanCondition, OnWebApplicationCondition). They read precomputed META-INF/spring-autoconfigure-metadata.properties, so classes whose required classes are missing are thrown out without being loaded.
  7. The survivors are sorted (@AutoConfiguration(before/after), @AutoConfigureOrder) and parsed like normal configuration classes. Each @Conditional* on the class and its @Bean methods is evaluated.

The common @Conditional* annotations

Annotation Matches when
@ConditionalOnClass / @ConditionalOnMissingClass a class is / isn't on the classpath
@ConditionalOnBean / @ConditionalOnMissingBean a bean of the type/name exists / doesn't exist (only reliable in auto-config, because of ordering)
@ConditionalOnProperty(prefix, name, havingValue, matchIfMissing) a property has a value
@ConditionalOnWebApplication(type = SERVLET/REACTIVE) / @ConditionalOnNotWebApplication the type of application
@ConditionalOnResource a resource exists
@ConditionalOnExpression a SpEL expression is true
@ConditionalOnSingleCandidate exactly one candidate bean, or one @Primary
@ConditionalOnJava, @ConditionalOnCloudPlatform, @ConditionalOnThreading (3.2+, e.g. virtual threads) environment checks

All of these build on Spring Framework's @Conditional(Condition.class). Its matches(ConditionContext, AnnotatedTypeMetadata) method is called while bean definitions are being registered.

Writing your own auto-configuration (e.g. a shared Smart City "common-audit" starter)

package com.trinity.common.audit.autoconfigure;

import org.springframework.boot.autoconfigure.AutoConfiguration;
import org.springframework.boot.autoconfigure.condition.ConditionalOnClass;
import org.springframework.boot.autoconfigure.condition.ConditionalOnMissingBean;
import org.springframework.boot.autoconfigure.condition.ConditionalOnProperty;
import org.springframework.boot.context.properties.EnableConfigurationProperties;
import org.springframework.context.annotation.Bean;
import org.springframework.kafka.core.KafkaTemplate;

@AutoConfiguration
@ConditionalOnClass(KafkaTemplate.class)
@ConditionalOnProperty(prefix = "trinity.audit", name = "enabled", havingValue = "true", matchIfMissing = true)
@EnableConfigurationProperties(AuditProperties.class)
public class AuditAutoConfiguration {

    @Bean
    @ConditionalOnMissingBean            // the user's own AuditPublisher wins
    public AuditPublisher auditPublisher(KafkaTemplate<String, Object> template, AuditProperties props) {
        return new KafkaAuditPublisher(template, props.topic());
    }
}

Debugging

  • Run with --debug or set debug=true to print the Conditions Evaluation Report (positive and negative matches).
  • The Actuator /actuator/conditions endpoint shows the same report.
  • To exclude something: @SpringBootApplication(exclude = DataSourceAutoConfiguration.class) or spring.autoconfigure.exclude=....

Gotchas

  • If the main class is in the default package (no package), scanning covers the whole classpath. It is slow and can break the app. Always use a root package such as com.trinity.citypulse.
  • Classes in sibling packages outside the main class's package are not scanned or found as entities. Use scanBasePackages, @EntityScan or @EnableJpaRepositories.
  • @ConditionalOnMissingBean inside your own @Configuration (not an auto-config) is order-dependent and unreliable.

Likely follow-ups:

  • Where were auto-configs listed before Boot 2.7? In META-INF/spring.factories under the EnableAutoConfiguration key. Boot 3 no longer reads auto-configs from there.
  • How do you see why a bean wasn't auto-configured? Use --debug (the conditions report) or /actuator/conditions.
  • Can you use the three annotations separately instead of @SpringBootApplication? Yes. It is just a composition, and splitting them lets you narrow the scan or replace @EnableAutoConfiguration with @ImportAutoConfiguration.
  • What does @AutoConfigurationPackage do? It registers the base package so JPA @Entity scanning and Spring Data repositories know where to look.
C2 What happens if @EnableAutoConfiguration (or equivalent) is not specified? TCS

Without it, Spring Boot creates none of its auto-configured beans. You get no embedded Tomcat setup, no DataSource, no ObjectMapper, no DispatcherServlet and no JPA. The app still starts as a plain Spring context with only your explicit @Configuration, @Bean and scanned components. For a web app, SpringApplication.run then usually fails with errors like "Unable to start ServletWebServerApplicationContext due to missing ServletWebServerFactory bean". You would have to configure everything by hand, as in classic Spring.

Without @EnableAutoConfiguration (or @SpringBootApplication, or @ImportAutoConfiguration), AutoConfigurationImportSelector never runs, so no auto-configuration class is loaded. You still get a plain Spring ApplicationContext that contains only what you declare yourself.

What you lose:

Feature Without auto-config
Embedded Tomcat Not created.
DispatcherServlet, Jackson ObjectMapper, message converters Not registered. @RestControllers are scanned but never mapped.
DataSource, EntityManagerFactory, JpaTransactionManager, Spring Data repositories None. Injecting a repository fails with NoSuchBeanDefinitionException.
Actuator, Security filter chain, Kafka/Redis templates, @ConfigurationProperties for starters None.
Things that still work SpringApplication itself: the Environment, application.yml loading, profiles, the banner, logging setup, ApplicationRunner/CommandLineRunner, and component scanning if @ComponentScan is present. Those features come from SpringApplication, not from auto-configuration.

The typical failure with spring-boot-starter-web on the classpath:

@Configuration
@ComponentScan
public class App {               // no @EnableAutoConfiguration
    public static void main(String[] args) { SpringApplication.run(App.class, args); }
}

SpringApplication sees the Servlet API and Spring MVC on the classpath (WebApplicationType.deduceFromClasspath() returns SERVLET). It therefore creates a ServletWebServerApplicationContext, but there is no ServletWebServerFactory bean, because ServletWebServerFactoryAutoConfiguration never ran:

ApplicationContextException: Unable to start web server;
  nested exception is ... Unable to start ServletWebServerApplicationContext due to missing ServletWebServerFactory bean.

For a non-web app it simply starts with only your beans. @Autowired DataSource then fails.

Equivalents and partial options

  • @ImportAutoConfiguration({DataSourceAutoConfiguration.class, JacksonAutoConfiguration.class}) imports only the auto-configs you list. Test slices like @WebMvcTest and @DataJpaTest work this way.
  • You can configure everything manually (TomcatServletWebServerFactory, DispatcherServlet, DataSource...). This is plain Spring Framework style.

Likely follow-ups:

  • Why would you deliberately avoid full auto-config? Faster startup, a smaller memory footprint, tight control (libraries, CLI tools), or test slices.
  • Is application.yml still read without it? Yes. Config loading is done by SpringApplication/ConfigDataEnvironmentPostProcessor, not by auto-config.
  • How do you turn off just one auto-config? exclude = X.class or spring.autoconfigure.exclude.
C3 @Configuration vs @Bean; why do we need configuration classes and bean annotations?
@Configuration @Bean
Target Class Method
Purpose Marks a source of bean definitions The method's return value becomes a bean
Proxying CGLIB-proxied (proxyBeanMethods=true), so calling one @Bean method from another returns the same singleton Inside @Component ("lite mode"), inter-method calls create new instances

Why we need them: @Component only works on classes you own. @Bean lets you register third-party classes such as RestTemplate, ObjectMapper or a Kafka ProducerFactory, or beans that need custom construction logic. It also keeps wiring explicit and in one place.

@Configuration
public class AppConfig {
    @Bean
    public RestTemplate restTemplate(RestTemplateBuilder b) {
        return b.setConnectTimeout(Duration.ofSeconds(3)).build();
    }
}
  • @Bean goes on a method. Its return value is registered as a bean, named after the method by default. You use it for third-party classes you can't annotate (RestClient, ObjectMapper, KafkaTemplate) or when creation needs logic.
  • @Configuration goes on a class. It marks a source of bean definitions and is itself a @Component.

Full mode vs lite mode

@Configuration                     // proxyBeanMethods = true (default) -> FULL mode
public class AppConfig {

    @Bean
    public Clock clock() { return Clock.systemUTC(); }

    @Bean
    public TicketService ticketService() {
        return new TicketService(clock());   // intercepted: returns the SAME singleton Clock
    }

    @Bean
    public ReportService reportService() {
        return new ReportService(clock());   // same Clock instance again
    }
}

Internals: ConfigurationClassPostProcessor (a BeanFactoryPostProcessor) runs ConfigurationClassEnhancer, which replaces the bean class with a CGLIB subclass (AppConfig$$SpringCGLIB$$0). Each @Bean method is overridden by a BeanMethodInterceptor. When clock() is called, the interceptor first checks the BeanFactory: if the bean already exists, it returns it; otherwise it calls super.clock(). This keeps singleton semantics for inter-bean method calls.

Lite mode applies to @Configuration(proxyBeanMethods = false), or to @Bean methods inside a @Component or a plain class:

  • There is no CGLIB subclass, so clock() is an ordinary Java call. Each call creates a new Clock, which silently breaks singleton expectations.
  • The fix is to declare dependencies as method parameters. That works in both modes and is the recommended style:
@Configuration(proxyBeanMethods = false)
public class AppConfig {

    @Bean
    public Clock clock() { return Clock.systemUTC(); }

    @Bean
    public TicketService ticketService(Clock clock) {   // container injects the singleton
        return new TicketService(clock);
    }
}

Why Boot's own auto-configs use proxyBeanMethods = false (@AutoConfiguration sets it): there is no CGLIB class generation, so startup is faster, memory use is lower, and the code works with GraalVM native images and AOT.

Rules and gotchas

  • In full mode the @Configuration class must not be final, and @Bean methods must not be private or final, because CGLIB has to override them.
  • BeanFactoryPostProcessor beans (e.g. PropertySourcesPlaceholderConfigurer) should be declared with static @Bean methods. Otherwise the config class is instantiated too early, and its @Autowired/@Value fields stay unprocessed (Spring logs a warning).
  • @Bean(initMethod = "...", destroyMethod = "..."). For @Bean, the destroy method is inferred: a public close() or shutdown() method is called automatically. Use destroyMethod = "" to disable that.
  • @Bean can be combined with @Scope, @Lazy, @Primary, @Qualifier, @Profile, @Conditional*, @Order and @DependsOn.
  • @Import(OtherConfig.class) composes configuration classes.

Why use configuration classes at all? Wiring lives in one type-safe, refactorable, testable place: no XML, compile-time checking, and you can use conditionals and profiles. It also keeps business classes free of framework construction code.

Likely follow-ups:

  • What happens if you call a @Bean method from a @Component class? A new instance is created (lite mode). Inject the bean instead.
  • Can @Bean methods be static? Yes. That is required for BeanFactoryPostProcessors. A static method is never intercepted by CGLIB.
  • @Bean vs @Component? @Component is class-level and auto-detected by scanning. @Bean is method-level, explicit, and works for third-party types.
C4 What is a Bean? How is a Bean created internally? TCSOther rounds (Question List)

A bean is an object whose creation, wiring and lifecycle the Spring IoC container (ApplicationContext) manages. Internally:

  1. Scan/parse. Config classes and @Component classes are read into BeanDefinitions (class, scope, dependencies, init/destroy methods).
  2. BeanFactoryPostProcessors modify the definitions. For example, PropertySourcesPlaceholderConfigurer resolves ${...} placeholders.
  3. Instantiate. The constructor runs via reflection (constructor injection resolves its dependencies at this point).
  4. Populate. Field and setter injection happens.
  5. Aware callbacks, then BeanPostProcessor before-init, then init, then after-init. The after-init step is where AOP/transaction proxies are created.
  6. The bean is stored in the singleton cache and handed out on request.

A bean is an object whose creation, wiring, lifecycle and scope are managed by the Spring IoC container. Spring describes it with a BeanDefinition (the recipe), and the BeanFactory turns that recipe into an instance.

BeanDefinition: the recipe

It holds the bean class or factory method (@Bean), scope, lazy-init flag, primary flag, dependsOn, constructor arguments, property values, init and destroy method names, autowire candidate flag and role.

  • Sources: ClassPathBeanDefinitionScanner (@Component), ConfigurationClassBeanDefinitionReader (@Bean, @Import), auto-configs, and XML.
  • They are stored in a BeanDefinitionRegistry. In practice that is DefaultListableBeanFactory, which holds Map<String, BeanDefinition> beanDefinitionMap.

BeanFactory vs ApplicationContext

  • BeanFactory is the basic container: getBean, lazy by default.
  • ApplicationContext extends it and adds eager singleton pre-instantiation, automatic BPP/BFPP registration, events (ApplicationEventPublisher), i18n (MessageSource), Environment/profiles and resource loading.
  • In Boot the concrete type is AnnotationConfigServletWebServerApplicationContext (web) or AnnotationConfigApplicationContext.

AbstractApplicationContext.refresh(): the big picture

  1. prepareRefresh(), then obtainFreshBeanFactory(), then prepareBeanFactory().
  2. invokeBeanFactoryPostProcessors(): ConfigurationClassPostProcessor parses @Configuration, @ComponentScan, @Import and auto-configs and registers BeanDefinitions. BeanFactoryPostProcessors can then modify the definitions (e.g. resolve ${...} placeholders).
  3. registerBeanPostProcessors(): instantiates every BeanPostProcessor early.
  4. initMessageSource(), then initApplicationEventMulticaster().
  5. onRefresh(): Boot creates and starts the embedded web server here.
  6. registerListeners().
  7. finishBeanFactoryInitialization() → preInstantiateSingletons(): creates every non-lazy singleton.
  8. finishRefresh(): starts SmartLifecycle beans and publishes ContextRefreshedEvent. Boot later publishes ApplicationStartedEvent and ApplicationReadyEvent.

Creating one bean: getBean() → doGetBean() → createBean() → doCreateBean()

  1. Check the singleton caches (DefaultSingletonBeanRegistry, the "three-level cache"):
    • singletonObjects: fully initialised beans
    • earlySingletonObjects: early references that are not yet fully initialised
    • singletonFactories: ObjectFactorys that can produce an early reference (possibly an AOP proxy)
  2. Merge the bean definition (parent/child) and create the dependsOn beans first.
  3. resolveBeforeInstantiation: an InstantiationAwareBeanPostProcessor may short-circuit and return a proxy.
  4. Instantiate (createBeanInstance): pick a supplier, a factory method (@Bean) or a constructor (autowireConstructor resolves constructor arguments from the factory). The result is a raw object.
  5. MergedBeanDefinitionPostProcessor: AutowiredAnnotationBeanPostProcessor and CommonAnnotationBeanPostProcessor scan the class for @Autowired, @Value, @Inject, @Resource, @PostConstruct and @PreDestroy, and cache that metadata.
  6. Expose an early reference: addSingletonFactory(beanName, () -> getEarlyBeanReference(...)). This is what allows setter/field circular references.
  7. Populate properties (populateBean): InstantiationAwareBeanPostProcessor.postProcessProperties. Here AutowiredAnnotationBeanPostProcessor injects @Autowired fields and setters and @Values.
  8. Initialize (initializeBean):
    • invokeAwareMethods: BeanNameAware, BeanClassLoaderAware, BeanFactoryAware
    • BeanPostProcessor.postProcessBeforeInitialization: ApplicationContextAwareProcessor handles EnvironmentAware, ResourceLoaderAware, ApplicationEventPublisherAware, ApplicationContextAware... and CommonAnnotationBeanPostProcessor calls @PostConstruct
    • invokeInitMethods: InitializingBean.afterPropertiesSet(), then the custom initMethod
    • BeanPostProcessor.postProcessAfterInitialization: AbstractAutoProxyCreator (AnnotationAwareAspectJAutoProxyCreator) wraps the bean in a JDK dynamic proxy or CGLIB proxy when an advisor applies (@Transactional, @Async, @Cacheable, @Aspect, method security). The proxy is what gets registered and injected.
  9. registerDisposableBeanIfNecessary records destroy callbacks.
  10. The bean is put into singletonObjects.
@Component
public class SignalController implements BeanNameAware, ApplicationContextAware, InitializingBean {
    private final SignalRepository repo;              // 4. constructor injection
    @Value("${signal.max-phase:120}") private int max; // 7. populate

    public SignalController(SignalRepository repo) { this.repo = repo; }

    @Override public void setBeanName(String name) { }                        // 8a
    @Override public void setApplicationContext(ApplicationContext ctx) { }   // 8b (via BPP)
    @PostConstruct void init() { }                                            // 8b
    @Override public void afterPropertiesSet() { }                            // 8c
}

Proxy type: Spring Boot defaults to CGLIB class proxies (spring.aop.proxy-target-class=true), even when the bean implements an interface. With JDK proxies, injecting the concrete class would fail.

Likely follow-ups:

  • Why does a constructor circular dependency fail when a field one can work? An early reference is exposed only after instantiation. With constructors, neither object can be instantiated first, so you get BeanCurrentlyInCreationException.
  • BeanPostProcessor vs BeanFactoryPostProcessor? A BFPP modifies definitions before any bean exists. A BPP modifies instances around initialization.
  • When are AOP proxies created? In postProcessAfterInitialization, or earlier through getEarlyBeanReference when a circular reference needs one.
C5 Bean life cycle. Other rounds (Question List)

Instantiate → inject dependencies → BeanNameAware/BeanFactoryAware/ApplicationContextAware → BeanPostProcessor.postProcessBeforeInitialization → @PostConstruct → InitializingBean.afterPropertiesSet() → custom initMethod → postProcessAfterInitialization (proxies created here) → bean ready → on context close: @PreDestroy → DisposableBean.destroy() → destroyMethod. Note: Spring does not call destroy callbacks for prototype beans.

@Component
public class SensorClient {
    @PostConstruct void init()   { /* open connection */ }
    @PreDestroy   void close()  { /* release resources */ }
}

Full sequence for a singleton:

  1. Container starts → BeanDefinitions are loaded → BeanFactoryPostProcessors run.
  2. Instantiation: the constructor runs (constructor injection happens here).
  3. Populate properties: field and setter injection, @Value.
  4. Aware callbacks: BeanNameAware.setBeanName → BeanClassLoaderAware → BeanFactoryAware → (through BPP) EnvironmentAware, EmbeddedValueResolverAware, ResourceLoaderAware, ApplicationEventPublisherAware, MessageSourceAware, ApplicationContextAware.
  5. BeanPostProcessor.postProcessBeforeInitialization (all BPPs).
  6. @PostConstruct, which is run by CommonAnnotationBeanPostProcessor as part of step 5.
  7. InitializingBean.afterPropertiesSet().
  8. Custom init method: @Bean(initMethod = "start").
  9. BeanPostProcessor.postProcessAfterInitialization. AOP proxies are created here.
  10. After all singletons exist: SmartInitializingSingleton.afterSingletonsInstantiated() → SmartLifecycle.start() → ContextRefreshedEvent → (Boot) ApplicationStartedEvent → CommandLineRunner/ApplicationRunner → ApplicationReadyEvent.
  11. Bean in use.
  12. Shutdown (context.close() or the JVM shutdown hook that Boot registers): ContextClosedEvent → SmartLifecycle.stop() (graceful web server shutdown) → for each disposable bean, in reverse dependency order:
    • @PreDestroy
    • DisposableBean.destroy()
    • custom destroy method (@Bean(destroyMethod=...), or the inferred close()/shutdown())
package com.trinity.citypulse.sensor;

import jakarta.annotation.PostConstruct;
import jakarta.annotation.PreDestroy;
import org.springframework.beans.factory.DisposableBean;
import org.springframework.beans.factory.InitializingBean;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;

public class SensorConnectionPool implements InitializingBean, DisposableBean {

    public SensorConnectionPool() { System.out.println("1. constructor"); }

    @PostConstruct void postConstruct()            { System.out.println("2. @PostConstruct"); }
    @Override public void afterPropertiesSet()     { System.out.println("3. afterPropertiesSet"); }
    public void customInit()                       { System.out.println("4. initMethod"); }

    @PreDestroy void preDestroy()                  { System.out.println("5. @PreDestroy"); }
    @Override public void destroy()                { System.out.println("6. DisposableBean.destroy"); }
    public void customDestroy()                    { System.out.println("7. destroyMethod"); }
}

@Configuration(proxyBeanMethods = false)
class SensorConfig {
    @Bean(initMethod = "customInit", destroyMethod = "customDestroy")
    SensorConnectionPool sensorConnectionPool() { return new SensorConnectionPool(); }
}

Output order: 1 → 2 → 3 → 4 … 5 → 6 → 7.

Which one should you use?

  • Prefer @PostConstruct/@PreDestroy (jakarta.annotation.* in Boot 3). They don't couple your class to Spring.
  • InitializingBean/DisposableBean couple you to Spring and are mostly used inside the framework.
  • initMethod/destroyMethod suit third-party classes you can't annotate.

Gotchas

  • Prototype beans: Spring runs the init callbacks but never calls the destroy callbacks. The client owns the instance.
  • @PostConstruct runs on the target object, before the AOP proxy exists. Calling a @Transactional method from @PostConstruct therefore gets no transaction. Use ApplicationReadyEvent or SmartInitializingSingleton instead.
  • Don't do heavy blocking work (such as calling remote services) in @PostConstruct. It delays startup and readiness. Use ApplicationRunner or an async listener.
  • Destroy callbacks run only on a graceful shutdown (SIGTERM). They do not run on kill -9.

Likely follow-ups:

  • Where does BeanPostProcessor fit in? It wraps initialization: before-init (which includes @PostConstruct), then afterPropertiesSet/initMethod, then after-init (proxies).
  • How do you run code once the app is fully started? @EventListener(ApplicationReadyEvent.class) or ApplicationRunner.
  • Are destroy methods called for request-scoped beans? Yes, at the end of the request or session. They are not called for prototypes.

The prototype-into-singleton problem

A singleton is created once, so a prototype injected into it is also resolved once. Every call then sees the same "prototype" instance:

@Service
public class ReportService {
    private final ReportBuilder builder;          // injected once -> effectively singleton (BUG)
    public ReportService(ReportBuilder builder) { this.builder = builder; }
}

Fix 1: ObjectProvider<T> (recommended)

@Service
public class ReportService {
    private final ObjectProvider<ReportBuilder> builderProvider;
    public ReportService(ObjectProvider<ReportBuilder> builderProvider) { this.builderProvider = builderProvider; }

    public String generate() {
        ReportBuilder builder = builderProvider.getObject();   // new instance every call
        return builder.build();
    }
}

(jakarta.inject.Provider<T> works the same way. You can also inject ApplicationContext and call getBean, but that is the service-locator anti-pattern.)

Fix 2: scoped proxy

@Component
@Scope(value = ConfigurableBeanFactory.SCOPE_PROTOTYPE, proxyMode = ScopedProxyMode.TARGET_CLASS)
public class ReportBuilder { ... }

The singleton gets a CGLIB proxy, and every method call on the proxy fetches a new target. That can surprise you: builder.add(); builder.build(); uses two different instances. Scoped proxies make sense for request/session scope, but are dangerous for prototypes.

Fix 3: @Lookup method injection

@Service
public abstract class ReportService {
    public String generate() { return createBuilder().build(); }

    @Lookup
    protected abstract ReportBuilder createBuilder();   // CGLIB overrides it to call getBean()
}

(@Lookup doesn't work on beans created through @Bean factory methods.)

Request/session beans in singletons: they need a scoped proxy, which @RequestScope/@SessionScope set by default. Without one, startup fails with "Scope 'request' is not active for the current thread" because there is no request at startup time.

Gotchas

  • A singleton holding mutable fields is shared across all request threads. That causes race conditions.
  • Request scope doesn't propagate to @Async threads or CompletableFutures.
  • A prototype bean that depends on a singleton is fine. The problem only goes the other way.

Likely follow-ups:

  • Is a Spring singleton the same as the GoF Singleton? No. It is one instance per container and bean id. You can define two beans of the same class.
  • Who destroys prototype beans? You do. Spring doesn't track them.
  • How is request scope implemented? RequestContextHolder holds request attributes in a ThreadLocal (set by RequestContextFilter/DispatcherServlet), and the scoped bean is stored as a request attribute.
C7 @Lazy. Co. 2

By default, singletons are created eagerly at startup, which makes misconfiguration fail fast. @Lazy delays creation until the bean is first requested. Uses:

  • Heavy beans that are rarely needed.
  • Breaking circular dependencies: @Lazy on the injection point injects a proxy.
  • Faster startup. Globally: spring.main.lazy-initialization=true.

Trade-off: errors show up at runtime instead of at startup, and the first request is slower.

public ReportService(@Lazy PdfEngine engine) { this.engine = engine; }

By default the ApplicationContext eagerly creates all singletons during refresh(). That gives fail-fast startup. @Lazy delays creation until first use.

1. On a bean definition

@Component
@Lazy
public class HeavyGisIndexLoader { ... }  // created on first getBean/injection use

@Configuration
@Lazy                                       // applies to ALL @Bean methods in this class
class ReportingConfig { ... }

Gotcha: if an eager singleton injects a lazy bean normally, the lazy bean is created right away anyway, because the eager bean needs it. So @Lazy on the class alone often has no effect.

2. On an injection point

@Service
public class AlertService {
    private final SmsGateway smsGateway;
    public AlertService(@Lazy SmsGateway smsGateway) {   // gets a lazy-resolution PROXY
        this.smsGateway = smsGateway;                    // real bean resolved on first method call

}

ContextAnnotationAutowireCandidateResolver builds a proxy whose methods call beanFactory.doResolveDependency(...) when first invoked. This is also a common way to break circular dependencies.

3. Global lazy initialization

spring:
  main:
    lazy-initialization: true

Every bean becomes lazy. Opt specific beans out with @Lazy(false).

Trade-offs

Pros Cons
Faster startup (dev, tests, serverless) Misconfiguration surfaces at runtime on the first request, not at startup

Likely follow-ups:

  • Does @Lazy work on prototypes? It isn't needed. Prototypes are always created on demand.
  • How do you lazily get a bean without a proxy? Use ObjectProvider<T>.getIfAvailable()/getObject().

C8 @Component; component scanning. Co. 2

@Component marks a class as a Spring-managed bean. It has these stereotypes:

  • @Service (business layer).
  • @Repository (DAO layer; adds exception translation to DataAccessException).
  • @Controller/@RestController (web layer).
  • @Configuration.

Component scanning (@ComponentScan, included in @SpringBootApplication) searches the main class's package and its sub-packages for these annotations and registers them. Classes outside that tree need @ComponentScan(basePackages = "com.trinity.common") or @Import. You can also add includeFilters and excludeFilters.

@Component marks a class for auto-detection by classpath scanning. The stereotypes are @Component specialisations that also carry meaning:

Annotation Layer Extra behaviour
@Component generic none
@Service business logic none (semantic only; a natural pointcut target)
@Repository persistence Exception translation: PersistenceExceptionTranslationPostProcessor proxies the bean and turns vendor exceptions (SQLException, Hibernate exceptions) into Spring's DataAccessException hierarchy

@Retention(RetentionPolicy.RUNTIME)
@Service
public @interface UseCase { }

How scanning works

@ComponentScan is processed by ComponentScanAnnotationParser, which uses ClassPathBeanDefinitionScanner:

  1. It resolves classpath*:com/trinity/citypulse/**/*.class.
  2. It reads each class with ASM metadata readers (MetadataReader), so classes are not loaded just to be checked.
  3. It applies include and exclude filters. The default include filter is "annotated with @Component, including through meta-annotations, plus jakarta.inject.Named/ManagedBean".
  4. It evaluates @Conditional/@Profile.
  5. It generates bean names with AnnotationBeanNameGenerator: the simple class name with a lowercase first letter (trafficService), or the value you give (@Service("tsvc")).
  6. It registers a ScannedGenericBeanDefinition.
@SpringBootApplication(scanBasePackages = {"com.trinity.citypulse", "com.trinity.common"})
public class CityPulseApplication { ... }

    basePackageClasses = MarkerForAlertsPackage.class,          // type-safe alternative to strings
    useDefaultFilters = true,

    excludeFilters = {

Gotchas

  • Two classes with the same simple name in different packages (e.g. com.a.UserMapper and com.b.UserMapper) both default to the bean name userMapper. The result is ConflictingBeanDefinitionException at startup. Give them explicit names.
  • A class outside the base package is silently not found, so injection fails with NoSuchBeanDefinitionException.
  • @Component on an abstract class or interface does nothing (Spring Data repositories use their own scanning).
  • The spring-context-indexer (META-INF/spring.components) was deprecated in Spring 6.1. AOT is the modern answer to startup speed.

Likely follow-ups:

  • Is @Service functionally different from @Component? No. It is semantic only. @Repository does add exception translation.
  • How do you exclude a class from scanning in a test? @ComponentScan exclude filters, @TestConfiguration (excluded by TypeExcludeFilter), or use a test slice.
  • How do you register a bean without scanning? @Bean, @Import, or GenericApplicationContext.registerBean(...).
C9 Dependency injection in Spring Boot; types of DI. G2

DI means the container supplies an object's dependencies, so the object does not create them itself (loose coupling, easier testing).

Type How Verdict
Constructor Dependencies passed via constructor (@Autowired optional when there is a single constructor) Preferred
Setter @Autowired on a setter Use for optional or changeable dependencies
Field @Autowired on a field Avoid: hides dependencies, cannot be final, harder to unit test

Constructor injection is preferred because:

  • Fields can be final, so the object is immutable.
  • Dependencies are mandatory and visible.
  • You can unit test with new and no Spring.
  • Circular dependencies fail at startup.
@Service
@RequiredArgsConstructor // Lombok generates the constructor
public class EmployeeService {
    private final EmployeeRepository repo;
}

Dependency Injection (DI) is a form of Inversion of Control. An object declares what it needs, and the container supplies it. The object doesn't construct or look up its dependencies (new, or a service locator). The benefits are loose coupling, easier testing (pass mocks in), and centralised wiring.

1. Constructor injection (preferred)

@Service
public class ChallanService {
    private final VehicleRepository vehicleRepository;
    private final NotificationClient notificationClient;

    // Single constructor -> @Autowired optional (since Spring 4.3)
    public ChallanService(VehicleRepository vehicleRepository, NotificationClient notificationClient) {
        this.vehicleRepository = vehicleRepository;
        this.notificationClient = notificationClient;
    }
}

(With Lombok, @RequiredArgsConstructor on final fields generates this constructor.)

2. Setter injection (optional dependencies)

@Autowired(required = false)
public void setMetricsPublisher(MetricsPublisher metricsPublisher) { this.metricsPublisher = metricsPublisher; }

3. Field injection (discouraged)

@Autowired private VehicleRepository vehicleRepository;

Why constructor injection is preferred

Concern Constructor Field
Immutability (final) yes no
Object is never half-built guaranteed not guaranteed: can be used with nulls
Unit test without Spring new ChallanService(mockRepo, mockClient) needs reflection or @InjectMocks
Hidden dependencies explicit; a long parameter list signals an SRP violation hidden; easy to keep adding
Circular dependency detected at startup (fail-fast) silently allowed (if enabled)
Framework coupling none (plain Java) needs @Autowired/reflection

Other injection styles: @Value for config values, @Resource (JSR-250, by name first), @Inject (JSR-330, by type), method/@Bean parameter injection, and ObjectProvider<T> for optional or lazy dependencies.

How resolution works: AutowiredAnnotationBeanPostProcessor → DefaultListableBeanFactory.resolveDependency() → doResolveDependency(). It finds candidates by type. If there are several, it narrows by @Qualifier, then @Primary, then @Priority, then parameter or field name (C10). Optional<T>, ObjectProvider<T>, List<T> and Map<String,T> are handled specially.

Circular dependencies

A → B → A.

  • Constructor cycle: never resolvable. It fails with BeanCurrentlyInCreationException: Requested bean is currently in creation: Is there an unresolvable circular reference?
  • Field/setter cycle: technically resolvable through the early-reference cache (C4). However, Spring Boot 2.6+ forbids it by default. Startup fails with "The dependencies of some of the beans in the application context form a cycle", and spring.main.allow-circular-references=true re-enables it (not recommended).

Fixes, best first:

  1. Redesign: pull the shared logic into a third bean C that both A and B depend on.
  2. Use events (ApplicationEventPublisher) to decouple the callback direction.
  3. Use @Lazy on one injection point: a proxy breaks the cycle at construction time.
  4. Use ObjectProvider<B> and resolve when needed.
  5. Use setter injection plus allow-circular-references (last resort).

Likely follow-ups:

  • Why does @InjectMocks work with field injection? Mockito uses reflection. That's exactly why field injection hides dependencies.
  • How do you inject an optional dependency? ObjectProvider<T>.getIfAvailable(), Optional<T>, or @Autowired(required = false).
  • @Autowired vs @Resource vs @Inject? @Autowired/@Inject resolve by type then qualifier. @Resource resolves by name first. Only @Autowired has required.
C10 Multiple beans of the same type: how to specify which one? TCSCo. 2

If two beans match one injection point, Spring throws NoUniqueBeanDefinitionException. Options:

  • @Primary: the default choice when there is no qualifier.
  • @Qualifier("beanName"): an explicit choice that overrides @Primary. This is how you use the non-primary bean.
  • By name: if the parameter or field name matches the bean name, Spring uses it as a fallback.
  • All of them: inject List<NotificationSender> or Map<String, NotificationSender> (key = bean name) and choose at runtime (strategy pattern).
  • Three beans, want only one registered: make the others conditional with @Profile, @ConditionalOnProperty, or by excluding them from the scan.
public interface NotificationSender { void send(String msg); }
@Component("sms")  @Primary class SmsSender   implements NotificationSender { public void send(String m) {} }
@Component("email")         class EmailSender implements NotificationSender { public void send(String m) {} }
@Component("push")          class PushSender  implements NotificationSender { public void send(String m) {} }

@Service
class AlertService {
    private final NotificationSender defaultSender;   // gets sms (@Primary)
    private final NotificationSender emailSender;
    AlertService(NotificationSender defaultSender,
                 @Qualifier("email") NotificationSender emailSender) {
        this.defaultSender = defaultSender; this.emailSender = emailSender;
    }
}

Two beans with the same name: Spring Boot disables overriding by default, so startup fails with BeanDefinitionOverrideException. To fix it, rename one with @Bean("smsSenderV2") or @Component("smsV2"). You can also set spring.main.allow-bean-definition-overriding=true, where the last definition wins, but that is not recommended because it hides bugs.

public interface NotificationSender { void send(String to, String msg); }

@Component("smsSender")   public class SmsSender   implements NotificationSender { ... }
@Component("emailSender") public class EmailSender implements NotificationSender { ... }
@Component("pushSender")  public class PushSender  implements NotificationSender { ... }

Injecting NotificationSender alone fails: NoUniqueBeanDefinitionException: expected single matching bean but found 3: smsSender,emailSender,pushSender.

How Spring narrows candidates (DefaultListableBeanFactory.determineAutowireCandidate):

  1. Match by type, then filter by @Qualifier if one is present at the injection point.
  2. If still more than one: the @Primary bean.
  3. Otherwise the highest @Priority (jakarta).
  4. Otherwise the bean whose name equals the field or parameter name. This "fallback qualifier" depends on the -parameters compiler flag for constructor parameters; the Boot Maven/Gradle plugins set it.
  5. Otherwise NoUniqueBeanDefinitionException.

(Spring 6.2 adds @Fallback, the inverse of @Primary: such a bean is used only if no other candidate remains.)

1. @Qualifier: pick one explicitly

@Service
public class AlertService {
    private final NotificationSender sender;
    public AlertService(@Qualifier("smsSender") NotificationSender sender) { this.sender = sender; }
}

2. @Primary: the default choice

@Component("emailSender")
@Primary
public class EmailSender implements NotificationSender { ... }

3. Injection by name: the parameter name matches the bean name.

public AlertService(NotificationSender pushSender) { ... }   // resolves pushSender

This is fragile (refactoring the name breaks it) and @Primary overrides it. Prefer @Qualifier.

4. Inject all of them: List or Map

@Service
public class BroadcastService {
    private final List<NotificationSender> senders;            // ordered by @Order / Ordered
    private final Map<String, NotificationSender> sendersByName; // key = bean name

    public BroadcastService(List<NotificationSender> senders, Map<String, NotificationSender> sendersByName) {
        this.senders = senders;
        this.sendersByName = sendersByName;
    }

    public void broadcast(String to, String msg) { senders.forEach(s -> s.send(to, msg)); }

    public void sendVia(String channel, String to, String msg) {        // strategy pattern
        NotificationSender s = sendersByName.get(channel + "Sender");
        if (s == null) throw new IllegalArgumentException("Unknown channel " + channel);
        s.send(to, msg);
    }
}

"There are three beans and I want only one": use @Qualifier at the injection point, or mark one @Primary. If you don't want the other two at all, don't create them: @ConditionalOnProperty(name="notify.channel", havingValue="sms"), @Profile, or a scan exclude filter.

"@Primary exists but I need a different one": @Qualifier takes precedence over @Primary, so @Qualifier("smsSender") gets SMS even though Email is primary. You can also define custom qualifier annotations:

@Target({ElementType.FIELD, ElementType.PARAMETER, ElementType.TYPE, ElementType.METHOD})
@Retention(RetentionPolicy.RUNTIME)
@Qualifier
public @interface Sms { }

@Component @Sms public class SmsSender implements NotificationSender { ... }
public AlertService(@Sms NotificationSender sender) { ... }

"Two beans with the same name"

  • Spring Boot 2.1+ disables bean definition overriding by default. Two @Bean methods (or a @Bean plus a scanned component) with the same name fail with: BeanDefinitionOverrideException: Invalid bean definition with name 'dataSource' defined in class path resource [...]: Cannot register bean definition ... since there is already [...] bound.
  • Re-enable with:
    spring:
  main:
    allow-bean-definition-overriding: true   # last one registered wins - hides bugs, avoid
  • Plain Spring Framework (without Boot) allows overriding by default and logs it.
  • Two scanned classes with the same default name fail with ConflictingBeanDefinitionException. The fix is the same: give them explicit unique names.
  • In tests, prefer @MockitoBean/@TestConfiguration with @Primary over overriding.

Likely follow-ups:

  • How do you order List injection? @Order(1) or Ordered on the beans. Note that @Order does not affect single-bean selection.
  • What does ObjectProvider give you here? orderedStream(), getIfUnique(), and lazy, optional resolution.
  • @Primary on two beans? NoUniqueBeanDefinitionException again ("more than one 'primary' bean found").

What it is
JPA (Jakarta Persistence) A specification: annotations (@Entity, @Id), EntityManager and JPQL. It contains no implementation.
Hibernate The most popular JPA implementation (ORM provider), plus its own extras (Session, Envers, caching).

Request flow: your code calls Spring Data's JpaRepository, which uses JPA's EntityManager, which Hibernate implements, which uses JDBC to talk to the DB.

JPA (Jakarta Persistence) Hibernate Spring Data JPA
What Specification (interfaces and annotations), jakarta.persistence.* Implementation of JPA (the ORM provider), plus extra native features Abstraction on top of JPA: repositories and query derivation

The layers: Your code → Spring Data repository proxy (SimpleJpaRepository) → JPA EntityManager → Hibernate Session → JDBC → DB.

Spring Data creates a JDK proxy for each repository interface. A call like findByVehicleNumberAndStatus is parsed by PartTree into JPQL at startup, so a bad method name fails fast. CRUD methods delegate to SimpleJpaRepository, which is @Transactional(readOnly = true) at class level, with @Transactional on its write methods.

Persistence context

A persistence context is the set of managed entity instances tied to an EntityManager. In Spring it is scoped to the transaction by default. Spring injects a shared, thread-safe EntityManager proxy that routes to the transaction-bound one.

  • First-level cache / identity map: find(Employee.class, 1L) twice in one transaction returns the same instance with one SQL query.
  • Dirty checking: at flush, Hibernate compares managed entities against their loaded snapshot and issues UPDATEs automatically. You don't need save() for managed entities.
  • Write-behind: SQL is queued and flushed at commit, before a query that touches affected tables (FlushModeType.AUTO), or on an explicit flush().

Entity states

          new Employee()                       persist()/save()
 [TRANSIENT/NEW] ---------------------------------> [MANAGED]
                                                     |   ^
                       tx commit / clear() / close() |   | merge()  (returns a NEW managed copy)
                                                     v   |
                                                  [DETACHED]
 [MANAGED] -- remove() --> [REMOVED] -- flush/commit --> DELETE (then effectively transient)
  • Transient: has no id and isn't tracked.
  • Managed: in the persistence context; changes are auto-flushed.
  • Detached: has an id but the persistence context is closed, so changes are not tracked. A typical example is an entity returned from a service after the transaction ended.
  • Removed: scheduled for deletion.

persist() makes the same instance managed. merge() copies state onto a managed instance and returns that instance; the argument stays detached. Spring Data's save() calls persist if entityInformation.isNew(entity) (the id is null, or @Version is null, or Persistable.isNew()), and merge otherwise.

Gotcha: if you assign ids manually (e.g. a UUID set in the constructor), save() thinks the entity isn't new. It calls merge, which costs an extra SELECT. Implement Persistable<ID> or use @Version to fix that.

Likely follow-ups:

  • Is EntityManager thread-safe? The real one isn't. Spring's injected shared proxy is, because it binds a real one per transaction/thread.
  • What is the 2nd-level cache? A Hibernate SessionFactory-level cache shared across sessions (Ehcache/JCache/Infinispan). It is opt-in, using @Cacheable plus @org.hibernate.annotations.Cache.
  • Do you need repo.save() after modifying a managed entity? No. Dirty checking flushes it at commit.

Gotchas

  • If the sequence's INCREMENT BY doesn't match allocationSize, you get duplicate-key errors, or Hibernate 6 fails schema validation. Keep them aligned (Flyway: INCREMENT BY 50).
  • Gaps in ids are normal: allocated blocks are lost on restart. Never use ids as business-visible sequential numbers such as challan numbers. Use a separate generator for those.
  • Random UUIDv4 primary keys cause B-tree index fragmentation (random inserts). Prefer time-ordered UUIDv7 or Style.TIME, or a Long PK with a UUID public id.
  • On MySQL, prefer IDENTITY over the TABLE strategy, and accept that inserts aren't batched (or use a UUID).

Likely follow-ups:

  • What does allocationSize = 50 mean? One sequence call reserves 50 ids, which Hibernate hands out in memory.
  • Which would you pick for Postgres? SEQUENCE with a pooled allocation size.

@Controller vs @RestController

  • @Controller: return values are view names resolved by a ViewResolver (Thymeleaf/JSP). Add @ResponseBody per method to write the return value to the body.
  • @RestController = @Controller + @ResponseBody on every method. The return value goes through HttpMessageConverters (Jackson for JSON).
@RestController
@RequestMapping(path = "/api/v1/vehicles", produces = MediaType.APPLICATION_JSON_VALUE)
public class VehicleController {

    private final VehicleService service;
    public VehicleController(VehicleService service) { this.service = service; }

    @GetMapping("/{id}")
    public ResponseEntity<VehicleDto> get(@PathVariable Long id) {
        return ResponseEntity.ok()
                .cacheControl(CacheControl.maxAge(Duration.ofSeconds(30)))
                .eTag("\"" + service.version(id) + "\"")
                .body(service.get(id));
    }

    @PostMapping(consumes = MediaType.APPLICATION_JSON_VALUE)
    public ResponseEntity<VehicleDto> create(@Valid @RequestBody CreateVehicleRequest req,
                                             UriComponentsBuilder uriBuilder) {
        VehicleDto dto = service.create(req);
        URI location = uriBuilder.path("/api/v1/vehicles/{id}").buildAndExpand(dto.id()).toUri();
        return ResponseEntity.created(location).body(dto);         // 201 + Location
    }

    @DeleteMapping("/{id}")
    @ResponseStatus(HttpStatus.NO_CONTENT)                          // alternative to ResponseEntity
    public void delete(@PathVariable Long id) { service.delete(id); }
}

ResponseEntity<T> gives full control over the status, headers and body: ok(), created(uri), accepted(), noContent(), notFound(), badRequest(), status(HttpStatus.CONFLICT). Returning a plain DTO gives 200 (or the @ResponseStatus value).

Content negotiation

The ContentNegotiationManager determines the requested media types:

  1. the Accept header (default strategy);
  2. optionally a query parameter (?format=xml) via spring.mvc.contentnegotiation.favor-parameter=true;
  3. path extensions (.json). This is disabled by default since Spring 5.3 and removed from suffix pattern matching in 6.

Then AbstractMessageConverterMethodProcessor intersects the requested types with the produces types and the types the registered converters can write, and picks the best match. If nothing matches, the client gets 406 Not Acceptable (HttpMediaTypeNotAcceptableException). On the request side, consumes mismatches give 415.

To support XML, add jackson-dataformat-xml. Boot then auto-registers MappingJackson2XmlHttpMessageConverter, and Accept: application/xml works.

@GetMapping(value = "/{id}", produces = { MediaType.APPLICATION_JSON_VALUE, MediaType.APPLICATION_XML_VALUE })
public VehicleDto getNegotiated(@PathVariable Long id) { return service.get(id); }

REST design checklist: plural nouns (/vehicles), HTTP verbs for actions, proper status codes, versioning (/api/v1 or a header; Spring 7 adds first-class API versioning), pagination (Pageable with page/size/sort), idempotency keys for POST, HATEOAS only if needed, OpenAPI docs via springdoc.

Likely follow-ups:

  • What happens if a @RestController method returns null? An empty body with 200. Prefer 404 or 204 explicitly.
  • How does Jackson get configured? JacksonAutoConfiguration provides an ObjectMapper (customise it with spring.jackson.* or a Jackson2ObjectMapperBuilderCustomizer).
  • ResponseEntity vs @ResponseStatus? ResponseEntity is dynamic per request (headers, status). @ResponseStatus is static.

PATCH option 2: JSON Merge Patch (RFC 7396) with Jackson Rules: fields present overwrite, null removes or clears the field, absent fields are untouched, and arrays are replaced wholesale.

package com.trinity.hr.employee;

import com.fasterxml.jackson.databind.JsonNode;
import com.fasterxml.jackson.databind.ObjectMapper;
import jakarta.validation.ConstraintViolationException;
import jakarta.validation.Validator;
import org.springframework.web.bind.annotation.*;

import java.io.IOException;

@RestController
@RequestMapping("/api/v1/employees")
public class EmployeePatchController {

    private final EmployeeService service;
    private final ObjectMapper objectMapper;
    private final Validator validator;

    public EmployeePatchController(EmployeeService service, ObjectMapper objectMapper, Validator validator) {
        this.service = service; this.objectMapper = objectMapper; this.validator = validator;
    }

    @PatchMapping(path = "/{id}", consumes = "application/merge-patch+json")
    public EmployeeDto mergePatch(@PathVariable Long id, @RequestBody JsonNode patch) throws IOException {
        EmployeeUpdateRequest current = service.getForUpdate(id);                 // current state as DTO
        EmployeeUpdateRequest patched = objectMapper.readerForUpdating(current)  // apply only present fields
                .readValue(patch);
        var violations = validator.validate(patched);                             // validate the RESULT
        if (!violations.isEmpty()) throw new ConstraintViolationException(violations);
        return service.replace(id, patched);
    }
}

Note: readerForUpdating works on mutable objects (POJOs with setters). Records are immutable, so with record DTOs, merge at the JsonNode level instead: ObjectNode base = objectMapper.valueToTree(current); merge(base, patch); objectMapper.treeToValue(base, Dto.class).

JSON Patch (RFC 6902) is an array of operations:

[ { "op": "replace", "path": "/department", "value": "Traffic" },
  { "op": "remove",  "path": "/phone" } ]

Libraries: com.github.java-json-tools:json-patch, or jakarta.json.JsonPatch.

Concurrency: both PUT and PATCH should use optimistic locking. The client sends If-Match: "<version>" (ETag), and the server returns 412 Precondition Failed on a mismatch, or 409 when @Version throws ObjectOptimisticLockingFailureException.

Likely follow-ups:

  • Is PATCH ever idempotent? It can be, for example merge patch with absolute values, but the spec doesn't require it.
  • Why validate after patching? Each field may be valid on its own while the merged object isn't. Validate the final state.
  • Which status should PUT/PATCH return? 200 with the updated body, or 204 with no body. PUT that creates returns 201.

  • CORS preflight OPTIONS responses (often 204).

202 Accepted Accepted for async processing, not done yet Often a status URL Bulk import, report generation through Kafka

Debated cases

  • 204 vs 202 for async? 202 means "accepted, not done". 204 means "done, nothing to return".
  • What does a browser do with 204 on a form submit? It stays on the current page.

C19 Front Controller design pattern (DispatcherServlet).

A single entry point handles every request and delegates it to the right handler. Cross-cutting concerns (routing, security, i18n, error handling) therefore live in one place. In Spring MVC, that entry point is the DispatcherServlet:

  1. A request arrives at DispatcherServlet.
  2. HandlerMapping finds the controller method.
  3. HandlerAdapter invokes it, using argument resolvers for @PathVariable, @RequestBody and so on.
  4. The return value is written by an HttpMessageConverter (Jackson to JSON) or resolved by a ViewResolver.
  5. Exceptions go to a HandlerExceptionResolver (@ControllerAdvice).
  6. The response is sent.

Spring Boot auto-registers DispatcherServlet at /.

import org.springframework.web.servlet.config.annotation.InterceptorRegistry;
import org.springframework.web.servlet.config.annotation.WebMvcConfigurer;

import java.util.UUID;

class CorrelationIdInterceptor implements HandlerInterceptor {
    @Override
    public boolean preHandle(HttpServletRequest req, HttpServletResponse res, Object handler) {
        String cid = req.getHeader("X-Correlation-Id");
        if (cid == null) cid = UUID.randomUUID().toString();
        MDC.put("correlationId", cid);
        res.setHeader("X-Correlation-Id", cid);
        req.setAttribute("startNanos", System.nanoTime());
        return true;
    }

    @Override
    public void afterCompletion(HttpServletRequest req, HttpServletResponse res, Object handler, Exception ex) {
        MDC.remove("correlationId");
    }
}

@Configuration

    @Override

        registry.addInterceptor(new CorrelationIdInterceptor())
                .addPathPatterns("/api/**")
                .excludePathPatterns("/api/public/**");
    }
}

C20 Exception handling in Spring Boot. Co. 2G2
  • @ExceptionHandler works for one controller only.
  • @RestControllerAdvice (= @ControllerAdvice + @ResponseBody) is global, so you get a consistent error format.
  • Throw a custom exception from the service layer and map it to a status in the advice.
  • Spring 6 adds ProblemDetail (RFC 7807/9457, application/problem+json). Enable it for framework exceptions with spring.mvc.problemdetails.enabled=true.
@RestControllerAdvice
public class GlobalExceptionHandler {

    @ExceptionHandler(ResourceNotFoundException.class)
    public ProblemDetail handleNotFound(ResourceNotFoundException ex) {
        ProblemDetail pd = ProblemDetail.forStatusAndDetail(HttpStatus.NOT_FOUND, ex.getMessage());
        pd.setTitle("Resource Not Found");
        return pd;
    }

    @ExceptionHandler(MethodArgumentNotValidException.class)
    public ProblemDetail handleValidation(MethodArgumentNotValidException ex) {
        ProblemDetail pd = ProblemDetail.forStatus(HttpStatus.BAD_REQUEST);
        pd.setProperty("errors", ex.getBindingResult().getFieldErrors().stream()
                .collect(Collectors.toMap(FieldError::getField,
                        fe -> String.valueOf(fe.getDefaultMessage()), (a, b) -> a)));
        return pd;
    }

    @ExceptionHandler(Exception.class)
    public ProblemDetail handleGeneric(Exception ex) {
        return ProblemDetail.forStatusAndDetail(HttpStatus.INTERNAL_SERVER_ERROR, "Unexpected error");
    }
}

Alternatives are @ResponseStatus on the exception class, or throw new ResponseStatusException(HttpStatus.NOT_FOUND).

Options, from local to global

  1. try/catch in the controller (avoid, because it scatters logic).
  2. @ExceptionHandler methods inside one controller, which apply only to that controller.
  3. @RestControllerAdvice (= @ControllerAdvice + @ResponseBody): global handlers. Scope them with basePackages, assignableTypes or annotations, and order several advices with @Order.
  4. @ResponseStatus on a custom exception class: maps it to a status, with no body control.
  5. ResponseStatusException: throw it with a status and reason directly (throw new ResponseStatusException(HttpStatus.NOT_FOUND, "Junction not found")). Good for quick cases.
  6. ErrorController/BasicErrorController at /error: the fallback for anything not handled, including filter errors.

Resolution internals: ExceptionHandlerExceptionResolver looks first at @ExceptionHandler methods in the controller, then in the advices. It picks the closest match in the exception hierarchy (ExceptionDepthComparator). It also matches causes for wrapped exceptions.

ProblemDetail (RFC 7807, now RFC 9457): Spring 6 supports it natively. ProblemDetail, ErrorResponse and ErrorResponseException produce application/problem+json.

  • spring.mvc.problemdetails.enabled=true makes Boot register a ResponseEntityExceptionHandler advice that renders Spring MVC's built-in exceptions (400/404/405/415...) as ProblemDetail.
  • To customise, extend ResponseEntityExceptionHandler yourself:
package com.trinity.citypulse.web;

import jakarta.validation.ConstraintViolationException;
import org.springframework.dao.DataIntegrityViolationException;
import org.springframework.http.*;
import org.springframework.lang.NonNull;
import org.springframework.orm.ObjectOptimisticLockingFailureException;
import org.springframework.web.bind.MethodArgumentNotValidException;
import org.springframework.web.bind.annotation.ExceptionHandler;
import org.springframework.web.bind.annotation.RestControllerAdvice;
import org.springframework.web.context.request.WebRequest;
import org.springframework.web.servlet.mvc.method.annotation.ResponseEntityExceptionHandler;

import java.util.List;
import java.util.Map;

@RestControllerAdvice
public class ApiExceptionHandler extends ResponseEntityExceptionHandler {

    // validation of @Valid @RequestBody -> 400 with field errors
    @Override
    protected ResponseEntity<Object> handleMethodArgumentNotValid(@NonNull MethodArgumentNotValidException ex,
            @NonNull HttpHeaders headers, @NonNull HttpStatusCode status, @NonNull WebRequest request) {
        ProblemDetail pd = ex.getBody();                         // already a ProblemDetail
        pd.setTitle("Validation failed");
        List<Map<String, Object>> errors = ex.getBindingResult().getFieldErrors().stream()
                .map(fe -> Map.<String, Object>of(
                        "field", fe.getField(),
                        "message", String.valueOf(fe.getDefaultMessage()),
                        "rejected", String.valueOf(fe.getRejectedValue())))
                .toList();
        pd.setProperty("errors", errors);
        return ResponseEntity.status(status).headers(headers).body(pd);
    }

    @ExceptionHandler(ResourceNotFoundException.class)
    ProblemDetail notFound(ResourceNotFoundException ex) {
        return ProblemDetail.forStatusAndDetail(HttpStatus.NOT_FOUND, ex.getMessage());
    }

    @ExceptionHandler(ConstraintViolationException.class)        // @Validated method-level (service layer)
    ProblemDetail constraint(ConstraintViolationException ex) {
        ProblemDetail pd = ProblemDetail.forStatusAndDetail(HttpStatus.BAD_REQUEST, "Constraint violation");
        pd.setProperty("violations", ex.getConstraintViolations().stream()
                .map(v -> v.getPropertyPath() + ": " + v.getMessage()).toList());
        return pd;
    }

    @ExceptionHandler(DataIntegrityViolationException.class)
    ProblemDetail conflict(DataIntegrityViolationException ex) {
        return ProblemDetail.forStatusAndDetail(HttpStatus.CONFLICT, "Duplicate or invalid reference");
    }

    @ExceptionHandler(ObjectOptimisticLockingFailureException.class)
    ProblemDetail optimistic(ObjectOptimisticLockingFailureException ex) {
        return ProblemDetail.forStatusAndDetail(HttpStatus.CONFLICT, "Resource was modified by another user");
    }

    @ExceptionHandler(Exception.class)
    ProblemDetail fallback(Exception ex) {
        logger.error("Unhandled", ex);                            // never leak stack traces to clients
        return ProblemDetail.forStatusAndDetail(HttpStatus.INTERNAL_SERVER_ERROR, "Internal error");
    }
}

Exceptions not caught by @ControllerAdvice

  • Exceptions thrown in servlet filters, including Spring Security's filter chain, happen before DispatcherServlet. The advice never sees them, and they go to the container's /error (BasicErrorController).
  • For Security: implement AuthenticationEntryPoint (401) and AccessDeniedHandler (403).
  • For custom filters: catch the exception in the filter and either write the response directly, or delegate to the MVC resolvers:
import jakarta.servlet.FilterChain;
import jakarta.servlet.ServletException;
import jakarta.servlet.http.HttpServletRequest;
import jakarta.servlet.http.HttpServletResponse;
import org.springframework.beans.factory.annotation.Qualifier;
import org.springframework.stereotype.Component;
import org.springframework.web.filter.OncePerRequestFilter;
import org.springframework.web.servlet.HandlerExceptionResolver;

import java.io.IOException;

@Component
public class TenantFilter extends OncePerRequestFilter {
    private final HandlerExceptionResolver resolver;

    public TenantFilter(@Qualifier("handlerExceptionResolver") HandlerExceptionResolver resolver) {
        this.resolver = resolver;
    }

    @Override
    protected void doFilterInternal(HttpServletRequest req, HttpServletResponse res, FilterChain chain)
            throws ServletException, IOException {
        try {
            if (req.getHeader("X-Tenant-Id") == null) throw new MissingTenantException();
            chain.doFilter(req, res);
        } catch (MissingTenantException ex) {
            resolver.resolveException(req, res, null, ex);   // routes to @RestControllerAdvice
        }
    }
}
  • Other cases the advice doesn't cover: exceptions in @Async methods (use an AsyncUncaughtExceptionHandler), @Scheduled jobs, Kafka listeners (DefaultErrorHandler/DLT), and errors after the response is already committed.

C23 SessionFactory: what it is and how to configure it.

SessionFactory is Hibernate's heavyweight, thread-safe, one-per-database factory that creates Session objects. A Session is lightweight and not thread-safe, and you use one per unit of work. The factory holds the mapping metadata, the connection provider and the second-level cache. The JPA equivalent is EntityManagerFactory → EntityManager.

In plain Hibernate you build it with new Configuration().configure("hibernate.cfg.xml").buildSessionFactory(). In Spring Boot you do not configure it. Boot auto-configures an EntityManagerFactory (Hibernate's SessionFactoryImpl implements it) from spring.datasource.* and spring.jpa.*. If you need native Hibernate APIs, unwrap it:

@Bean
public SessionFactory sessionFactory(EntityManagerFactory emf) {
    return emf.unwrap(SessionFactory.class);
}
// or per-operation: Session session = entityManager.unwrap(Session.class);

SessionFactory (Hibernate native API):

  • It is a heavyweight, thread-safe, immutable factory, created once per database at startup. It holds the compiled mappings, metadata, the connection provider, the 2nd-level cache and the statistics.
  • It produces Sessions, which are lightweight, not thread-safe, and one per unit of work or transaction. Each Session wraps the persistence context (first-level cache).
  • JPA equivalents: SessionFactory ↔ EntityManagerFactory, and Session ↔ EntityManager. Since Hibernate 5.2, SessionFactory extends EntityManagerFactory and Session extends EntityManager.

Plain Spring (no Boot): LocalSessionFactoryBean

package com.trinity.legacy.config;

import com.zaxxer.hikari.HikariDataSource;
import org.hibernate.SessionFactory;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.orm.hibernate5.HibernateTransactionManager;
import org.springframework.orm.hibernate5.LocalSessionFactoryBean;
import org.springframework.transaction.annotation.EnableTransactionManagement;

import javax.sql.DataSource;
import java.util.Properties;

@Configuration
@EnableTransactionManagement
public class HibernateConfig {

    @Bean
    public DataSource dataSource() {
        HikariDataSource ds = new HikariDataSource();
        ds.setJdbcUrl("jdbc:postgresql://localhost:5432/citypulse");
        ds.setUsername("app");
        ds.setPassword(System.getenv("DB_PASSWORD"));
        return ds;
    }

    @Bean
    public LocalSessionFactoryBean sessionFactory(DataSource dataSource) {
        LocalSessionFactoryBean sf = new LocalSessionFactoryBean();
        sf.setDataSource(dataSource);
        sf.setPackagesToScan("com.trinity.legacy.domain");
        Properties props = new Properties();
        props.put("hibernate.hbm2ddl.auto", "validate");
        props.put("hibernate.show_sql", "false");
        props.put("hibernate.jdbc.batch_size", "50");
        sf.setHibernateProperties(props);
        return sf;                               // FactoryBean -> exposes SessionFactory
    }

    @Bean
    public HibernateTransactionManager transactionManager(SessionFactory sessionFactory) {
        return new HibernateTransactionManager(sessionFactory);
    }
}

When you need the native API, unwrap it:

@Service
public class BulkSensorIngestService {

    private final EntityManagerFactory emf;
    @PersistenceContext private EntityManager em;

    public BulkSensorIngestService(EntityManagerFactory emf) { this.emf = emf; }

    public SessionFactory sessionFactory() {
        return emf.unwrap(SessionFactory.class);          // e.g. for Statistics, StatelessSession
    }

    @Transactional
    public void useNativeSession() {
        Session session = em.unwrap(Session.class);       // the transaction-bound Session
        session.setJdbcBatchSize(100);
    }

    public void statelessInsert(List<SensorReading> readings) {   // high-volume IoT ingest, no persistence context
        try (StatelessSession ss = sessionFactory().openStatelessSession()) {
            Transaction tx = ss.beginTransaction();
            readings.forEach(ss::insert);
            tx.commit();
        }
    }
}

Likely follow-ups:

  • getCurrentSession vs openSession? getCurrentSession is bound to the current transaction and closed automatically. openSession is a new one that you must close.
  • Why is SessionFactory expensive? It parses all mappings, builds metamodels and SQL, and initialises caches. Do it once.
  • What is a StatelessSession? It has no first-level cache, dirty checking or cascades. It suits bulk inserts.

Steps:

@Configuration

Gotchas

  • @Primary is required on one set. Otherwise auto-configured consumers (JdbcTemplate, Flyway, Actuator health) hit NoUniqueBeanDefinitionException.
  • Boot's spring.jpa.* naming strategy and ddl-auto are applied to the EMF built by EntityManagerFactoryBuilder only partially. Pass Hibernate settings explicitly in properties(...), as above, for consistent naming.

C25 Lazy vs eager loading in Hibernate.
Relationship Default fetch
@ManyToOne, @OneToOne EAGER
@OneToMany, @ManyToMany LAZY
  • Lazy loads a proxy and runs the query only when the association is accessed. Eager loads it immediately. Best practice: make everything LAZY (@ManyToOne(fetch = FetchType.LAZY)) and fetch what each use case needs.
  • LazyInitializationException: you accessed a lazy association after the session or transaction closed, for example in the controller or during JSON serialisation. Fix it by fetching inside a transaction, using a fetch join or entity graph, or mapping to a DTO. Do not rely on Open-Session-In-View; Boot enables it by default, so set spring.jpa.open-in-view=false.
  • N+1 problem: 1 query loads N parents, then N more queries load each child collection.

Fixes:

@Query("select d from Department d join fetch d.employees where d.id = :id")
Optional<Department> findWithEmployees(@Param("id") Long id);

@EntityGraph(attributePaths = "employees")
List<Department> findAll();

Other options are @BatchSize(size = 50) or hibernate.default_batch_fetch_size, and DTO projections.

Defaults (JPA)

Association Default fetch
@ManyToOne, @OneToOne EAGER
@OneToMany, @ManyToMany LAZY
@ElementCollection LAZY
@Basic fields EAGER (lazy basics need bytecode enhancement)

Best practice: make everything LAZY (@ManyToOne(fetch = FetchType.LAZY)) and fetch explicitly per use case. EAGER can't be turned off per query, and it causes hidden extra queries (eager @ManyToOne under JPQL triggers N+1).

How lazy works

  • For to-one: Hibernate puts a proxy (a ByteBuddy subclass, Employee$HibernateProxy$...) holding only the id. The first call to a non-id getter initialises it with a SELECT.
  • For collections: a PersistentBag/PersistentSet wrapper loads on first access (size(), iteration).
  • Initialisation needs an open Session/persistence context.

Anti-fixes: making things EAGER, hibernate.enable_lazy_load_no_trans=true (opens a new session per lazy load), or relying on OSIV.

Open Session in View (spring.jpa.open-in-view)

  • Boot sets it to true by default and logs a warning. OpenEntityManagerInViewInterceptor keeps the EntityManager open for the whole web request, so lazy loads in the controller or Jackson "work".
  • The cost: DB connections are held for the entire request, including slow serialisation and remote calls, which can exhaust the pool under load. Queries also fire from the view layer (hidden N+1), and the transaction boundary is blurred.
  • Set spring.jpa.open-in-view=false in services and fetch deliberately.

Pagination gotcha: JOIN FETCH of a collection combined with Pageable makes Hibernate warn HHH90003004 ("firstResult/maxResults specified with collection fetch; applying in memory"). C26 One-to-Many relationship across multiple tables.

For a bidirectional mapping, the child (@ManyToOne) owns the foreign key, and the parent uses mappedBy.

@Entity
public class Department {
    @Id @GeneratedValue private Long id;
    @OneToMany(mappedBy = "department", cascade = CascadeType.ALL, orphanRemoval = true)
    private List<Employee> employees = new ArrayList<>();

    public void addEmployee(Employee e) { employees.add(e); e.setDepartment(this); } // keep both sides in sync
    public void removeEmployee(Employee e) { employees.remove(e); e.setDepartment(null); }
}

@Entity
public class Employee {
    @Id @GeneratedValue private Long id;
    @ManyToOne(fetch = FetchType.LAZY)
    @JoinColumn(name = "department_id")       // FK column in employee table
    private Department department;
}
  • cascade = ALL: saving or deleting the department cascades to its employees.
  • orphanRemoval = true: removing an employee from the list deletes its row.
  • Join table option (unidirectional, no FK in the child table): @OneToMany @JoinTable(name="dept_emp", joinColumns=@JoinColumn(name="dept_id"), inverseJoinColumns=@JoinColumn(name="emp_id")). A unidirectional @OneToMany without @JoinColumn creates a join table by default.
  • Chains across tables (City → Zone → Device) are just repeated one-to-many mappings. Fetch the levels you need with join fetch or an entity graph.
  • Avoid toString/equals that touch both sides, because that causes infinite recursion. In JSON, use DTOs or @JsonManagedReference.

Bidirectional Department (1) → Employee (N)

  • The owning side is the side with the foreign key: Employee.department (@ManyToOne + @JoinColumn). Only the owning side's changes are written to the FK column.
  • The inverse side is Department.employees (@OneToMany(mappedBy = "department")). It is a mirror for navigation.

Cascade and orphanRemoval

  • cascade = ALL (PERSIST, MERGE, REMOVE, REFRESH, DETACH) belongs only on parent → child (composition). Never cascade from @ManyToOne (removing an employee would delete the department) or on @ManyToMany REMOVE.
  • orphanRemoval = true deletes a child removed from the collection. CascadeType.REMOVE deletes children only when the parent is deleted.
  • Don't replace the collection (setEmployees(new ArrayList<>())) when orphanRemoval is on. Hibernate throws "A collection with cascade=all-delete-orphan was no longer referenced". Call clear() and then addAll() instead.

@JoinColumn(name = "department_id")   // unidirectional with FK in child: extra UPDATE statements to set FK

@ManyToMany
@JoinTable(name = "employee_project",
        joinColumns = @JoinColumn(name = "employee_id"),
        inverseJoinColumns = @JoinColumn(name = "project_id"))
private Set<Project> projects = new HashSet<>();

A unidirectional @OneToMany without @JoinColumn produces an unexpected join table and inefficient SQL. Prefer bidirectional, or plain @ManyToOne alone. For a join table with extra columns (e.g. assigned_on), model it as an entity (EmployeeProject) with two @ManyToOnes.

  • Lombok @Data/@ToString/@EqualsAndHashCode on bidirectional entities cause StackOverflowError (recursive toString/hashCode) and trigger lazy loads.

  • Index FK columns. Postgres doesn't index them automatically.

package com.trinity.citypulse.audit;

import com.fasterxml.jackson.databind.ObjectMapper;
import org.aspectj.lang.ProceedingJoinPoint;
import org.aspectj.lang.annotation.Around;
import org.aspectj.lang.annotation.Aspect;
import org.slf4j.MDC;
import org.springframework.security.core.context.SecurityContextHolder;
import org.springframework.stereotype.Component;

import java.time.Instant;

@Aspect
@Component
public class AuditAspect {

    private final AuditWriter writer;
    private final ObjectMapper mapper;

    public AuditAspect(AuditWriter writer, ObjectMapper mapper) { this.writer = writer; this.mapper = mapper; }

    @Around("@annotation(audit)")
    public Object around(ProceedingJoinPoint pjp, AuditAction audit) throws Throwable {
        // capture context ON the request thread (SecurityContext/MDC are ThreadLocal)
        var auth = SecurityContextHolder.getContext().getAuthentication();
        String user = auth != null ? auth.getName() : "system";
        String correlationId = MDC.get("correlationId");
        String args = safeJson(pjp.getArgs());
        long start = System.currentTimeMillis();
        try {
            Object result = pjp.proceed();
            writer.write(new AuditEvent(audit.value(), user, args, "SUCCESS", null,
                    correlationId, Instant.now(), System.currentTimeMillis() - start));
            return result;
        } catch (Throwable ex) {
            writer.write(new AuditEvent(audit.value(), user, args, "FAILURE", ex.getMessage(),
                    correlationId, Instant.now(), System.currentTimeMillis() - start));
            throw ex;
        }
    }

    private String safeJson(Object[] args) {
        try { return mapper.writeValueAsString(args); } catch (Exception e) { return "[unserializable]"; }
    }
}
public record AuditEvent(String action, String username, String payload, String outcome, String error,
                         String correlationId, Instant at, long durationMs) { }

Code generation: option A, Base62 of a DB sequence or ID (recommended)

  • Characters [0-9a-zA-Z]. 62^7 ≈ 3.5 trillion codes, so 7 characters is plenty.
  • id → Base62 is a bijection, so there are no collisions by construction.
  • Downside: sequential codes are guessable/enumerable. Fixes: start at a large offset, apply a reversible permutation or obfuscation of the id (Feistel cipher, Hashids/Sqids), or use a random 64-bit id.
  • To scale writes: give each app instance a range of ids (e.g. reserve 10,000 at a time from the DB or Redis INCRBY), or use Snowflake ids. Then no DB round trip is needed per create.
public final class Base62 {
    private static final char[] ALPHABET =
            "0123456789abcdefghijklmnopqrstuvwxyzABCDEFGHIJKLMNOPQRSTUVWXYZ".toCharArray();
    private Base62() { }

    public static String encode(long value) {
        if (value == 0) return "0";
        StringBuilder sb = new StringBuilder();
        while (value > 0) {
            sb.append(ALPHABET[(int) (value % 62)]);
            value /= 62;
        }
        return sb.reverse().toString();
    }

    public static long decode(String s) {
        long result = 0;
        for (char c : s.toCharArray()) {
            int d;
            if (c >= '0' && c <= '9') d = c - '0';
            else if (c >= 'a' && c <= 'z') d = c - 'a' + 10;
            else if (c >= 'A' && c <= 'Z') d = c - 'A' + 36;
            else throw new IllegalArgumentException("Invalid char " + c);
            result = result * 62 + d;
        }
        return result;
    }
}

Option B: hash the long URL (MD5/SHA-256/MurmurHash, Base62-encoded, first 7 characters)

  • It is deterministic: the same URL gives the same code, so dedupe comes for free.
  • Truncation causes collisions. Seven Base62 characters carry only about 41.7 bits. By the birthday paradox, there is about a 50% chance of at least one collision after roughly 2 million URLs, and at billions of URLs collisions happen constantly. On collision, append a salt or counter and rehash, then retry.
  • Every create needs a DB check.

Collision and duplicate handling

  • A unique index on short_code is the final arbiter. Insert, and on DataIntegrityViolationException regenerate and retry (bounded, e.g. 3 times). Never "check then insert", which is a race.
  • Same long URL submitted again: keep a long_url_hash column (SHA-256) with a unique index (per user/tenant if needed), and return the existing code instead of creating a new one. Hash it because long URLs exceed index-length limits.
  • Custom aliases go through the same unique index. A conflict returns 409 Conflict.

C29 What does LOC mean?

LOC = Lines of Code. It is a size metric for a codebase or a change, sometimes used for effort or productivity estimates and code-quality ratios (defects per KLOC). Variants are SLOC (source lines, excluding blanks and comments) and KLOC (thousands). It is a weak productivity measure, because fewer, cleaner lines are often better. In a banking/trade-finance context, LOC can also mean Letter of Credit: a bank's guarantee of payment to a seller on behalf of a buyer.

It depends on the context, so clarify it in the interview ("Do you mean lines of code?").

  1. Lines of Code (software engineering): a size metric for a codebase or a change.
    • Variants: physical LOC (all lines), SLOC/NCLOC (source lines excluding blanks and comments; SonarQube reports "Lines of Code" as NCLOC), and logical LOC (statements).
    • Uses: rough size and effort estimation (COCOMO), normalising defect density (bugs per KLOC), and tracking code growth or PR size (small PRs, roughly under 400 LOC, review better).
    • Limits: it measures volume, not value or quality. Fewer lines often means better code, and LOC varies by language and style. Never use it as a productivity metric. Better signals: cyclomatic or cognitive complexity, coverage, DORA metrics, and story or cycle-time throughput.
    • Tools: cloc, tokei, SonarQube, git diff --stat.
  2. Letter of Credit (banking/trade finance): a bank's guarantee to pay a seller on behalf of a buyer once documents meeting the terms are presented (governed by UCP 600). Types include sight/usance, revocable/irrevocable, confirmed, standby LC (SBLC) and back-to-back. This matters if the interviewer's domain is BFSI. Messages travel over SWIFT (MT700 for issuance).
  3. Others: Line of Control (geography), and Locus of Control (psychology).

In a Smart City context it is almost always lines of code, e.g. "The incident service is about 25K LOC across 6 modules, with 80% coverage."

C30 @Transactional and why transaction management is used. Hexaware

Transactions guarantee ACID for a unit of work. Either all DB operations commit or all roll back, for example "debit + credit" or "save incident + save assignment". @Transactional is declarative. Spring wraps the bean in an AOP proxy that begins, commits or rolls back through the PlatformTransactionManager.

Key attributes:

Attribute Key points
propagation REQUIRED (default: join the existing transaction or create one), REQUIRES_NEW (suspend the outer one and start a new one, e.g. for an audit log), NESTED (savepoint), SUPPORTS, MANDATORY, NEVER, NOT_SUPPORTED
rollbackFor By default, rollback happens only on unchecked exceptions (RuntimeException, Error). Checked exceptions commit unless you set rollbackFor = Exception.class
readOnly = true Flush and dirty-checking optimisations for queries
isolation, timeout Isolation level and timeout

Pitfalls:

  • Self-invocation. Calling a @Transactional method from another method of the same class bypasses the proxy, so no transaction is applied. Fix it by moving the method to another bean or injecting self/TransactionTemplate.
  • @Transactional has no effect on private methods; it applies only to proxied, public methods.
  • Catching the exception inside the method prevents rollback.

How it works (proxy-based AOP)

  • @EnableTransactionManagement (auto-enabled by Boot) registers BeanFactoryTransactionAttributeSourceAdvisor with TransactionInterceptor.
  • At bean creation, the auto-proxy creator wraps @Transactional beans in a CGLIB proxy (C4).
  • A call through the proxy goes to TransactionInterceptor.invoke → TransactionAspectSupport.invokeWithinTransaction:
    1. read the TransactionAttribute (propagation, isolation, timeout, readOnly, rollback rules);
    2. PlatformTransactionManager.getTransaction(def). JpaTransactionManager begins the JPA transaction, takes a JDBC connection, and binds the EntityManagerHolder/ConnectionHolder to the thread through TransactionSynchronizationManager (ThreadLocal);
    3. invoke the target method;
    4. on success, commit (flush, then commit). On an exception, check rollbackOn(ex) and roll back, or commit if the rule says so;
    5. clean up and unbind.

Propagation

Propagation Existing tx present No tx present
REQUIRED (default) join it create a new one
REQUIRES_NEW suspend it and create an independent new one (a new connection!) create a new one
NESTED savepoint inside the existing tx (rolls back to the savepoint only). Supported with JDBC DataSourceTransactionManager; limited with JPA create a new one
SUPPORTS join it run non-transactionally
NOT_SUPPORTED suspend it, run non-transactionally run non-transactionally
MANDATORY join it throw IllegalTransactionStateException
NEVER throw run non-transactionally

The use case for REQUIRES_NEW is audit or failure logging that must persist even when the outer transaction rolls back. The cost: it holds 2 connections per thread, so under load you risk pool exhaustion or deadlock.

Isolation levels

Level Dirty read Non-repeatable read Phantom
READ_UNCOMMITTED possible possible possible
READ_COMMITTED (Postgres/Oracle/SQL Server default) no possible possible
REPEATABLE_READ (MySQL InnoDB default) no no possible (InnoDB prevents most with next-key locks)
SERIALIZABLE no no no

Isolation.DEFAULT uses the DB default. For counters and inventory (e.g. parking slot booking), prefer optimistic locking (@Version) or SELECT ... FOR UPDATE (@Lock(PESSIMISTIC_WRITE)) over raising the isolation level globally. Note: JpaTransactionManager supports a custom isolation level only through HibernateJpaDialect.

Rollback rules

  • By default it rolls back on unchecked exceptions (RuntimeException) and Error, and commits on checked exceptions (an EJB heritage).
  • @Transactional(rollbackFor = Exception.class) or noRollbackFor = BusinessWarningException.class.
  • Catching the exception inside the method means no rollback, unless you rethrow or call TransactionAspectSupport.currentTransactionStatus().setRollbackOnly().
  • UnexpectedRollbackException: an inner REQUIRED method throws, so the shared transaction is marked rollback-only. The outer method catches the exception and tries to commit, and Spring throws "Transaction silently rolled back because it has been marked as rollback-only". Fix it with REQUIRES_NEW for the inner call, by not catching, or by redesigning.

readOnly = true

  • Hibernate sets the session to FlushMode.MANUAL and read-only, so no dirty-checking snapshots are kept (less memory and CPU).
  • It calls Connection.setReadOnly(true) as a hint to the driver or DB, which can route to a replica with a routing DataSource.
  • It does not prevent writes in all DBs. Native queries may still write.

The self-invocation pitfall

@Service
public class ChallanService {
    public void processBatch(List<Long> ids) {
        ids.forEach(this::processOne);       // 'this' = target, NOT the proxy -> no transaction!
    }

    @Transactional(propagation = Propagation.REQUIRES_NEW)
    public void processOne(Long id) { ... }
}

Fixes:

  1. Move processOne to another bean (the cleanest fix).
  2. Self-injection: @Lazy @Autowired private ChallanService self; then self.processOne(id).
  3. TransactionTemplate (programmatic):
    private final TransactionTemplate txTemplate;   // inject PlatformTransactionManager, then new TransactionTemplate(tm)
public void processBatch(List<Long> ids) {
    ids.forEach(id -> txTemplate.executeWithoutResult(status -> processOneInternal(id)));
}
  4. AspectJ weaving mode (@EnableTransactionManagement(mode = AdviceMode.ASPECTJ)), which has no proxy limitations but needs build or load-time weaving.

Method visibility

  • Private methods are never transactional. The proxy can't override them, and Spring silently ignores the annotation.
  • Since Spring 6.0, protected and package-private methods work with CGLIB class proxies. Before 6.0, only public methods worked.
  • final methods can't be overridden either, so no transaction. The same goes for static methods.

Other gotchas

  • @Transactional on a @PostConstruct method has no effect (C5).
  • @Async plus @Transactional: the transaction is on the async thread. ThreadLocal transactions don't cross threads.
  • A long transaction holding a DB connection while calling remote APIs: do the HTTP calls outside the transaction.
  • timeout = 5 (seconds) sets the query timeout.
  • In tests, @Transactional on a test class rolls back after each test by default.

Likely follow-ups:

  • Class-level vs method-level @Transactional? The method-level annotation overrides the class-level one. Class level applies to all methods the proxy can intercept.
  • Does @Transactional work on interfaces? Yes, since Spring 5, also with class proxies. Annotating the concrete class is still recommended.
  • How do you run code after a commit? @TransactionalEventListener(phase = AFTER_COMMIT), or TransactionSynchronizationManager.registerSynchronization.

Enable caching with @EnableCaching. With @Cacheable, the first call runs the method and stores the result. Later calls with the same key return the cached value without hitting the DB, which reduces latency and DB load for read-heavy data such as master data or device configs.

@CacheEvict(value = "employees", key = "#id")

Preventing DB problems:

Problem Fix
Stale or unbounded memory TTL plus size-based eviction (Caffeine maximumSize, Redis time-to-live)

Consistency across instances and microservices:

  • When another service owns the data, publish a domain event (Kafka) or Redis pub/sub on change, and consumers evict their entries.
  • Short TTLs are the safety net. For a two-level cache (local + Redis), broadcast invalidations.

What to cache: read-mostly reference data (wards, junction metadata, device configs), expensive aggregations, and remote API responses. Don't cache highly volatile or per-user sensitive data without careful keys and TTLs. Never cache JPA entities (lazy proxies, detached state).

Cache consistency across multiple instances and microservices

The problem: with a local cache, instance A updates the DB and evicts its own cache, but instances B and C keep serving stale data until their TTL expires.

Strategies:

  1. A centralised distributed cache (Redis): every instance reads and evicts the same entry, so instance divergence goes away.
  2. Cache-aside with evict-on-write: write to the DB, then delete the cache key (@CacheEvict). Don't update the cache: concurrent writers can leave a stale value. Do it after commit (transactionAware() or @TransactionalEventListener(AFTER_COMMIT)). Otherwise a reader can re-populate the old value between the eviction and the commit.
    • Remaining race: a reader misses, loads the old value, the writer commits and evicts, then the reader writes the old value. This is rare. Mitigations are a delayed double delete (evict again after ~500 ms) and short TTLs.
  3. Write-through / write-behind: the cache layer writes to the DB synchronously (through) or asynchronously (behind, which risks data loss). It suits cache-first systems (Hazelcast/Redis Gears) and is less common with Spring's annotations.
  4. Two-level (Caffeine + Redis) with broadcast invalidation: on write, publish {cache, key} on Redis Pub/Sub or a Kafka topic. Every instance subscribes and evicts its local L1 entry.
  5. Cross-microservice ownership: service X caches data owned by service Y. Y publishes domain events (JunctionUpdated) to Kafka, and X's consumer evicts or refreshes its cache. Even better is CDC (Debezium) from Y's DB, which catches every change including manual SQL fixes.
  6. Versioning: keys include a version (junction:{id}:v{version}) or a namespace version (citypulse:v2:). Bumping it invalidates everything at once, which helps with schema changes in DTOs. You can also compare @Version before serving.
  7. Short TTL as a safety net: even with explicit invalidation, always set a TTL so missed events self-heal.

Here is an example of Kafka-driven eviction:

@Component
public class JunctionCacheInvalidator {
    private final CacheManager cacheManager;
    public JunctionCacheInvalidator(CacheManager cacheManager) { this.cacheManager = cacheManager; }

    @KafkaListener(topics = "junction-events", groupId = "#{T(java.util.UUID).randomUUID().toString()}") // every instance gets it
    public void onEvent(JunctionChangedEvent event) {
        var cache = cacheManager.getCache("junction");

    }
}

package com.trinity.hr.employee;

import com.trinity.hr.common.ResourceNotFoundException;
import org.junit.jupiter.api.DisplayName;
import org.junit.jupiter.api.Nested;
import org.junit.jupiter.api.Test;
import org.junit.jupiter.api.extension.ExtendWith;
import org.mockito.ArgumentCaptor;
import org.mockito.Captor;
import org.mockito.InjectMocks;
import org.mockito.Mock;
import org.mockito.junit.jupiter.MockitoExtension;

import java.math.BigDecimal;
import java.time.LocalDate;
import java.util.Optional;

import static org.assertj.core.api.Assertions.assertThat;
import static org.assertj.core.api.Assertions.assertThatThrownBy;
import static org.mockito.ArgumentMatchers.any;
import static org.mockito.BDDMockito.given;
import static org.mockito.BDDMockito.then;
import static org.mockito.Mockito.never;

@ExtendWith(MockitoExtension.class)
class EmployeeServiceTest {

    @Mock EmployeeRepository repository;
    @InjectMocks EmployeeService service;
    @Captor ArgumentCaptor<Employee> employeeCaptor;

    @Nested
    @DisplayName("getEmployeeById")
    class GetById {

        @Test
        void returnsDto_whenEmployeeExists() {
            Employee e = new Employee("Asha", "asha@trinity.com", "Traffic", new BigDecimal("90000"),
                    LocalDate.of(2022, 1, 10));
            given(repository.findById(1L)).willReturn(Optional.of(e));

            assertThat(dto.name()).isEqualTo("Asha");
            assertThat(dto.department()).isEqualTo("Traffic");

            then(repository).should(never()).save(any());

    }
}

import java.time.LocalDate;

import static org.assertj.core.api.Assertions.assertThat;

@DataJpaTest

    @ServiceConnection                                   // Boot 3.1+: wires spring.datasource.* automatically

                .andExpect(content().contentType(MediaType.APPLICATION_PROBLEM_JSON))

5. Integration-level checks

  • @DataJpaTest with duplicate data: assertThatThrownBy(() -> repo.saveAndFlush(dup)).isInstanceOf(DataIntegrityViolationException.class). You need saveAndFlush, because the constraint only fires on flush.
  • Transaction rollback: call the service in a non-transactional test, force an exception, then assert the DB row count is unchanged.
  • Async or Kafka error paths: use Awaitility to assert that the message landed in the DLT.

Gotchas

  • Put only the throwing call inside the lambda. If the setup is inside it, a setup failure can satisfy the assertion and give a false pass.
  • With Mockito strict stubs, an unused willThrow stub fails the test (UnnecessaryStubbingException). That's good, because it flags dead setup.
  • Don't catch and swallow exceptions in tests (try { ... } catch (Exception e) { }). Use fail() if you must use try/catch.
  • Checked exceptions: test methods can declare throws Exception. That is better than wrapping.

Likely follow-ups:

  • assertThrows vs assertThatThrownBy? Both work. assertThrows returns a typed exception, while AssertJ chains assertions fluently (message, cause, fields).
  • How do you test that a void method throws? assertThrows(X.class, () -> service.voidMethod()). To make a mock's void method throw, use doThrow(...).when(mock).voidMethod().
  • How do you verify nothing was saved after an exception? verify(repository, never()).save(any()), or verifyNoMoreInteractions.
